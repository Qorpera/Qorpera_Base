# Coding sessions: the executor

This is the Linux LXD/Codex executor for runtime-contract Order 9, on the coding-session kernel of Step 9 part 1 (migration `20260922210000`, sessions as sponsored workers) and part 3 (`20260922220000`, the executor's SQL). Order 9 remains open until installed acceptance is complete. The migrations leave coding execution disabled until an operator configures an executor (`qorpera_configure_coding_executor`), its repository grants, its VM policy and its NAS policy.

## Execution path

An agent dispatches a coding session through `manage_worker` (species `coding`); the session is owned and sponsored by one member, who may have any number of sessions. The executor claims session turns with renewable SQL leases (`qorpera_claim_coding_session`) and runs many at once. Each turn runs on its member's coding machine: one LXD VM per company, environment, member, coding agent, repository and setup digest (20260930394000; per member since bundle v101), planned in SQL from the executor's VM policy (`qorpera_plan_coding_machine`) and started, or woken, on reserved company and node capacity. The executor hot-plugs the session's two exact NAS folders into it, installs the session's configuration and user, and seeds a credential-free checkout at a pinned base, once per session, and records the session's attachment (`qorpera_attach_coding_session`). The session then stays attached between turns (see below). The machine has no identity volume and no GitHub, provider or cloud-control credential; each session has its fixed branch (`qorpera/coding/<worker>`). The executor then admits the model turn through the wake bus under the owner's own sponsor (`qorpera_begin_coding_turn`). Model turns never run on the coding machine; the harness runs on the member's execution host and reaches the machine only through the command gateway. A turn that cannot have its machine yet (a full node, its machine being removed, the session still on an earlier machine that is awake) goes back to the queue (`qorpera_defer_coding_session`) and is claimed again later; nothing counts or caps sessions.

The native harness runs the turn on the identity host like any other run, in the coding composition: three tools start/read/cancel repository commands through this service's command gateway, `coding_finish` submits a commit, `coding_ask` submits a question for the owner. Commands execute as the session's own uid in the session's systemd slice, with no time, memory, CPU or task limit of their own (the agent may set a deadline for one command); the member's sessions share the machine by equal cgroup weights, and the machine keeps a reserve for its own control (`MemoryMax=90%` and `TasksMax=90%` on `qorpera-coding.slice`). A root-owned guest lease, tied to the boot and Linux uptime, follows the session's attachment and expires independently of the executor's network connection; a reviewed timer stops the session's slice on expiry. A receipt's hash binds the exact command, deadline, worker, VM, turn id and sequence. A command starts only in its own turn: it is authorized in SQL against the turn (`qorpera_authorize_coding_command`) and the guest lease must name that turn open. Reading and cancelling reach the session's commands of any of its turns.

The harness's submission is durable in SQL (`qorpera_submit_coding_turn`); the executor waits on `qorpera_describe_coding_turn` for the run to end and acts on the submission, never on prose. A commit is exported as a bundle, validated in a fresh constrained Git broker, pushed only to the fixed session branch, and published as the same draft PR. The turn ends (`qorpera_complete_coding_turn`: succeeded with the PR, blocked with the question and its choices, or failed) without detaching the session: it stands by on its machine with its user, folders and whatever its commands left running, like an open Claude Code session. The owner's answer or a follow-up starts the next turn on the same worker, NAS folders, repository and branch, on the member's current machine; a session still attached keeps its attachment's generation, so its running commands are there, and the turn's context names them (`commands.running`), with the ones stopped since the previous turn (`commands.stopped`: the machine slept, the session was archived, the executor lost it). Every turn is a row of its own (`qorpera_coding_session_turns`, 20260925113000): what started it (the dispatch, the agent's follow-up or the owner's answer), the harness's submission, which belongs to that turn's sequence only, and how it ended. The next turn reads them through its run authority (`qorpera_read_coding_turn_context`) and the native runtime composes them into its context: the exact question and choices a reply answers, and the session's earlier turns (the newest that fit, the rest counted). A new turn never inherits an earlier submission; when an executor is lost after the harness submitted, the lease expiry settles that turn as failed, keeps the submission in it and names the unanswered question or the unpublished commit, and the owner's retry runs clean. The provider thread itself is not resumed: continuity is the composed record, not provider-held state.

## Sessions between turns: standing by, archive

A session is attached to its member's machine by its first turn and stays attached, under an attachment of its own (a token and a deadline on `qorpera_coding_sessions`), until it is archived, its attachment ends or the machine sleeps. Every 10 s the executor's keeper takes each awake machine that carries attached sessions: the pinned storage helper's `observe` action publishes, per session, the commands whose processes still run, the processor time its slice has used and its guest lease (`/run/qorpera-coding/observation.json`, running commands per session beside it); `qorpera_keep_coding_attachments` renews each attachment for a minute with that observation and names its current turn (open only while the turn prepares or runs); the executor renews the session's guest lease under the renewed deadline (TTL at most 45 s). A session SQL releases (archived, owner no longer a member, repository grant withdrawn, executor disabled, deadline passed) is taken off: its running commands are cancelled through the command helper, the guest's `detach` stops its slice and removes its boot-local state and user, its folders are unplugged under detach custody, and the detach is recorded with what it stopped (`qorpera_record_coding_session_detached`). A session whose guest lease of the live generation has run out for good is left out of the observation, so SQL releases it (`EXPIRED`, after a 30 s grace for a fresh attach) and it is taken off the same way. A turn keeps its session's generation only if the guest's lease of it has at least 15 s left (`p_guest_generation`); otherwise it takes a new generation, which stops anything an earlier one left. Machines are kept side by side, each within 15 s, in a pass every 10 s from the start of the last one, so every guest lease is renewed at least every 30 s; take-offs run beside the passes (one per session at a time) and hold the machine's lifecycle step. A session whose turn this executor still runs and whose guest lease ran out is attached again under the turn's own authority as a new generation, so the turn goes on; an attach whose kept generation ran out in the guest meanwhile attaches once more the same way. A restarted executor adopts attached sessions from the guest's active configuration, which must equal the one it journaled for that boot; a restart shorter than the guest lease keeps their commands running.

**Archive.** The owner archives a session from its thread (`qorpera_archive_coding_session`), the agent with `manage_worker` action `archive`, and the executor archives a session with no turn and no busy command for `session_archive_after_seconds` (default 30 days, `qorpera_archive_quiet_coding_sessions`, checked every 10 minutes). Before that, the folder drain `coding_checkins` asks the agent that started a quiet session, once each after 1, 3 and 7 days, whether it can be archived (`qorpera_folder_coding_checkins_company`, 20260928519100; the executor's scan asked it until the legacy sweep's F3a, 20260930294000): a worker-completion continuation of the agent whose report is the question, answered with `manage_worker` action `archive` or left alone. A session archived, reopened or busy meanwhile is not asked; a new turn starts a new quiet period and withdraws a question no run has taken yet, and a question's run cannot archive a session that got a new turn after it was asked. A person who stops a question run stops only that run, and the session is not asked again in that quiet period. Sessions already quiet when the migration ships are asked from their next mark on. The runtime gives these wakes their own instruction (occurrence key `coding-quiet:`); ship the migration in the same cut as that bundle. A turn still working is cancelled first. The attachment ends at once, so the keeper takes the session off within seconds. Its NAS folders stay. A follow-up or an answer reopens it.

## Member machines: sleep, wake and removal

Every 30 s the executor asks SQL for its machines on this node (`qorpera_list_coding_machines`) and acts on the ones due:

- **Sleep.** A machine sleeps after `machine_sleep_after_seconds` (default 600) with no session turn on it and no command using the processor: the keeper reports a session busy when its slice used more than 5 % of one core since its previous look, and a busy session keeps the machine awake; a server that only waits does not. Each attached session is taken off first (its running commands cancelled, its slice stopped, its boot-local state removed), then every command slice is stopped and the guest synced, the machine is powered off under its journal, its session folders are unplugged while it is off, its node demand is suspended (`qorpera_suspend_coding_machine`), and each session's detach is recorded as `SLEEP` with what it stopped. Asleep, it holds no node capacity; its root disk and every session's files stay. The next turn wakes it (re-reserving capacity, or waiting in the queue on a full node). LXD cannot keep a sleeping machine's memory instead: it refuses `migration.stateful` for any VM with a shared-folder disk (LXD 6.9, `lxd/device/disk.go`), and every session's NAS folders are shared folders.
- **Removal.** A machine asleep for `machine_remove_after_seconds` (default 600) once none of its own sessions is open (unarchived; a session of the member's on another of their machines does not keep it, 20260930394000), or planned from an older VM policy, is deleted under a journaled LXD delete; only that delete plus LXD's absence of the instance releases its allocation (`qorpera_release_coding_machine`). A machine planned from an older policy is removed at the next moment with no turn on it; its sessions are recorded as `RETIRED`. A machine never given node capacity, or already released elsewhere, is closed without touching LXD. The member's next turn gets a new machine; the NAS folders are never removed by this.
- **Kept per-session VMs** from before bundle v101 are retired the same way (stopped, deleted, released) once their session has no turn; only the VMs go, their NAS folders stay. A session whose previous machine is still awake waits until it sleeps (`PREVIOUS_MACHINE_AWAKE`).

SQL re-checks custody for every effect, so a turn that takes the machine in the meantime only makes the step "not now". A hot-plug, a take-off, a sleep and a delete of one machine never overlap; the keeper's renewals run beside them, each machine within 15 s of its pass, and its take-offs run beside its passes. A failed step is written to the machine (`last_error`, `qorpera_record_coding_machine_error`), logged as `coding-machine-error`, and retried at the next pass; a later success clears it. A failed release is its own step (`release`): after a delete the machine is gone but its capacity is not yet returned; for a machine that never had one, or was released elsewhere, only the record is not yet closed. Housekeeping runs beside claiming, so a long pass never holds up a turn. Nothing is hidden or silently dropped. Both delays are per-environment configuration (`qorpera_configure_coding_machine_lifecycle(environment, owner, sleepAfterSeconds, removeAfterSeconds)`, 60–86400 s and 300–31536000 s), not constants; so is `session_archive_after_seconds` on the executor row.

A stop first takes the attached sessions off (20 s), stops the command slices and syncs the guest (8 s), then powers the machine off within 30 s; a stop LXD reports failed, or no longer knows, is settled from the machine's own state and re-issued while it still runs, at most three times in a row. A delete is re-issued the same way only while the machine is there and stopped. A machine whose journal cannot settle is `recovery-required` for an operator. When that is because an effect's submission failed (its dispatch is the journal's tail, and whether LXD took it is unknown), what the submission threw is written next to the journal for that operator: `dispatch-error-<segment>-<sequence>.json` (schema `qorpera.coding-machine-dispatch-error/v1`: the dispatch's segment, sequence and action, the error's fixed code, and LXD's own answer when it gave one, its HTTP status, error code and message on one line), and the step's code names LXD's status (`CODING_HOST_VM_RECOVERY_REQUIRED:LXD_REFUSED_<status>`).

**Failures a turn names (C8 C4-1).** A turn whose workspace cannot be made for one of these fails at once with its reason and code (`qorpera_complete_coding_turn`, under its lease), instead of leaving its lease to lapse as "The coding executor stopped responding":
- `CODING_HOST_STORAGE_TIMEOUT`: a step on the NAS ran out of its 5 s. A folder check (the control path's `machines`, `guests` and `git` folders, a wake's first step) is tried three times in all, after 250 ms and then 500 ms; each try waits for the one before it, so a NAS that does not answer still gets one request at a time, and the step fails after about 16 s.
- `CODING_MACHINE_PROJECT_REFUSES_AGENT_CARD`: before a create with the agent card the executor reads the machine's LXD project, read only (`GET /1.0/projects/<project>`), and LXD's own rule refuses the card there (`deploy/agent-exit/ROLLOUT.md` step 0: `restricted.devices.nic=allow` not set). Nothing is plugged, dispatched or written down, so the machine needs no operator: the next turn creates it once the project allows the card. The executor never changes the project.
- The code host's own codes (`CodeHostJobFailure`, `CodeHostRefusal`: `CODE_HOST_WORKTREE_FAILED`, `CODE_HOST_WORKTREE_NO_BRANCH`, `CODE_HOST_SEED_FAILED` and the rest in `code-host-jobs.ts` and `code-host-seed.ts`): the job that makes the session's worktree in the company folder (`attachCodeSession`) failed a step or was refused by rule. The turn says "Making the session's copy of the code failed. The workspace is kept; a follow-up tries again. [code=…]".

**What the log keeps of an error.** A `coding-turn-error` line, and a code host's `code-host-error` and `code-host-view-error` lines, carry the error's `code` and, when it says more than that, its `detail`: git's message or the paths a code host's rule names (a code host error reads `CODE: detail`, and is logged by its own code, never `UNCLASSIFIED`), or another error's own text, or its cause's under a bare code. The detail is one line of at most 500 characters (its start and its end), with anything shaped like a credential taken out first (`redactCodingErrorText`: a URL's user and password, an Authorization header's value, basic and bearer credentials, GitHub tokens, `token=`, `password=`, `secret=` and `key=` values, and opaque runs of 32 or more characters that mix cases and digits). Paths, digests and names stay. It reaches the log only, not the turn's result: the member's card reads that result's words.

**Machines stopped from outside.** A member's machine can stop without the executor: the host watchdog force-stops one whose host lease lapsed, a node reboots, or a guest powers itself off. A machine LXD shows stopped (`Stopped`, 102) after its settled start counts as stopped: the next turn starts it again on the same disk, a sleep goes on without a stop of its own, and a removal deletes it. Only LXD's own state counts, never the guest's word; a machine LXD shows in any other state still waits for an operator. Each such stop is written next to the machine's journal, once per start: `outside-stop-<segment>-<sequence>.json` (schema `qorpera.coding-machine-outside-stop/v1`: the start's segment, sequence and operation id, the machine's running `count` of outside stops, and when it was seen). A machine stopped from outside a 4th time within an hour (its newest four records less than an hour apart) is `recovery-required` from then on, whatever is asked of it, so a stop-start loop waits for an operator instead of going round. Company machines and the kept per-session VMs keep their rules.

Once such a stop is written down, and before anything else is done to the machine (a start, a delete, or waiting for an operator), the executor records it in SQL with `qorpera_record_coding_machine_stopped` (migration `20260930431000`). That call ends every attachment on the machine with the commands last seen running there, stopped for `MACHINE_STOPPED` ("The machine stopped"). The session's thread shows it and its next turn's context tells the agent, so a command never just vanishes. SQL keeps each stop once (`qorpera_coding_machine_outside_stops`), named by the start it ended, the LXD operation in the machine's journal: the same stop recorded again, by a retry or by an abandoned try's request that reaches SQL only after the machine started again and a session attached anew, gets the first record's answer and ends nothing. Nothing else starts the machine (it never starts by itself), and the executor starts it only once the stop is recorded. A turn then unplugs the session folders while the machine is stopped, under its own run receipt, and plugs in only its own session after the start; a sleep unplugs them under its stop custody. If the record fails, the turn or step fails and nothing is started, and the next one records it. The keeper only observes running machines, so the stop is recorded by the next turn, sleep or removal. The receipt's own `machine_stopped` state comes in 5g-3. A turn of another session that was running when the machine stopped loses its commands the same way, and its thread shows `MACHINE_STOPPED`. Rollout: the runtime that knows the reason `MACHINE_STOPPED` goes out before or with this executor, since an older one refuses the turn context (`CODING_TURN_CONTEXT_INVALID`); the coordinator enables the host watchdog timer only after this is live.

**Machines restarted for the company folder (F3 5g-5, migration `20260930501000`).** A machine whose reads the folder can't prove released must restart before a coding view opens on it again (`deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md`, rule 4). SQL marks it when a crashed folder service's view closes (`service_crashed`), closes its other coding views, and refuses a coding view's open on it ("Coding machine must restart first"). The executor restarts it when the open is refused for that, when a view it holds was closed (`VIEW_CLOSED`), when a view's final boundary answered `unproven` before another view opens on the machine, and when a publication answers `READS_UNPROVEN`: it marks the machine itself (`qorpera_mark_coding_machine_folder_restart`), ends its folder views, stops it under stop custody (SQL grants a marked machine's stop while a turn uses it), tells the folder service `restarted`, and records the restart before the start (`qorpera_record_coding_machine_folder_restart`). The record ends every attachment on the machine, a leased turn's too, each with one `FOLDER_RESTART` event ("The machine restarted for the company folder", with the commands it stopped), and clears the mark. It is not an outside stop: nothing counts toward `recovery-required`. The turn then attaches its session again, once; a second refusal fails the turn. A failed mark or record fails the turn with `CODING_HOST_FOLDER_RESTART_UNCONFIRMED`, and the next turn tries again. Rollout: the runtime that knows the reason `FOLDER_RESTART` goes out before the migration and this executor, since an older one refuses the turn context.

**Machines given a new disk (F3 5g-5, migration `20260930505000`).** A machine that holds a read the folder core can no longer place (rule 4, `unreadable`) keeps that read on its disk across a restart, so it gets a new disk from its image under the same machine id: only `/company` is kept, and home and cache folders, Docker images and anything installed outside `/company` start fresh. The executor marks it (`qorpera_mark_coding_machine_new_disk`, which marks it to restart too) when the final boundary of the machine's last view said so, before a turn's view opens (`READS_UNREADABLE`); when the boundary before a publication says so, which fails the publication with `CODING_FOLDER_BOUNDARY_HELD:READS_UNREADABLE` or `:REFUSED_UNREADABLE` and publishes nothing; and once per command transport when a command's boundary says so (the machine keeps running until the session's next turn finds its view refused). The machine then restarts as above, but the restart's record answers `new-disk`: it detaches each session with a `MACHINE_NEW_DISK` event ("The machine got a new disk; only the company folder was kept") and keeps both marks. The executor rebuilds the stopped instance from its binding's image (`imageFingerprint`) under `rebuild` custody, which SQL grants only to a machine so marked; the instance keeps its name, configuration and devices. Right before the start after the rebuild, `qorpera_record_coding_machine_new_disk`, named by the rebuild's LXD operation, empties the machine's read set and clears both marks, so views open on it again. A failed mark or record fails the turn (`CODING_HOST_FOLDER_RESTART_UNCONFIRMED`, `CODING_HOST_NEW_DISK_UNCONFIRMED`), and the next turn tries again: a rebuild already done is recorded before the start, never done twice. Old images get cleaned up, so before the rebuild the executor checks that the image is still in the node's LXD image store: while it is not, nothing goes out, the machine stays stopped and marked, its error is `CODING_MACHINE_IMAGE_GONE` (step `wake`), and each turn on it fails so until the image is back or the machine is removed; the new disk's record clears the error. Rollout: the runtime that knows `MACHINE_NEW_DISK`, then the migration, then this executor; the migration rolls only together with this executor.

The Order 5 completion path wakes the managing agent with the outcome; there is no separate listener. The thread shows the session from the kernel's own view and events. Neither the agent nor a member client needs to be online while the session runs.

Unknown create, command, push, PR or dispatch outcomes retain intent and require observation/reconciliation. Process restart is not permission to replay an effect. Expired or revoked request authority does not grant resume; cleanup has a separate stop-only authorization. A failed or uncertain run must remain visibly unsuccessful.

## Host leases and the host watchdog

A member's machine runs only while its executor holds it. For every member machine SQL reserves on this node, the executor keeps a host lease: `/run/qorpera-coding-host/qorpera-coding-machine-<machine>.json` (`qorpera.coding-host-lease/v1`: the machine, its VM name and LXD project, the node's boot id, and when it was renewed and when it runs out, both as milliseconds of that boot's uptime from `/proc/uptime`), good for 90 s. A wall-clock change cannot stretch a lease, and a lease from an earlier boot never counts. The executor writes the lease once SQL has reserved the machine and before it starts or wakes it (`prepareWorkspace`); every keeper pass renews the lease of every member machine SQL still lists as reserved here, with sessions attached or not, so two renewals are at most 75 s apart even when SQL's listing (30 s) and each machine's step (15 s) take their longest. A sleep drops the lease once the machine is stopped; a removal drops it once the machine is deleted or gone. Each pass also removes the files of leases that are no longer live. A lease is a private file (0600) written to a temporary name, synced and renamed in place. Its folder is the executor's systemd `RuntimeDirectory` (0700, kept across executor restarts with `RuntimeDirectoryPreserve=yes`, emptied at boot). A lease that cannot be written fails the turn's preparation before the machine starts, or is reported as the machine's `keep` failure.

`qorpera-coding-host-watchdog.service` (`host-watchdog.ts`, started by its timer 30 s after boot and then 5 s after each pass) runs as the executor's account and needs neither the executor nor SQL, the NAS or the network: only LXD and the leases. Each pass lists every LXD instance; in the executor's project (`vmPolicy.project`, read from the executor's own configuration) it takes every VM named `qorpera-coding-machine-<32 hex>` that is not stopped, starting VMs included, and only then reads their leases, and the clock after the leases (so a renewal published meanwhile is never taken for one from the future). A lease a renewal replaced while it was being read is read again from its name. A VM whose lease is missing, unreadable (wrong owner or mode, a link, malformed, longer than 90 s, from the future), from another boot, lapsed, or naming another machine or project is force-stopped; the stops run side by side. Kept per-session VMs, company machines, stopped VMs and every other project are left alone. Each stop is logged as one JSON line (`coding-host-watchdog`, or `coding-host-watchdog-error` with its code when LXD refuses); a quiet node logs nothing. A pass that cannot confirm the inventory, the boot id or the uptime stops nothing and exits 1. There is no grace for a VM with no lease: the lease is written before the start, so a VM running without one is never one the executor is starting.

So a machine stops within about 95 s (90 s plus one pass) once its executor stops renewing it: the executor stopped or crashed for longer than the lease, SQL unreachable for that long (the keeper renews only what SQL lists), or SQL no longer reserving the machine. A restart inside the 90 s stops nothing: the leases outlive the process. Two races are harmless and expected. A keeper pass that read SQL's list before a sleep can write the lease again after the sleep dropped it; the machine is stopped and the lease lapses. A machine slept between the watchdog's listing and its lease read is stopped again or is already stopped, and its stop fails or does nothing; the next pass no longer lists it.

**Rollout.** The service and timer ship disabled. Until the executor treats a machine stopped from outside as stopped (the rule after this change, 5g-1b), a machine the watchdog stopped would become `recovery-required`, so the timer is enabled only after that change merges, and only on a node whose `/run/qorpera-coding-host` shows the executor writing leases: `systemctl enable --now qorpera-coding-host-watchdog.timer`.

## Package and configure

Build the two reviewable artifacts on an allocated Linux runtime node from a checkout whose `npm run check` passes:

```sh
node scripts/package-coding-guest.mjs --out /task-owned/new-guest-package
node scripts/package-coding-executor.mjs --out /task-owned/new-executor-package
```

The scripts package files and checksums; they do not install or activate services. The executor package holds two bundles, the executor and the host watchdog, each listed with its checksum and size in its manifest (`qorpera.coding-executor-package/v2`), and pins the generated runtime bundle. The guest package includes storage initialization, command, Git and watchdog entrypoints. Install those artifacts and the supplied watchdog service, timer and slice into a dedicated coding image, with the ownership, workspace and utility requirements in `command-guest-installation.json` and `COMMAND-GUEST.md` (sessions on a member's machine: paths, slices, users). Enable the timer in the image. Mask the five apt self-update units (`apt-daily{,-upgrade}.{timer,service}`, `unattended-upgrades.service`) in the image build; the guest and the executor refuse an image where any is not a link to `/dev/null` (`RUNNER_IMAGE_SELF_UPDATE_ENABLED`, see `COMMAND-GUEST.md`). Keep the image's non-root coding account (uid and gid below 200000, no privileged groups): the executor's configuration names it (`guest.uid`, `guest.gid`), though since 20260930394000 no session runs as it. Every session runs as its own uid/gid in 200000–524287 (`qorpera_coding_session_uids`), registered per boot as a `/run/userdb` record, so the image needs nss-systemd for passwd and group (the Ubuntu default). Each session's NAS-backed `/workspace/<worker>/repository`, `home` and `cache` are attached per turn. Configure Git's author identity as a service identity for every user (system gitconfig).

Before enabling work, independently verify image/bootstrap provenance, isolated LXD project/network policy, blocked metadata/control-plane/office-network access, storage and genuine reserved node capacity. Pin the resulting image fingerprint, bootstrap digest and provider policy. A pinned network name is not by itself evidence of network isolation. Disposable unsigned candidate tests are permitted by the runtime contract; production activation retains the provenance gates.

Install `qorpera-coding-executor.service` with its persistent dedicated account and private NAS control directory, and both bundles in `/opt/qorpera-coding-executor`. Install `qorpera-coding-host-watchdog.service` and `.timer` beside it, but leave the timer disabled until its rollout step ("Host leases and the host watchdog"). The service uses the local LXD socket, protected machine identity, a loopback HTTP backend, and a separately configured HTTPS reverse proxy. `owner` must be the executor's owner in `qorpera_coding_executors` (with `harnesses` naming `codex`). ## Fleet command routing

Install an independently configured executor on each eligible node, with its own owner, local provider policy and NAS placement. SQL selects an eligible node for a new member machine against shared node capacity and preserves the host of retained machines and existing NAS volumes. An existing volume never moves because its lease expired or another node has spare capacity. Configure each environment's executor records through the administrative RPCs before enabling that node.

The harness may keep its existing `QORPERA_CODING_COMMAND_URL`: `commandPort` is the authenticated ingress. After exact command authorization, `qorpera_route_coding_command` resolves the session's persisted machine and executor. A local machine executes locally. A remote machine is reached only through the matching `commandPeers` owner/provider entry. SQL never supplies an arbitrary network destination. Forwarding has no effect retries, follows no redirects and validates the bounded command receipt.

Each node exposes a second HTTPS origin whose proxy targets loopback `peerCommandPort`. This listener reauthorizes the binding, receipt and current placement, and refuses a machine assigned to any other executor; it never forwards. Install `/etc/qorpera/coding-peer-command.key` as 32 random bytes encoded in base64url for that node's peer listener. Its required systemd credential is `qorpera-coding-peer-command`. For every remote peer, install that peer's token in a private file and a reviewed drop-in, for example `LoadCredential=qorpera-coding-peer-node-01:/etc/qorpera/coding-peer-node-01.key`. Peer tokens must be unique per destination and distinct from the harness ingress token and broker tokens. Configuration contains credential names only. The peers' HTTPS certificates must be trusted by the executor (`NODE_EXTRA_CA_CERTS` in the deployment drop-in when using the private CA).

**The guest's lease proof (G2-6b).** On `commandPort`, every coding or machine command also carries the run's lease as `x-qorpera-identity: job.<job id>.<lease token>`, which only the run's own native host holds. The executor asks `qorpera_native_binding_proven` (migration `20260930152000`, as service_role) before the command's own authorization, and refuses a missing, malformed or unproven holder with the plain 403; it never logs the header. The peer listener takes no holder: only executors hold its token, and the forwarding executor proved the guest's at its own ingress. The public proxy in front of `commandPort` must pass the header through. See `deploy/first-node/RUNTIME-NATIVE-HOST-KEY.md` "G2-6".

Both command backends bind only loopback. Public ingress and peer proxies must target their respective ports; the peer origin must never point back at an ingress. The separate peer token and local-only execution prevent forwarding loops even if deployment routing is wrong. `commandPeers: []` is valid for a node with no remote destinations; unknown destinations fail closed.

**Members' looks at agents' desktops (20260930712000).** The optional key `"memberScreens": {"port": 8791, "publishableKey": "sb_publishable_…"}` gives the executor a third listener on loopback `port` (distinct from the other two) for the web's computer window: `GET /v1/member-machine-screens/<companyId>/<machineId>[/watching]` with the member's own bearer token and `If-None-Match`. Only the node behind the member bridge (`supabase/functions/member-company-gateway`, upstream `QORPERA_MEMBER_GATEWAY_UPSTREAM_URL`) has it, and its mux sends exactly `^/v1/member-machine-screens/` to that port. The executor begins each look as the member: it calls `qorpera_member_machine_screen_begin` at `supabaseUrl` with the member's token and the publishable key (not a secret; no service key), so the database checks the token. It then reads the look as itself (`qorpera_member_machine_screen_authority`), looks locally when the machine is its own, or sends the look's single-use id once to the machine's executor through the peer listener (`/v1/machine-commands/member-screen`), which reads it again and never forwards. The token is never logged; a failed look is logged as `member-machine-screen-error` with a fixed code. A watched desktop's own work (the X server answering a look a second: about 3 % of a core) counts in the machine's idle measure, so a watched desktop that moves may keep its machine awake while watched; the web stops looking when the window is put away or the tab hidden, and pauses after 30 minutes without a touch.

**A member takes over an agent's desktop (20260930713000).** The same listener takes `POST /v1/member-machine-screens/<companyId>/<machineId>/act` with the member's bearer token and `{"action": {...}, "epoch": n, "seat": s}` (JSON, at most 16 KiB): one of machine_screen's actions (click, double, move, drag, type, key, scroll; never `open`) of a member who holds the desktop, and the hand-back epoch and the seat of the hold the member's page captured it under (each a safe whole number, 0 or more; anything else, or no epoch or seat, is a bad request, never guessed). The node's mux location for `^/v1/member-machine-screens/` must now pass `POST` as well as `GET`. Holding is a SQL lease the web takes, keeps and gives back itself (`qorpera_member_take_machine_desktop`, `_keep_`, `_hand_back_`): 5 minutes from the member's last word, never past 30 minutes from their last input; it ends by time alone. Each take-over, heartbeat and hand-back names the member's hand-back epoch for the machine, a counter only the database moves: a take-over is accepted only at the current epoch, a hand-back at it moves it on and gives back the lease taken under it (an older one changes nothing), so a take-over that arrives after a hand-back of its epoch is refused (`TAKE_CALLED_OFF`). Two holds of one member can live under one epoch (a lease that ran out and was taken again, another tab's take-over of the member's own live lease), so every seating gets a seat (the lease generation, which only grows): the take-over answers it, a heartbeat renews only the lease taken under its epoch in its seat, and a hand-back has two forms: EXACT names a seat and ends only that lease, moving the epoch on only when no live hold of the member's is left, which a page sends when every take-over it sent at that epoch was answered (so a stale tab's close never ends another tab's hold); VOID moves the epoch on at the current one and ends the member's lease under it, whichever seat, which a page sends while a take-over of its own may still be on its way (it voids that take-over, and ends another tab's hold under that epoch too: the one race where a closing tab ends another's). A page never has two take-overs alive: before a new one while an earlier one has no answer, it sends VOID and waits for its answer. A page holds a seat only from the answer to its own take-over, or from a list that shows the hold seated by that very take-over. The agent's take-over card waits for the web's I'm done: it answers once, after a list read that counts (none of its machines below the epoch the page knows), the page owes nothing for the agent's machines; what it owes about an epoch (a take-over it sent at it, a hold it took up or was shown there) is discharged by learning from the database that the member's epoch is above it, or seat by seat at that epoch: a take-over with no answer by its own answer (or a list showing the hold it seated); a seat the page's own take-over got, or one shown it, by an EXACT hand-back's answer for that seat or a higher one, or by a heartbeat or an action answered `ended` for it. No refusal of another request, timeout or closed window discharges anything. A take-over the member starts from another tab after that read was taken is a new take-over, outside this answer; the agent then hears `DESKTOP_MEMBER_IN_CONTROL`, as for any take-over without a card. No page can exclude what the member does a moment later. A page uses a hold only after a Take over pressed on that page: one from another window, or from before a reload, is shown and never taken up, so after a reload the member presses Take over once to go on (without that the old lease ends by itself). The executor begins each action as the member (`qorpera_member_machine_desktop_act_begin`, with the member's token, the publishable key, that epoch and that seat): SQL checks under the machine's lock that the member holds the desktop under a lease taken at exactly that epoch, in exactly that seat (else `DESKTOP_CONTROL_ENDED`, nothing recorded, counted or renewed: input delayed across a hand-back and a new take-over, a lease that ran out and was taken again, or another tab's take-over never runs under the new hold) and records the action with a typed text's length, never the text, and its seat. It then reads the action as itself (`qorpera_member_machine_desktop_act_authority`, which must hold exactly that record and the lease still in its seat), runs it when the machine is its own, or sends the action, text and all, once to the machine's executor through the peer listener (`/v1/machine-commands/member-act`), which reads it again and never forwards. A click, drag, scroll or key goes through the image's screen helper as an agent's action (the action id its receipt; no look: the member's window looks again itself); a typed text goes through a fixed script with the text on its stdin (`COMPANY_MACHINE_MEMBER_TYPE`), because the helper's `desktop type TEXT` unit puts its command line in the machine's journal; the script runs as a transient unit of its own with a fixed description and `RuntimeMaxSec=10`, so systemd ends it and all it started at its limit, also when the executor cut it off; after a text the desktop pasted (beyond plain ASCII) both selections are cleared. Members and agents share the one-actor rule (`DESKTOP_BUSY`, and the 11 s grace after an action that did not end cleanly). While a member holds the desktop, SQL refuses the agent's looks and actions, new commands and `save_coding_value` on that machine (`DESKTOP_MEMBER_IN_CONTROL`), and every picture is fenced: after the capture and before anything of it leaves, the executor asks `qorpera_machine_desktop_picture_check` whether the lease generation the look's read saw still stands and no one but the looker holds the desktop, so a look authorized before a take-over never shows what the member did after it. `save_coding_value` is fenced the same way (v233 release review r1, F29 of #1661): its read answers the lease generation it saw, the clipboard helper takes the desktop as an action does (a member's action meanwhile is `DESKTOP_BUSY`; a read that meets a member's action is refused at once, one that meets an agent's waits up to 6 s for it), and the same check runs before the helper reads the clipboard and again before the box is answered: a take-over since the read drops the box whole, nothing kept or logged, and the agent hears `DESKTOP_MEMBER_IN_CONTROL`. A helper that had begun before the take-over may already have cleared the clipboard; that cannot be undone. After a member has held a desktop, the platform clears its clipboard before an agent can read a key from it (F32 to F35 of #1661), since what a member copied stays on the clipboard after they hand back. The clear is owed from the hold on (SQL's `desktop_clipboard_generation` differs from the lease generation), and only the platform's confirmed clear lifts it: the host of the machine's node takes the desktop as an action does, asks the fence, runs its own fixed clear (`COMPANY_MACHINE_CLIPBOARD_CLEAR`: both selections cleared, each xsel checked, each read back by its byte count alone; never the helper's `--clear-only`, which answers cleared whatever xsel did) and records it with `qorpera_machine_desktop_clipboard_cleared`, which SQL keeps only while that generation stands and no member holds the desktop. It is done first at the agent's first screen call after the hold (a look or an action): SQL says the clear is owed (`clipboardClear`), and the host clears and records under that call's hold, within 3 s, before it looks or acts; if the fence or the record says a member holds the desktop again, an action does not run (`DESKTOP_MEMBER_IN_CONTROL`), and any other failure fails nothing (it stays owed). The backstop is `save_coding_value`: while the clear is owed SQL answers its read `clear` (with the lease generation), nothing is read, the clear is done the same way, and the agent hears `CLIPBOARD_EMPTY` (true then: copy the key on the site and call again); its next call reads as before. A desktop that is not running counts as cleared (the image keeps no clipboard past the desktop's session). A member's action asks the fence for its seat again once the host holds the desktop. A stated limit: the computer is the agent's; while a member holds the desktop the agent starts nothing new and reads nothing through the platform's tools, but a program the agent started there before the take-over keeps running and can see the screen and the clipboard. The text is never logged, stored or put in an error or an answer; a failed action is logged as `member-machine-screen-error` with a fixed code. While the picture changes or the member holds the desktop, the window looks every 450 ms (SQL's floor is 400 ms) instead of every second: at about 3.7 % of a core per look a second on the X server (measured 10 Nov 2026), that is about 8 % of a core, and about two member bridge calls a second, for as long as it lasts; three unchanged looks bring it back to one a second, then 2 s and 3 s.

**Shared input carries the lease generation it was made under (20260930738000).** The window's list names the desktop's lease generation (`generation`, which moves at every seating of a member and every hand-back that ends a lease) to owners, admins and contributors, and a shared action names the one its input was made under: `{"action": {...}, "generation": g}` (a safe whole number, 0 or more; beside an epoch or a seat it is a bad request). The executor's read of a shared action is unchanged: it still serves it only while the generation it was begun at stands.

**A member's pointer is the desktop's pointer (20260930744000).** The member listener takes `POST /v1/member-machine-screens/<companyId>/<machineId>/pointer` (JSON, at most 256 bytes; the member bridge reads it without asking the auth service, since the executor checks the token itself). `{"begin": {"generation": g}}` or `{"begin": {"epoch": e, "seat": s}}` begins a pointer pass as the member (`qorpera_member_machine_desktop_pointer_begin`: a shared pass at the lease generation the window knows, or one on the member's own private hold; the shared and private actions' own checks, no action recorded, no lease renewed, one row per member and machine), which the executor reads once as itself (`qorpera_member_machine_desktop_pointer_authority`, in `CODING_CONTROL_METHODS`; a pass SQL no longer holds is `POINTER_PASS_ENDED`) and keeps in its memory for its 10 seconds: the pass id, the sha-256 of the member's token, the machine and where it runs. `{"pass": p, "x": n, "y": n}` moves on it: the executor checks only that pass (the token's hash, the company and machine, its time, at most 30 moves a second; past it a move is dropped), and moves the pointer on its node or sends the move to the machine's node (`/v1/machine-commands/member-pointer`, which reads the pass once itself). The host keeps one held-open exec per desktop while a member's pointer moves (`COMPANY_MACHINE_MEMBER_POINTER`: python3 and XTest, in the live image), gives it the newest position only, drops moves while an action holds the desktop (the one-actor rule and its grace: a move is never an action, holds nothing and delays nothing), refuses a pass's moves once it saw a newer lease generation (any look, action or pass it serves tells it; the private holder's window looks before it can type), and closes the exec 20 s after the last move. A move waiting on its way never moves the pointer after an action or a newer generation: it carries the host's pointer fence, which only the host writes (root's `/run/qorpera-pointer`, kept across desktop restarts) and the desktop must have confirmed before each action runs, before any look is taken and before a mover starts (`COMPANY_MACHINE_POINTER_FENCE`; a write that failed or is on its way runs nothing and shows nothing); each mover is bound to the desktop's incarnation (its unit's invocation id) and ends, having moved nothing, as soon as the desktop is another one, and the mover moves only for the desktop's current fence (review r1 of #1733). An answered move was taken in that order: the window sends an action only after the move on its way was answered. **A member's live picture of an agent's desktop (20260930745000).** The optional key `"memberStreams": {"port": 8793}` (with `memberScreens`) gives the executor a fourth listener on loopback `port`, for node 1's own Cloudflare tunnel alone (`deploy/screens-door/`: `screens.qorpera.com` to `http://127.0.0.1:8793`; no other node and no mux has it). **Each watched desktop in a process of its own (20260930745000; the lead's decision after review r11 of #1746).** The optional key `"desktopStreams": {"socket": "/run/qorpera-desktop-stream.sock"}` turns members' live pictures of this node's desktops on; without it they are refused (`STREAM_UNAVAILABLE`, the window keeps its pictures). The executor parses a frame's 9-byte header in constant time, never scans a picture's bytes (it hands them on as the pieces they came in), and holds an instance back by not reading (32 frames and 4 MiB a turn; a member's release no sooner than 25 ms after its last). Every frame it reads belongs to a step it asked for or allowed, or ends the instance: a pong only to its ping; one ok lets one cycle through (at most 160 messages and 72 MiB); a member it let go of may still send one frame and then its DONE, nothing after (and at most 16 such members); no pong for 15 s of its reading (its own lateness is not counted); more than 1 MiB written that the instance has not read. Closing the connection ends a live instance at once; a stuck one is killed by its own guard thread within 10 s. The executor starts at most one instance every 500 ms and one desktop's at most every 2 s (a tenth of the socket's trigger limit; past that limit systemd fails the socket and it stays failed until `systemctl reset-failed`). At most 8 desktops a node and 8 members a desktop; past either `STREAM_BUSY`, and the window keeps its pictures and asks again 30 s later. **The program file.** The stream unit must run the SAME file the executor's loaded `ExecStart` names. On the fleet the executor runs `/opt/qorpera-coding-executor/<sha>/qorpera-coding-executor.mjs`, set by its drop-in (`qorpera-coding-executor.service.d/90-fleet-v6.conf`), so the install writes a drop-in for the stream unit from what systemd says, never typed:

**The smoke after the install** (`desktop-stream-smoke.mjs`, plain node, no dependency), with no desktop and no member, as the executor's account, against the file the executor's loaded `ExecStart` names (`$file` above): `systemd-run --wait --pipe -p User=qorpera-coding-executor -p Group=qorpera-coding-executor /usr/bin/node <the smoke> /run/qorpera-desktop-stream.sock "$file"`. It says HELLO twice: one of another version must be refused (ENDED "another program version", closed), one of that file's version for a machine that does not exist must be taken (READY) and ended when its relay fails (ENDED, closed). It prints one line a step and `STREAM UNITS SMOKE OK` (exit 0), or one cause line (exit 1: the socket not reachable, a HELLO not refused, the units running another file than `$file`), within 20 s; each instance ends with its connection.

Measured in a machine of the live image (4 cpus): full-screen noise held an instance to 141 MB at 1600x1000 and 296 MB at 3840x2160 with 8 members; an instance holding memory was killed at its 512M and eight at 420 MB each by the slice's 3G, while a stand-in for the executor with its 2G and two cores stayed flat and its loop's longest hold stayed under 7 ms.

**A member turns an agent's desktop on (20260930714000).** The same listener takes `POST /v1/member-machine-screens/<companyId>/<machineId>/start` with the member's bearer token and the body `{}` (JSON, at most 1 KiB; any key is a bad request, `member_start_invalid`: what to open there is for a later stage). The executor begins the start as the member (`qorpera_member_machine_desktop_start_begin`, with the member's token and the publishable key): SQL checks the member may wake machines, the machine runs and is big enough, the disk rule, and a 5 s floor per machine, marks what an agent's first screen use marks and answers a start id. A member's hold of the desktop, the caller's or another's, does not stop a start (a hold does not prove the desktop runs; a start takes no hold and does nothing to a desktop that runs). The executor then reads the start as itself (`qorpera_member_machine_desktop_start_authority`, single use within 15 s), runs it when the machine is its own, or sends it once to the machine's executor through the peer listener (`/v1/machine-commands/member-start`), which reads it again and never forwards. The host runs one fixed script (`COMPANY_MACHINE_MEMBER_START`: the boot id check, then the image's own `desktop start` with no arguments, which takes the desktop's lock, checks the size and waits until the screen is drawn) in a transient unit (`systemd-run --wait`, `RuntimeMaxSec=20`, `KillMode=control-group`, a fixed description, no `--pipe`): `desktop start` starts `qorpera-machine-desktop.service`, a unit of its own, so the transient unit's end or its limit never stops a desktop that started. It takes no hold (`DESKTOP_BUSY` never applies: the desktop's own lock orders it with an agent's `desktop` command). Its exits map to fixed outcomes: 0 started, 92 running already, 3 `DESKTOP_MACHINE_TOO_SMALL`, 97 `MACHINE_BOOT_CHANGED`, 98 `MACHINE_IMAGE_WITHOUT_SCREEN`, anything else (or no answer within 22 s) `DESKTOP_DID_NOT_START`; a failure is logged as `member-machine-screen-error` with a fixed code. The node 1 mux location `^/v1/member-machine-screens/` passes `POST` (from v233 on).

All privileged credentials use systemd `LoadCredential`: registry service key (`qorpera-coding-registry`), the distinct coding-command transport token (`qorpera-coding-command`) and the executor's own broker token (`qorpera-coding-broker-executor`, the name `broker.executorTokenCredential` gives). Never put a credential into configuration JSON, a model prompt or the repository VM. `repositories` is the executor's own allowlist; it does not substitute for current SQL repository authority.

## Repository access (bundle v88)

Members never hand-place repository tokens. A repository is reached through the GitHub connection of the session's company (Settings → Connections → Services, sealed in that company's secret broker, shared with every agent). For each step that touches the repository (resolving and seeding the base while the session is `preparing`, pushing the bundle and opening the draft PR while it is `publishing`) the executor posts `{workerId, leaseToken, executorOwner, repository}` to `POST <broker.origin>/v1/repository-credentials?company=<profileId>` with its own broker token. The public origin routes by `company=` to that company's broker, which asks the kernel (`qorpera_authorize_coding_repository_credential`). The kernel answers only when the session is leased to this executor owner with this lease token, the lease is live, the repository is the session's, the session's agent holds an enabled repository grant, and the company has an active GitHub connection sealed by that broker (the Services connection: company-owned, named `primary`; a secret card or any other company secret filed under github never serves) on which the agent holds a live grant; it audits every answer (`repository_credential_used`). The broker opens the envelope and returns `{schema, token}` with `Cache-Control: no-store`. The executor lends the token to the Git broker or GitHub API step and drops it; it is never cached, logged, stored or passed to the repository VM, and a refusal is never retried with another credential. Disconnecting the company's GitHub connection, revoking the agent's grants on it, withdrawing the repository grant or losing the lease stops the next step.

The executor's broker token is not the runtime token guests hold (`qorpera-cloud-secret-runtime`, which does not open this route). The coding session's lease token binds a request to a live session but does not authenticate the caller, so it is no credential of its own (guests held the Supabase service-role key until G2-5, and with it could claim a session and learn its lease token). The executor's token is 32 random bytes (base64url) that only the executor (`qorpera-coding-broker-executor`) and the brokers of companies running coding sessions (`qorpera-cloud-secret-coding-executor`, a drop-in) hold; it opens nothing but this route, the environment route and the relay routes below. With the same token and lease check, `POST <broker.origin>/v1/coding-environment?company=<profileId>` (`{schema: "qorpera.coding-environment-request/v1", workerId, leaseToken, executorOwner}`, 5j-3) returns the session's environment variables as `{schema, environment, mask}` with `Cache-Control: no-store`. Since 5j-4 the executor calls it once for each command a folder-model session starts, puts the values into that command's environment and masks them in its saved output; `mask` holds the older values the session's member used on its machine (migration `20260930514000`), which the executor masks in every session on the machine and never puts in an environment. It keeps them all in memory only, until the machine's last session is released. A command it did not start in this process, or whose start the guest did not confirm, has none of its output saved. Since 5j-6b the same token and lease check open the broker's relay, which sends a running session's request on with a sign-in that never leaves the broker: `<broker.origin>/v1/coding-mcp?company=<profileId>` (GET, POST, DELETE) to the MCP server named in `x-qorpera-mcp-url`, and `/v1/coding-repository-fetch/refs` (GET) and `/upload-pack` (POST) to the session's own GitHub repository (upload-pack only). The session is named in the `x-qorpera-coding-worker`, `x-qorpera-coding-lease` and `x-qorpera-coding-executor` headers; 5j-6c builds the relay unit that calls them. The unit loads it unconditionally, so install the file before starting the executor. See the Step 7 connectors runbook for the broker side and the accepted risks (the OAuth token is account-wide; network Git egress is open). The origin must present a certificate Node trusts (a public CA, or `NODE_EXTRA_CA_CERTS` in a reviewed drop-in) and be reachable from the executor's node.

**Bringing code in (own code storage, step 6).** An import (a code request of kind `import`) is fetched by the executor itself, as bytes only: git's protocol v2 over smart HTTP, one GET of `info/refs` and two POSTs (`ls-refs`, then one `fetch` of every head and tag), the pack of side band 1 written behind a bundle header into the node's bundle store in 1 MiB pieces, each awaited (`packages/runner-orchestrator/src/code-import-fetch.ts`; the transports are `repository-fetch.ts`). No git runs on the node for it, and nothing is fetched but that one repository's upload-pack. With the company's GitHub connection the executor calls the same relay routes, `GET <broker.origin>/v1/coding-repository-fetch/refs?company=<profileId>` and `POST …/upload-pack?company=<profileId>`, with its own broker token and the import named as a session's turn is named (`x-qorpera-coding-worker` the request's id, `x-qorpera-coding-lease` its lease token, `x-qorpera-coding-executor` this owner, `x-qorpera-coding-repository` the GitHub `Owner/Name`), `Git-Protocol: version=2`, and redirects refused. For a request id that names no session the kernel's fetch authority checks the import instead (`qorpera_authorize_code_import_fetch`: the request leased to this executor and still at its fetch, its asker's grant on the connection, the connection sealed by that broker); the broker adds GitHub's header and streams GitHub's answer back. **The token stays in the broker**: the executor never holds it, so nothing of an import can log, store or pass it on. A public project, or an asker who may not use the connection, is fetched straight from `https://github.com/<Owner>/<Name>.git` with no credential, under the relay's own rules: github.com resolved once and refused unless every address is public, TLS verified for github.com, no redirect followed (a renamed project ends refused, `IMPORT_SOURCE_MOVED`), 10 s to connect, 30 s to the headers and 2 minutes idle. A whole fetch has 60 minutes. GitHub's own 401, 403 and 404 end an import refused; the relay's own 503, a source's 429 or 5xx and a cut transfer (a reset, an idle connection, a proxy that cut a reader that paused) put it off to its next claim (`busy`); the relay's own 404 fails it (no broker takes the company: an operator's matter); the relay's own 403, which the broker gives alike for a database blip, a refusal and a renamed project, puts it off twice and ends it refused the third time in a row. The proxy in front of the brokers must let a reader that pauses up to 2 minutes keep its connection (`send_timeout 150s` on the two fetch locations, `deploy/first-node/RUNTIME-STEP-7-CLOUD-CONNECTORS.md`).

**An import does not consult `repositories`, and never adds to it.** That allowlist bounds which repositories this node is lent a token for, to seed a session's checkout and to push its branch. An import is lent no token: it only reads (upload-pack), its repository is named by the company's own agent or an owner or admin when they ask, and the kernel checks that ask and the connection's grant at every relay call, as it checks a session's. An entry per company repository would put an operator back into every import, for no bound the kernel does not already hold.

The OAuth connection carries the scopes the GitHub OAuth app grants (`repo`); what a session can push is bounded by that account's access and by the fixed session branch. A repository entry may still name a static `"credential": "qorpera-coding-repository-NAME"` (with its own `LoadCredential` in a reviewed drop-in). That is proof-only plumbing: it bypasses the company connection, so disconnecting the company's GitHub does not stop it. A configuration whose repositories all name static credentials may omit `broker`.

The identity guest receives the gateway from its host: on the **LXD provider** (and the shared execution service) set `QORPERA_CODING_COMMAND_URL` to the executor's HTTPS origin and `QORPERA_LXD_CODING_COMMAND_TOKEN_FILE` to a private file holding the same distinct transport token; the provider writes `QORPERA_CODING_COMMAND_URL` into the guest's native provider environment and the token into the `qorpera-coding-command` systemd credential (empty when no gateway is configured), and the guest bootstrap verifies both against its immutable bootstrap authority. The gateway certificate must chain to the cloud secret broker CA the guest already trusts (`NODE_EXTRA_CA_CERTS`). The native provider service selects the coding composition only when that URL is present. The fenced Codex binary, existing native isolation and identity recovery configuration remain required. Rebuild/provision the native image through its existing reviewed deployment process; do not attach an existing identity volume to a repository VM.

Configure SQL executor ownership (`qorpera_configure_coding_executor` with `harnesses`), repository grants (`qorpera_set_coding_repository_grant`), the exact VM policy (`qorpera_configure_coding_vm_policy`), the dedicated NAS source/machine placement (`qorpera_configure_coding_nas_policy`) and, if not the defaults, the machine sleep and removal delays (`qorpera_configure_coding_machine_lifecycle`) through the migration-defined administrative RPCs. A new VM policy supersedes every machine planned from the old one: each is removed when it is next idle and the member's next turn gets a machine from the new policy. Apply bundle activation only with the matching installed artifacts.

## NAS, retained credentials and deployment limits

Provision a dedicated hard NFSv4.1/4.2 TCP export with `nosuid,nodev`, pinned source address, byte/inode quotas and private executor-owned `rootPath`0700. The existing company object store and office exports are not coding allocations. Install a service drop-in with `RequiresMountsFor` and `ReadWritePaths` for the measured NAS mount point (the policy's `mountPoint`), not `rootPath` or another folder below it: systemd binds a `ReadWritePaths` entry onto itself, and the bind of a folder below the mount point is a mount whose root is that folder, which the executor's storage check refuses (`OFFICE_HOST_MOUNT_MISMATCH`). The underlying unmounted directory must be root-owned and contain no writable fallback workspace. The control journal is `rootPath/control`; per-worker data and guest custody use deterministic company/environment/worker subdirectories. Local VM root is only the reproducible OS/toolchain. Never silently copy work to local disk.

The two exposed roots are executor-owned0755 with immutable0444 binding markers. No session uid may equal that owner. The export must let root in the guest create and chown each session's directories to its uid (200000–524287) as well as to the image's coding uid: with root squashing, the operator grants those uids on the NAS before the cut (design proof 3). The trusted guest initializer creates exact coding-owned repository/home/cache directories and root-owned custody children (`logs`, `inbox`, `commands`, `git`) only through verified virtiofs descriptors. A volume initialized before bundle v93 has a coding-owned `logs` directory; the initializer refuses it (`CODING_GUEST_STORAGE_DIRECTORY_UNPROTECTED`) instead of repairing ownership, so such a worker needs a new volume or an operator `chown root:root` of that directory. Before that chown, check that `logs/` contains only root-owned per-command directories (UUID names, mode 0755, no symlinks or other entries); anything else means the volume was written by something other than the supervisor, and it should be replaced instead. The export must support those ownership operations, or an operator must preprovision the exact directories; the helper does not weaken ownership when root squashing prevents initialization. A 9p fallback is refused. Each session's temporary watchdog lease, configuration and user record live under `/run/qorpera-coding/<worker>` and `/run/userdb`, so a hard-NFS stall cannot prevent local expiry, and a machine that slept wakes with no session attached.

NAS placement and writer generation1 are pinned in SQL and on disk. This implementation has no automatic cross-node takeover, marker overwrite or cold-replacement protocol. Queue expiry does not fence storage. Restoring snapshots or introducing a successor writer requires a separate physical-fencing and recovery procedure. Backup, retention and volume-quota proof remain rollout gates.

Native provider credential generations retain encrypted refreshed Codex state after the official client settles. See [credential ownership](../first-node/native-codex/credential-ownership.md) for rollout and recovery. All relevant identity hosts must use the managed generation path; an older host must never consume a stale enrollment capsule. One managed process owns each login at a time. This is not proof of simultaneous same-login runs or of Claude/Gemini adapters.

The independent SQL emergency-stop custody of #140/#200 is not part of this executor yet: a stop that cannot be confirmed through the NAS journal returns `recovery-required` and an operator settles the machine. It returns in its own change on the session kernel.

The Git broker requires `/usr/bin/bwrap` (no unsafe fallback), user namespaces, seccomp and the reviewed host egress policy. Untrusted local Git parsing has no network or credentials. HTTPS stages still need enforcement against internal TCP destinations, and Git scratch needs an aggregate NAS quota. Normal upstream base advancement is accepted without changing the pinned worker ancestry. The current complete-bundle transport remains bounded at64MiB; large-repository streaming is a separate open gate.

A full Linux LXD VM per member is the implemented compute backend. Desktop/browser tooling and true Firecracker microVMs are not advertised by this image. User-level dependency installation can use NAS-backed home/cache/workspace; privileged OS installation requires a reviewed image update. Windows/macOS and additional subscription clients require their own accepted adapters.
