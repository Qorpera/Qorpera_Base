# Managed credential generations

The company-path provider service enables managed generations by default; `QORPERA_NATIVE_CREDENTIAL_MODE=managed-generations-v1` explicitly selects the durable managed-auth owner in the native provider service. It requires `QORPERA_NATIVE_RUNTIME=company-path-v1`, migration `20260922083000_native_credential_generations.sql`, the existing current Compute Identity recovery epoch/key, and the private capsule storage service credential. It does not change the code VM: that VM receives no provider credentials.

The owner records an irreversible refresh intent before restoring rotating credentials to the existing isolated official Codex client. Only after that client and its descendants settle does the host encrypt the current `codex/auth.json` into a new generation-addressed immutable object. SQL publishes the exact digest and generation before another owner is admitted. A provider/model failure still saves credential rotation. Cancellation may save an encrypted candidate, but cannot bypass the current SQL authority check to publish it.

Concurrent executions using separate capsules remain independent. The pinned managed client may refresh at any point during a run, so same-capsule contention returns HTTP 503 (`native_credential_busy`, `dispatched:false`); it is not concurrent-model support for one subscription. A lost claim response never launches a client. A later authorized identity home can finish publication of a complete immutable candidate. An intent without a candidate never expires into permission to repeat refresh: provider reconnection or separately verified recovery is required. Do not mix older capsule-overwriting hosts with generation-owning hosts for one capsule; activation requires all its eligible hosts upgraded and old processes stopped.

## Unsupported concurrent access-token adapter

The [current public app-server documentation](https://learn.chatgpt.com/docs/app-server#3c-log-in-with-externally-managed-chatgpt-tokens-chatgptauthtokens) describes experimental externally managed ChatGPT access tokens. However, both the retained 0.147.0 protocol and the [latest inspected stable 0.155.1 protocol](https://github.com/openai/codex/blob/rust-v0.155.1/codex-rs/app-server-protocol/src/protocol/v2/account.rs#L86) explicitly mark that login variant internal-only. The [0.155.1 release](https://github.com/openai/codex/releases/tag/rust-v0.155.1) was published September 18, 2026. An artifact upgrade alone has not resolved that support contradiction. This implementation does not activate that variant or recreate OAuth refresh endpoints.

Same-capsule concurrent models require either a provider-confirmed supported access-token adapter or an audited single managed app-server that multiplexes isolated sessions. The latter must route result fences, tool calls, cancellation, provider-session IDs and authority independently by thread/run and checkpoint rotated auth durably before ownership changes. The current one-run-per-process result-fence boundary must not be weakened to obtain concurrency. Tests using synthetic driver rotation prove the host/store/SQL protocol; they do not prove real provider refresh, deployed guest isolation, or live subscription acceptance.

## Physical-drain adoption gate

Before any capsule can use generations, a trusted operator must stop and verify the old provider processes/hosts, explicitly revoke their native lease records, and retain a reviewable physical-drain evidence artifact. Then call the service-only `qorpera_adopt_native_credential_generations(p_capsule_id, p_compute_identity_epoch, p_runtime_bundle_sha256, p_physical_drain_evidence_sha256)`. The digest identifies that actual evidence; it must never be invented from an elapsed lease or an operator intention. The RPC requires the current identity epoch, current active bundle with the credential-owner and process-settlement implementations, and no active lease record (even an expired active record is refused). Evidence is immutable. Reads/claims/publications fail closed until adoption matches the current epoch, active bundle, and run bundle. Re-adoption is necessary after changing that epoch or bundle. Fresh reconnect capsules also require adoption; login completion alone does not manufacture physical-drain proof.

SQL does not kill offline writers, inspect a host, or prove the attestation true. Existing offline processes must be physically stopped before this RPC; old service credentials/artifacts must not remain an eligible path afterward. This is an explicit operational acceptance gate, not automatic deployment or a substitute for fencing infrastructure.

On failed cloud publication the host retains its private run directory and latest auth instead of deleting them. `qorpera-credential-owner.json` is a service-owned 0600 locator in that 0700 directory, fsynced before credentials are restored; it binds compute identity, capsule, run, lease, owner, generation and candidate reference. The settled auth file/directory are fsynced before upload. Recovery may inspect this protected location, but must confirm physical process settlement and exact current SQL ownership before publishing. There is no automatic replay from local files. Retention is local to the provider guest and does not claim to survive destruction of that guest volume; successful immutable cloud upload is the remote durability boundary.
