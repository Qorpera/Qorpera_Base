# Node admission candidate

This is an unreleased part of Step 4. The shared SQL ledger, office/native/login dispatch checks, complete-host inventory publisher and protected standalone installer are integrated locally. The installer and actual systemd service pass offline acceptance. Production installation/enrollment and actual host/LXD acceptance remain required before enabling a live node.

The company machine ceiling remains a separate preceding check. `qorpera_reserve_runtime_node_machine` requires that exact unreleased company allocation, an operator-enrolled provider/host/policy and matching per-computer CPU/RAM costs. Office creation, first boot and explicit resume use this second gate immediately before their journaled LXD command. The returned window is at most five seconds and the caller deducts RPC time. Lost replies preserve the allocation; an explicit retry uses the same identity.

Native jobs use the same node ledger before volumes, VM creation and first boot. `lxdNativeNodePolicy` hashes the public physical configuration, exact binary-unit resource costs and protected local host digest; it excludes credentials. The native journal retains immutable node, policy, host and CPU/RAM placement. Existing journals without node placement block acquisitions until reconciliation checks the physical VM's actual resource configuration and registers its allocation. This covers known native journals, not a complete LXD host inventory. A changed host, policy, cost or node cannot silently move an existing allocation.

Native LXD submission uses the short admission signal; operation observation retains the caller's longer lifetime after acceptance. A pre-start capacity refusal keeps the stopped VM and allocation retryable. Lost submissions retain uncertain physical outcomes, and cleanup does not require healthy node admission. Neither a failed request nor an absent VM during uncertain creation frees capacity. The identity/recovery volumes survive confirmed VM deletion.

Login admission uses `20260908003800_runtime_login_machine_capacity.sql`. Each real login session has a distinct immutable physical allocation; it cannot be substituted for a run or office. Company admission rechecks current membership, Compute Identity ownership/status, provider policy, pause and expiry. Native jobs and login VMs cannot attach the same identity concurrently. An unsuccessful company reservation retains its request identity and reason. The node gate uses provider kind `login` and the public `lxdLoginNodePolicy` digest, with protected host identity and exact CPU/RAM costs.

The login gateway persists its binding before reservation, then reserves before identity storage, VM creation and first boot. Its private hash-linked operation sequence atomically claims create/start/stop/delete dispatch across provider instances. Accepted operation IDs can be observed after restart; a lost submission, missing operation or absent VM does not settle unknown creation/start. Closure competes with dispatch in that sequence and permanently prevents a delayed start. Runtime SQL closure also prevents a delayed first reservation from recreating an already cleaned allocation. No expiry timer alone frees capacity.

The headless login service scans retained journals independently of member requests. Completed, expired, cancelled, paused or revoked logins stop and delete the exact verified VM, retain the Compute Identity disk, and release company/node capacity together. Lost stop/delete polls and release replies resume from the same history. Cleanup uses retained public authority and current service credentials; it does not require node health or the original bootstrap secrets. Shutdown cancels member requests and retains unfinished physical history for the next process. Changed or missing journals, unexpected expanded resource/device configuration and legacy identity-keyed VMs remain unconfirmed; they are never automatically recreated, adopted or erased.

Node policies define total CPU/RAM, operating headroom and a standard computer size. Admission subtracts headroom and every unreleased node reservation, then admits a machine when its own CPU and RAM fit in what is left; it never needs a whole free standard slot. `qorpera_runtime_node_capacity` reports that remainder as `freeCpuMillis` and `freeMemoryBytes` (bundle v96), next to `admissibleSlots`, the number of whole standard computers that would still fit. Two companies cannot claim the same final share. A disabled node, missing/stale/unavailable observation, changed hardware or insufficient budget returns an explicit refusal. A refused demand remains pending. Reservation age, job completion, idle screens, shutdown requests and suspended VMs never free capacity. The existing provider-only exact physical-deletion acknowledgement releases the company and node reservations at the same timestamp.

Operator admission APIs in `20260908003700_runtime_node_capacity.sql`:

- `qorpera_configure_runtime_node`: versioned node policy; immutable host digest; occupied capacity cannot be discarded by lowering limits.
- `qorpera_enroll_runtime_node_provider`: immutable placement and resource costs for the exact provider ID and policy digest together. A provider can serve several office policies; a particular binding cannot move or change cost.
- `qorpera_observe_runtime_node`: a hardware-only measurement with immutable identity and original timestamp. It can report unavailability; a hardware-only ready record cannot authorize dispatch or report admissible slots after migration 039. Exact retry never refreshes measurement age or replaces a newer observation.
- `qorpera_reserve_runtime_node_machine`: native/office/login ledger admission, with current company allocation and immutable physical identity. This is not a substitute for the provider's current tenant, lifecycle or physical-authority checks.
- `qorpera_runtime_node_capacity`: a consistent per-node reservation view, pending count, distinct allocated computers/companies and whole available slots. Overflow is explicitly unavailable. Physical computer states and active human users are unknown in this reservation view.

Migration `20260909000100_runtime_computer_history.sql` adds the service-only `qorpera_runtime_computer_history(allocation_id, from, until)` query. Its explicit past window is at most 24 hours. It binds one allocation to its retained profile/run/office/login identity, local node/provider/policy, physical UUID/configuration and original requested/reserved/released times. It reports node-reservation hours and separate estimated running, suspended, starting and stopping hours, failed/unavailable time and unknown time. It never joins agent or member counts into computer-hours. Pending demand has no node-reservation hours; confirmed physical release ends the interval independently of shutdown intent.

The method is explicitly `physical_inventory_sample_hold`, not exact transition measurement: a valid sample contributes until the next sample or its original 60-second freshness limit, whichever comes first. Consecutive samples with matching state/reason/boot are combined while retaining their first/last observation IDs. Missing/stale evidence, failed node observations, hardware-only reports, absent instances and substituted physical bindings remain visible unknown intervals. The entire reserved window remains accounted for, including periods with no observations. Original receipts are retained; querying or replaying one never refreshes its timestamp. A query exceeding 20,000 samples or a 4 MiB response is refused completely and requires a smaller window. The indexed query reads a consistent statement snapshot and changes no authority or capacity.

These estimates are useful basic operational usage, but do not supply exact requested/ready/closing/closed physical lifecycle events or screen lifetimes. `screenUsage` remains explicitly null. Migration `20260909000500_runtime_computer_lifecycle.sql` adds an operator projection of retained admission/service/boot-intent/allocation records alongside these estimates. Database record times remain distinct from exact physical transitions, which are still unavailable. See `RUNTIME-COMPUTER-LIFECYCLE.md`. The inventory SQL driver verifies actual publisher-to-history identity, database-restart preservation and separate rolled-back historical arithmetic fixtures. Live physical state remains fixture evidence in that driver.

All tables are private, including to the service role; only explicit service-role RPCs expose these operations. Member and guest registries cannot configure policy, enroll providers or publish observations. SQL retains policy versions, observation receipts, demand and allocation history without automatic deletion. No message bodies, file contents, screenshots, credentials or raw machine IDs are stored. A separately approved retention mechanism must preserve identity deduplication if this history is ever pruned. The latest-observation table makes admission reads bounded without dropping immutable receipts.

Migration `20260909000600_runtime_node_computers.sql` adds a separate operator page of current allocations, immutable placement, pending requests/refusals, physical state and recorded job activity. Stale or uncertain evidence cannot classify a computer as idle or release capacity. This page leaves admission slot calculations in `qorpera_runtime_node_capacity`. Migration `20260909000700_runtime_node_health.sql` separately retains CPU, available RAM, root filesystem and network counter diagnostics; its collector and export cannot block inventory publication. Migration `20260909000800_runtime_compute_users.sql` separates current allocated computers, companies and associated members from windowed human activity observed through viewer redemption and admitted control input. Missing activity, continuous presence, NAS health and network reachability remain explicitly unknown. See `RUNTIME-NODE-COMPUTERS.md`, `RUNTIME-NODE-HEALTH.md` and `RUNTIME-COMPUTE-USERS.md` for sources, freshness, access and remaining scope.

Local tests use the real migrations and admission functions with synthetic hardware observations and explicit provider-deletion acknowledgements. `scripts/test-runtime-node-capacity.mjs` also races two different companies for one slot and restarts PostgreSQL. `scripts/test-runtime-office-start.mjs --vm-cycles` composes the real office workers and SQL gates; VM/root observations remain synthetic. `scripts/test-runtime-native-node.mjs` composes real queued-job provisioning, company/node gates and release with the actual native backend. It loses committed replies, refuses health between creation and boot, restarts PostgreSQL and retains the identity volume. These tests do not prove a physical host budget, LXD/NAS durability or live rollout.

`scripts/test-runtime-login-node.mjs` composes the actual login gateway, protected operation journal and all 195 migrations. Eight company/node gates recover lost admission and unavailable health before boot into one created VM and one start. With every member client absent, expiry and disabled node policy still permit cleanup; a lost accepted stop poll and committed release reply recover into one stop/deletion and a preserved identity disk. The SQL capacity driver separately proves concurrent same-identity login exclusion and closure racing a delayed first reservation, including restart. The provider sign-in and physical host/LXD effects are explicit fixtures; no subscription account or model is contacted.

Migration `20260908003900_runtime_node_inventory.sql` requires a matching inventory receipt for both dispatch and reported slots. `qorpera_enroll_runtime_node_inventory` records an immutable reviewed host/socket/daemon policy and explicit infrastructure VM/container identities and costs. Operating headroom plus every enrolled infrastructure reservation must fit the node's reserved headroom. Infrastructure remains charged even when absent or stopped. Unregistered instances, unsupported resource limits and incomplete observations never become zero-cost machines.

`qorpera_runtime_node_inventory_context` supplies the current node version, reviewed policy and every unreleased reserved allocation. The publisher binds a scan to its digest. `qorpera_observe_runtime_node_inventory` locks the node, rechecks that exact context and atomically records the hardware observation and inventory receipt. A changed ledger rejects publication. An earlier hardware-only receipt cannot acquire inventory authority later. A node-policy version change invalidates earlier inventory eligibility. The first confirmed observation permanently binds each allocation to its project, name, physical UUID and configuration digest; replacement or drift blocks admission. All three new tables are private, including to the service role. Only explicit service RPCs expose the necessary metadata.

The headless `RuntimeNodeInventoryObserver` reads the fixed protected machine identity, actual boot and mount namespace, root-owned canonical Unix socket and hardware totals before and after a complete LXD scan. The daemon must match its pinned certificate, name, version and architecture and support all-project inventory. The reader compares complete nonrecursive identities with two matching expanded listings, across every project, VM/container type and power state. Missing, duplicate, changing, oversized or failed entries refuse the scan. It uses the [LXD instance API](https://documentation.ubuntu.com/lxd/latest/api/) and the [LXD 6.9 all-project implementation](https://github.com/canonical/lxd/blob/lxd-6.9/lxd/instances_get.go). Clustered daemons are unsupported.

Native, login and office VM metadata must exactly match a current allocation and its enrolled provider policy, instance digest and effective CPU/RAM limits. New native/login plans include those public markers. Older guests lacking them remain unaccounted and require explicit reconciliation or verified retirement; the observer never adopts or edits them. Raw LXD configuration, cloud-init and credentials stay local; only a configuration digest and the closed public inventory records leave the host. An absent VM never releases its company/node reservation. Observations describe current state, not measured job activity or billable lifecycle intervals.

`node scripts/package-runtime-node-observer.mjs --out <new-directory>` creates a separate Linux Node package with observer, namespace helper, installer and two systemd templates. It imports no desktop or browser client. The service reads `/etc/qorpera/node-observer.json` with exactly `registryUrl` (canonical HTTPS origin) and `policy` (the enrolled public policy), and the separate `/etc/qorpera/node-observer.key`. Both paths require protected root-owned local parents; the key must be root-owned mode 0400 or 0440 for the service's dedicated primary group. No environment-selected endpoint or policy enrollment occurs at startup. The [protected installer](NODE-OBSERVER-INSTALLATION.md) verifies the manifest, host and stopped-unit custody, then installs the dedicated account, reviewed socket group, package, configuration and fixed TLS CA under an inherited kernel lock. It leaves the observer disabled/inactive and preserves exact existing files. Eighteen offline actual-systemd checks pass. Installation/enrollment has not been performed or accepted on a live node.

Polling is serialized. A failed completed scan publishes unavailable; an unconfirmed host or cancelled/stalled IO cannot fabricate a fresh measurement. The prior observation then expires on its original timestamp within 60 seconds. RPCs refuse redirects, oversized bodies and uncertain replies without automatic replay. The process retains an outstanding probe until settlement, and service shutdown cannot release machines. The root namespace helper alone has its existing limited capability; the observer has none and must remain in the host mount namespace.

`scripts/test-runtime-node-inventory.mjs` joins the actual reader/publisher with Unix HTTP and all 195 PostgreSQL migrations. It proves hardware-only refusal, a ledger change during scanning, permanent physical binding, unknown/stopped/absent machine accounting, infrastructure headroom, lost replies and history through database restart. The daemon and physical host are explicit fixtures. `scripts/test-runtime-node-inventory-host.mjs` separately runs actual protected Linux socket, namespace, machine identity and non-root custody checks in an offline disposable container. Named TLS tests exercise the real HTTPS adapter under `--jitless`. Native/login capacity and recovery proofs also pass migration 039 using a clearly labelled test-only synthetic inventory publisher; that helper is never installed by a migration. Live host/LXD/NAS acceptance, lifecycle intervals, active-human measurements and the complete operational view remain separate work.
