# Combined offline office workload

**Gone (legacy removal, step C; migration `20260930190000`).** The `--combined` and `--combined-rebuild` modes, their probe and the object gateway route they wrote through are removed: they ran a snapshot-v1 company. This file records what they covered.

Run from the repository with the prepared, local browser image:

```sh
QORPERA_OFFICE_TEST_IMAGE=qorpera-office-linux-test:step4-browser node scripts/test-runtime-office-linux.mjs --combined
```

For replacement of the entire disposable guest and a database restart, use
`--combined-rebuild` instead. Both modes use a separate, private Docker volume
for canonical object bytes and the object-gateway journal.

The proof applies every migration to disposable PostgreSQL, admits two native
staff runs through the existing wake/session/runner APIs, and executes their
tools through the native receipt ledger and office TLS gateway. The actual
`CompanyComputerLinuxGuest` owns two persistent XFCE desktops. Each shell and
Chromium runs inside the production Linux namespace boundary. Docker has no
external network. A strict host-side RPC allowlist connects the broker to SQL
over stdio; neither the shell nor browser can use that channel.

Both initial native sessions close while the desktop directories remain. Fresh
native sessions then produce separate totals on the shared workbench, read one
another's files and reconcile 40 in a browser form using real navigation, input,
click and snapshot tools. No member application, web client or viewer is running
during this workload. This proof does not establish disconnect delivery; the
separate whole-guest/viewer tests exercise an actual viewer disconnection.

The second staff run exports the first run's binary report through the object
gateway and publishes it with `company_write`. The exact publication replay
returns its original result. The first staff run imports the new live Company
File version and compares its bytes. Both desktops survive native-session
closure. Closing and reconstructing every guest adapter preserves the report
and allows another authorized import of the original canonical binary source.
The SQL verifier checks both staff identities, completed receipts, the published
path and zero remaining active office resources or screen leases.

Local result: 205 migrations, two persistent desktops, two staff runs, browser
total 40, seven exact report bytes, one published path, 18 completed receipts,
zero active resources and zero screen leases. The test exercises actual disk
object storage, HTTP transfer, canonical mutation and TLS office transport.

The rebuild mode additionally reserves one machine through the actual SQL
capacity API. After the ordinary workload completes, the driver confirms the
old container is absent and restarts PostgreSQL. It renews the still-current
runner/provider leases through their real APIs; no expiry columns are edited.
Previously released screen leases are refused after the restart. The Company
File row, current snapshot, live path entries and allocation record remain
exactly unchanged.

A second container starts with a new root and empty workbench, desktop runtime
and browser-profile directories. It does not seed or restage canonical bytes.
The verifier checks every retained object's SHA-256 address, reads the exact
current snapshot's tree manifest, compares its entries to the live SQL paths
and restores each file through the real object transport. Authorized imports
recover both files into the new workbench. The model shell cannot see the
private canonical volume. Final verification confirms that all object hashes
and canonical SQL records are unchanged.

Rebuild result: five unchanged canonical objects, two live files totaling 13
bytes, two exact-version imports, zero canonical re-uploads, one retained
charged allocation and 21 completed native receipts. No active office resources
or screen leases remain. This is a local physical guest-loss/database-restart
proof; actual LXD boot/adoption and NAS durability still require live acceptance.
It deliberately discards the test workbench and browser profiles to establish
canonical independence, rather than claiming those working surfaces survived.

The following limits are explicit:

- VM/image adoption and initial office readiness are fixtures. This is a Linux
  container, not an enrolled LXD VM or a NAS mount.
- The browser profile starts with synthetic prior preparation; its owner grant
  and ongoing authorization use actual SQL. An esbuild test-only hook serves
  the reconciliation page through Playwright routing after the real browser
  launch. It changes page content only. It does not replace browser control,
  input, the guest endpoint, effect authorization or native receipts.
- Tool inputs are deterministic test instructions; no paid model is called.
- Screen lifecycle export is covered separately and is not composed here.
- The base mode reconstructs guest adapters only. Rebuild mode removes the
  entire Linux container but does not exercise an LXD VM, guest boot/adoption
  attestation or NAS. Existing provider lifecycle proofs cover those control
  gates with physical VM observations as fixtures. Actual-host acceptance and
  undelivered screen-event custody remain separate work.

The driver removes only its uniquely named disposable containers, derived
image, volumes and temporary files. It does not change production state.
