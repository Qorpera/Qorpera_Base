# Physical screen lifecycle registry

This is unreleased Step 4 lifecycle integration. Migration `20260909000200_runtime_screen_lifecycle.sql` records physical-screen evidence independently of desired screen power, native input leases, browser grants and viewer connections. The production Linux guest supplies these records. Migration `20260909000300_runtime_screen_history.sql` adds discovery, bounded screen usage estimates and provider-stop correlation. A private disk queue separates production lifecycle recording from SQL delivery and survives service restart. Migration `20260909000400_runtime_screen_observation_recovery.sql` retains observations first delivered after authority loss in a separate, explicitly unconfirmed history. Registry and physical-guest proofs are separate, with their fixture boundaries stated below.

`qorpera_record_runtime_screen_event(startup, binding, privacy, event)` is service-only. `startup` is the exact admitted `CompanyComputerStartupIdentity`, including allocation, boot, configuration digest and systemd invocation. `binding` is the complete screen identity and generation. `privacy` is JSON null for a shared desktop or the exact current private-surface challenge. An initial request and every new ready/heartbeat event require the matching active invocation and current shared/private surface authority. Publication itself grants no physical dispatch, native input, viewer access or machine capacity.

The closed event document contains exactly `lifetimeId`, `eventId`, `sequence`, `observedAt`, `state` and `reason`. A fresh UUID identifies each physical lifetime, including a replacement on the same screen generation. A service invocation can retain only one non-closed physical lifetime on a screen at once, across shared/private modes. The permanent binding cannot change; closed lifetimes cannot revive. A later service activation has its own identity and does not overwrite prior history.

| State | Allowed reasons | Meaning |
| --- | --- | --- |
| requested | `SCREEN_REQUESTED` | Request retained before physical launch; not readiness. |
| ready | `DESKTOP_READY`, `SCREEN_HEARTBEAT` | Trusted guest reports physical readiness or continued readiness. Initial ready follows requested; heartbeat follows ready. |
| closing | `SCREEN_DRAIN_REQUESTED`, `OFFICE_SERVICE_STOPPING`, `PRIVACY_FENCE`, `AUTHORITY_LOST` | Shutdown intent; physical reaping is still unconfirmed. |
| failed | `DESKTOP_START_FAILED`, `DESKTOP_EXITED`, `DESKTOP_DRAIN_UNCONFIRMED`, `SERVICE_INTERRUPTED` | Known failure category; does not imply confirmed cleanup. |
| closed | `DESKTOP_REAPED` | Trusted guest confirms complete physical shutdown after closing or failure. |

Events append with consecutive safe-integer sequences and nondecreasing finite UTC observation times. Initial requests must be current and belong to the admitted activation. Future observations, missing sequence entries, changed event bodies, conflicting lifetimes and raw exception text are refused. Historical observation time and database receipt time are distinct. The mutable lifetime row is only the latest cursor; immutable event rows retain every accepted transition/heartbeat.

Exact replay returns the original event receipt, including its original times, even after revocation, closure or a successor activation. Competing first deliveries serialize through the existing profile/office lock order and return one receipt. Once a lifetime exists, its exact closing/failure/reaped observations remain recordable after current authority is revoked. Cleanup never needs new work authority. A terminal record does not release the cloud computer or its allocation.

`qorpera_runtime_screen_events(lifetime_id, after_sequence, limit)` is a service-only operator read with an explicit cursor and page limit of 1–1000 events. It returns the bound invocation, screen and kind, current cursor/state, confirmed screen closure time and the ordered event page. The private challenge itself is not exported by this read. Raw tables and the internal receipt helper are private, including to the service role. No automatic retention deletion is installed. Receipts contain identities, times and fixed categories; no screenshots, page URLs, browser contents, messages or credentials.

`CompanyComputerScreenLifecyclePublisher` takes the same protected configuration, allocation, boot and systemd invocation identity as ordinary-service startup. The production Linux service requires this port; no desktop/web caller selects it. Each shared desktop or private sign-in surface gets a distinct lifetime. A request is durably retained before launch, ready follows actual launcher readiness, and closed follows confirmed physical cleanup. A launch timeout without a returned handle requires the launcher's separate drain confirmation. Native-session and viewer closure leave the screen lifetime open. Privacy transitions and service shutdown own the physical drains.

The publisher serializes observations, enforces local transition ordering, and advances sequence only after durable local retention. Its optional direct-registry mode, used by existing SQL fixtures, instead requires an exact SQL receipt. Neither result replaces startup/readiness authority or physical cleanup. Production request, ready and final-close recording performs no network I/O. Export failure alone cannot prevent launch, authorized work or confirmed cleanup; local custody failure is still reported. Raw exception text is never recorded.

`CompanyComputerScreenOutbox` owns `/var/lib/qorpera-office-events`, provisioned by the ordinary systemd unit as a service-owned 0700 StateDirectory. It is separate from all adopted workbench/home/screen/profile roots and private runtime mounts. Canonical real paths, owner/mode, directory identity, regular private 0600 files and immutable scope are checked before I/O. Model namespaces do not mount this directory. Atomic no-overwrite records are flushed to disk with their exact startup, binding, private challenge and event. The sole ordinary service owns writes; this is not a multi-writer or host-failover protocol. Recovery repairs only verified interrupted hardlinks and removes uncommitted private temporaries. Missing scope with existing records, changed bytes, unexpected links or unsafe custody is refused.

Export runs independently with a three-second RPC deadline and round-robin delivery of each lifetime's earliest pending sequence. Only an exact canonical receipt or a distinct, hash-bound unconfirmed-retention receipt removes a local record, followed by directory fsync. A lost committed reply retries the original event after reopen. Local recording does not wait behind export, and service shutdown drains physical resources before closing the queue. Pending heartbeat samples are omitted while that lifetime has a backlog; transitions remain recorded. Sampling resumes at the actual observation time with the next sequence, so SQL's existing 15-second hold leaves missing intervals unknown. Queue bounds are 8,192 records and 64 MiB; reaching them refuses further local custody rather than deleting unconfirmed events.

Authorized host operators can inspect the private retained files; desktop/web clients cannot. Raw files retain the private challenge needed for exact replay, whereas the SQL operator queries omit it. There is no automatic expiry of unacknowledged records. Successful delivery removes only the local copy; SQL retains the canonical event or separately classified unconfirmed observation. This directory must survive ordinary restarts; guest-destruction/host-loss retention remains acceptance work. A never-committed request older than 60 seconds or new ready/heartbeat after revocation can still be refused by the canonical RPC. The exporter then invokes `qorpera_retain_runtime_screen_observation(p_record)` with the exact canonical file text. This service-only RPC validates closed metadata and the complete historical startup against the retained activated invocation, including predecessor invocations. It validates the screen's office identity and scope, without claiming that the reported screen generation, private challenge or physical state has current work authority. The original observation and SHA-256 of the submitted record are retained; arbitrary text fields and private contents are refused. Observation time is preserved even with clock skew, and these observations do not contribute to usage.

The separate `qorpera.runtime-screen-retention-receipt/v1` identifies the event, original observation time, retained time and exact record hash with `confirmation: unconfirmed`. Exact replay returns the original receipt. If a direct write committed before its response was lost, recovery instead returns its original canonical receipt. Immutable startup/binding/private metadata and consecutive state transitions are enforced across the confirmed prefix and unconfirmed suffix. A bounded set of transaction-lock buckets serializes cross-table lifetime/event identity races. Once a suffix exists, a trigger refuses new canonical writes for that lifetime; an old canonical receipt can still replay. This prevents a delayed request from silently promoting uncertain history. No recovery RPC activates a service, reopens a grant, changes canonical screen history or releases an allocation. Local files remain pending if neither RPC returns an exact receipt.

## Enabled lifecycle and destructive maintenance

The enabled office supervisor preserves the VM root through service restart,
power-off and reboot/resume. An explicit replacement request stops and remains
held; it does not delete the VM. Retention across those supported transitions
and destructive-maintenance limits are audited in
[RUNTIME-OFFICE-RETENTION.md](RUNTIME-OFFICE-RETENTION.md). No automatic custody
handoff before VM/root deletion is implemented or claimed. Such a workflow must
preserve private pending records before it can be enabled.

## Operator discovery and usage

`qorpera_runtime_screen_observation_lifetimes(allocation_id, after_lifetime_id, limit)` discovers both canonical and previously unregistered retained lifetimes. `qorpera_runtime_screen_observation_events(lifetime_id, after_sequence, limit)` pages their confirmed prefix and unconfirmed suffix with an explicit confirmation label on every event. Both are service-only, accept 1–1000 rows, and refuse responses above 4 MiB. Discovery is a live UUID scan, not a snapshot across pages, and declares `retained_observations_only` coverage. Local undelivered records and unobserved physical events remain outside that coverage. These reads omit private challenges.

The combined read exposes `canonicalState`, `reportedState`, `canonicalClosedAt`, `confirmedThroughSequence` and `firstUnconfirmedSequence`. A raw reported close never fills `canonicalClosedAt`. `usageIncludesUnconfirmed` is always false. Raw retained tables, shape validators, receipt helpers and the guard trigger are private, including to the service role; only the bounded write/read RPCs are granted. Neither canonical nor unconfirmed cloud history is automatically deleted. Existing canonical usage queries below continue to exclude the uncertain suffix and all unregistered lifetimes.

`qorpera_runtime_screen_lifetimes(allocation_id, after_lifetime_id, limit)` discovers retained lifetimes for one allocation, with pages of 1–1000. It returns exact startup/screen identities, shared/private kind, requested/last-observed times, the recorded state, guest closure and independently confirmed provider termination. It does not export private challenges. The UUID cursor orders a live scan, not a snapshot across pages; refresh the scan to include concurrent insertions. Coverage is explicitly `registered_lifetimes_only`. An empty page is not evidence that no unrecorded screen existed.

`qorpera_runtime_screen_history(lifetime_id, from, until)` accepts a finite past window of at most 24 hours. It clips the window to the registered request and the earliest guest closure or provider-confirmed absence. Each guest observation is held for at most 15 seconds, through the next event if earlier. Heartbeat gaps are unknown; a later heartbeat does not fill them retroactively. Ready-screen estimates, requested, closing, failed and unknown time are separate. `observedLifetimeHours` is their sum and includes uncertain time; it is not an assertion that the screen ran throughout. The method is `guest_screen_heartbeat_hold`, with `exactTransitionTimes: false`. Precise idle time and richer concurrency reports remain deferred by the contract.

Intervals preserve first/last event IDs for investigation. Indexed second-prefix bounds admit variable UTC timestamp precision, while exact clipping/ordering uses timestamps. More than 20,000 observations or a response over 4 MiB is refused; use a smaller explicit window. Both queries are service-only, the termination helper is private, and no query mutates events, grants or allocations. Original events remain retained without automatic deletion. Screen-hours never multiply computer-hours; aggregate separate lifetimes only within the stated coverage, and use the independent allocation/computer history for machine usage and release.

Provider termination comes only from a retained `qorpera_runtime_office_stops` acknowledgement joined to the lifetime's exact activation and complete startup identity. It exposes `confirmedGoneAt`, inspection/transition identity and the action. This means the service cgroup was confirmed empty/absent by that time, not that a screen closed at that exact instant. A missing guest-closed event stays missing and its recorded state is unchanged. Stale time before the provider acknowledgement remains unknown. The allocation remains charged until its independent release boundary.

`node scripts/test-runtime-office-start.mjs --lifecycle-stop` exercises real provider/startup activation, revocation and stop acknowledgement after all 199 migrations. The existing TypeScript publisher still recovers discarded committed replies. New fixtures prove 30 ready, 15 unknown, 5 requested, 5 closing and 15 failed seconds over a 70-second lifetime, fractional/clipped/partitioned windows, private-kind visibility, bounds and read-only access. Paginated discovery and the usage result survive database restart. The actual stop adapter/SQL acknowledgement independently caps a lifetime whose guest supplied only requested/ready events; it leaves those events and charged allocation intact. Root stop measurements and physical event timestamps remain fixtures. The earlier ambiguous `event` name in fixture setup was qualified; no production authority rule was relaxed.

The same SQL driver prepares 11 observations in the actual disk outbox before revocation, closes/reopens the queue and exports after the actual stop acknowledgement. It proves lost-retention-response recovery, exact original hashes, mixed canonical/unconfirmed history, discovery of never-registered shared/private lifetimes, private-challenge omission, malformed/member-call refusal, concurrent replay and database-restart stability. Canonical history, office state and allocations remain unchanged. The first guard version exhausted PostgreSQL shared lock memory in the existing 20,000-event fixture; bounded lock buckets fixed that without increasing server limits.

`scripts/test-runtime-office-linux.mjs --guest` separately runs the actual Linux guest, XFCE/TigerVNC, Chromium, private surfaces, publisher and disk queue against fixture authority/registry. SQL export stays unavailable through six physical lifetimes (four shared, two private), ordinary workload, viewer disconnection, private transitions and guest reconstruction. The fixture inspects actual per-screen directories at local retention. All 24 transitions replay unchanged after queue reopen, including a lost committed closing reply. The model shell cannot see the private queue volume. This is not a SQL/physical-guest combined proof, a VM reboot or a live NAS acceptance. Initial use of a macOS bind-mounted queue failed its directory-safety guard; the passing fixture uses a private Linux volume without relaxing that guard.

`scripts/test-office-boot-service-start-systemd.mjs` separately exercises the packaged unit and protected startup/stop controls under actual systemd. The service can fsync its private StateDirectory, and a synthetic pending file preserves its inode, bytes and owner through two explicit restarts and final stop. Ordinary workload and event contents are fixtures in that systemd proof; the real outbox/physical guest is exercised by the Linux probe above.
