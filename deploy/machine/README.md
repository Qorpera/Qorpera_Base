# Company machines

Machines are virtual machines that agents start themselves, for tests, builds, Docker stacks and long jobs (Jonas, 2026-09-28). The word follows the contract's wording: a computer is one agent's screen, and a machine is a VM. The coding machines and the company machines that host computers are separate things. So is this one.

An agent picks the size (CPUs, memory, disk). Inside, the agent's commands run as root, and Docker with Compose, Node, Python, Git, build tools and the toolbox every Qorpera machine has are installed. A machine belongs to the company. Every member sees it and may stop, wake or delete it. Any agent of the company may use it. It holds no credential, it can reach the internet but none of our networks, and nothing reaches it from outside. Machines run on our own nodes only.

## What runs where

| Part | Where | What it does |
|---|---|---|
| SQL (`20260928259050_runtime_company_machines`) | the kernel | Machines, their disposable placements, commands and events; placement and admission on the shared node ledger (provider kind `machine`); the executor's custody of each placement; members' list and actions; `machine-event` wakes |
| `machine_*` tools (`packages/runtime/src/cloud-machine-tools.ts`) | the identity host, in a company conversation and in its agents' workers | start, run, read, cancel, stop, delete, list (a worker's start and read can wait) |
| Command route `/v1/machine-commands/*` (`cloud-machine-command-http.ts`) | the coding executor's ingress and peer listener | SQL authority, local execution or forwarding to the machine's node |
| Machine workload (`packages/runner-orchestrator/src/company-machine-host.ts`) | the coding executor on each node, a pass every 10 s, or at once on a wake (below) | admit waiting machines; create, start, stop, delete them under the coding machine's journal (`company-machines/` on the NAS control path); keep each guest's lease; record how commands ended, which were busy, and busy work outside them |
| Guest helper (`packages/runtime/src/cloud-machine-guest.ts`) | `/opt/qorpera-machine/cloud-machine-guest.mjs` in the machine | commands as transient systemd units under `qorpera-machine.slice`, their retained intent and bounded logs on the machine's disk, the watchdog, and `folder-mount`, which mounts the company folder at `/company` from a view read on its stdin |

### Lifetime

- **Placement.** A start places the machine on the node with the most room that fits it: processors and memory on the shared node ledger, and disk against the room on the node's pool (20260930757000): the executor reports LXD's real figures for its pool at most every 30 s, and the room is its real free space less a fifth of the pool (what else shares it, db-standby among it) and less what the awake machines could still grow into (their disk size less what they hold); a sleeping machine counts only what it holds. Without a report of the last 2 minutes the room is the paper budget (`disk_bytes`, every placement that still exists counting its full disk). When the first machine in line fits nowhere and what sleeping disks on a node really hold would make it fit, their disks are given up: never one used in the last 24 hours while an older one can go, the asking company's own first, the longest asleep first, only as many as needed, never one whose use the report does not give. Such a machine's row keeps when (`disk_freed_at`), and its view says `diskFreed` while it has no disk and on its first new disk; it starts fresh on its next wake. When no node fits it now, the machine waits, and every pass of every executor admits one waiting machine at a time. The build takes them in the order they asked, where they fit; the contract does not fix an order yet. A size larger than every node's largest machine or machine disk is refused at once. There are no prices, no priority rules and no count per company or agent.
- **Task machines** sleep once the node's idle delay has passed (default 1 hour) with no agent use and no busy machine (the one idle rule, 2026-10-03 amendment): the machine as a whole keeps itself awake while it is busy, at least 5% of one core or 512 KiB read or written in 30 s (`@qorpera/contracts` idle-rule), its commands, containers and programs left behind together, apart from its own control (the watchdog in `qorpera-control.slice`, the LXD agent the executor's calls run under, and a command's relay to its log: its own processor time and bytes, never its command's) and the system's plumbing (systemd as pid 1 in `init.scope`, `systemd-journald.service` and `rsyslog.service` where the image has it: they only start, log and stop for other processes, which count on their own). Its processor time is user, nice, system, irq and softirq from `/proc/stat`; steal (the host's) does not count. A dev server that only waits lets the machine sleep. Just before a sleep the executor takes one last look, so a machine busy again keeps running (stop custody then refuses). Once SQL grants the stop, the helper's `stop-commands` lists what runs (this boot's running commands, at most 32 oldest first, and whether Docker ran containers) and stops the commands, Docker and containerd; the executor records that snapshot before the power-off, so those commands end with the stop's cause (`stop_cause`) and the agents are told once (`machineStopped`), containers once per machine and boot. A stop whose power-off fails is over: the next is a new stop with its own snapshot. A helper without `stop-commands` is stopped with `systemctl stop` as before, and what still ran is told at the power-off. Sleeping powers the VM off, frees its room and keeps its disk on that node for a wake there. The disk is scratch: a machine that wakes when its node is full or gone starts fresh as a new placement on another node, and its old node's executor deletes the old VM (Stateless Compute). A running machine never moves, nor one that asked for room under five minutes ago while its node has no usable observation. A task machine that never came up sleeps the same way and gives its room back. A task machine is removed after the node's removal delay asleep (default 30 days, like a quiet coding session's archive). The command is `qorpera_configure_machine_lifecycle(owner, sleepAfterSeconds, removeAfterSeconds)`.
- **Always-on machines** are never stopped or removed by the kernel.
- **A wake** (`machine_start` with the machine's name, or a member's Start) asks for room again, first on the node it slept on. A member's Start only puts it in line; the next pass gives it room. A machine asleep on a placement made before its node's machine policy changed (a new image) wakes fresh from the current image. One that still holds room keeps its old image, and restarts on it after a node reboot, until it sleeps or is stopped.
- **Workers** (an agent's background helpers, 2026-09-28) start and use machines like their agent, with the same authority, and their commands are their own. A worker has no conversation to continue, so nothing wakes it: it waits inside its run, up to 300 s a call and no model turn spent, while its machine starts (`machine_start` with `waitSeconds`) or until its command ends (`machine_read` with `waitSeconds`). It waits by looking every 5 s at the kernel's `status` (the machine's state and the command's end as the executor last recorded it, a pass every 10 s), and at once when its machine's executor says to look again; it writes nothing, takes no machine lock (only the run's own authority check locks its job row) and never reaches the machine; the one read of the command's output comes after. To wait longer, the worker repeats the same call (same `operationKey`; `waitSeconds` may change). A cancelled worker, or a paused company, is told its work stopped and stops waiting. A machine waiting in line for room answers at once, and the worker reports that to its agent, which can retry. The kernel never puts a worker run on a machine's list of runs to tell and refuses a worker's command that asks to be notified (migration `20260928259055_runtime_machine_workers`). A conversation's machine card also shows the machines its agent's workers started. Since 20260930747000 a conversation's run may wait the same way while its machine starts, up to 60 s a call (`machine_start` with `waitSeconds`; its commands still wake it with `notify`); it stays on the machine's list of runs to tell, and its look that sees the machine running suppresses its own 'running' word. A new task machine is the agent's own free machine of the same size when it has one, woken if it sleeps (`qorpera_company_machine_reusable`), and the answer says `reused`. Since 20260930755000 the start waits by default (60 s, also through a short line for room, never for computer hours; `waitSeconds` asks for less, 0 for none), and each wait is kept in `qorpera_company_machine_start_waits` (whether the model asked, how long, how it ended).
- **A wake's path** (perf sprint, 7 Nov 2026). The executor's next pass need not be up to 10 s away. `machine_start` of a machine that is starting or in line calls `/v1/machine-commands/wake` on the coding gateway (the run's own lease proves it, as for a command; it goes on to every peer, since a machine in line has no node yet). That only asks for a pass: it carries no authority, every step of that pass asks SQL as ever, and a lost word costs only the next pass. A worker's wake stays open for up to 20 s and answers once a step took the machine somewhere (its start done, its folder settled too), which ends the worker's wait; the worker then looks at what SQL says. A new boot is marked running only once it is usable (`systemctl is-active basic.target network-online.target`), so commands that need the network or Docker find them (`docker.socket` is up by then, and waits for its daemon); one that is not usable a minute after it was first seen starting is marked all the same, as before. Between passes, each guest still starting is asked every second, of LXD alone (its agent answers a file read, then that check), and a usable one asks for the next pass, three times per boot at most. A stop or a release asks for the next pass too, since a machine in line may fit now. However many wakes come, passes come a second apart at most. A pass waits 2 s at most for its steps: a step still running then goes on by itself, its placement gets no other step until it ends, nor from a pass whose list was asked before that step ended, and what it came to is logged with a later pass, so one machine's slow guest or LXD call holds up nobody's wake. A member's Start has no such word: the next pass gives it room.
- **Commands** have no deadline unless the agent sets one. They survive the agent's turn and stop when the machine stops. The executor watches every open command, and SQL records how it ended. A command started with `notify: true` wakes the run that started it once it ends. A machine that finished waiting wakes the runs that asked for it, unless they already used it; one that was stopped or deleted before it ran tells them so (kind `stopped`). The wake is a continuation in that run's conversation (source `machine-event`), like a worker's report.
- **Crash detection.** The executor renews a 15-minute lease in the guest every pass, also while SQL refuses new room (a node that looks unavailable, or machines switched off): only creating or starting needs room. The watchdog timer stops `qorpera-machine.slice` when the lease runs out. The lease is long on purpose, so jobs of hours outlive an executor restart or a release cut. Root in the guest can switch the watchdog off. The VM is the boundary, and the executor powers machines off from outside whenever SQL wants them stopped.
- **What LXD shows settles the rest.** A machine's VM keeps nothing of its own, so the executor settles from LXD's view what its journal cannot. A VM that stopped by itself (a `poweroff` inside, a node reboot) is stopped, then started again, put to sleep or deleted as SQL wants. A failed create or start is tried again up to three times. An operation LXD forgot after an LXD restart is settled from the VM at once, and an effect it never confirmed (an executor stopped mid-request, a refused request) is settled ten minutes later.

### What a machine can reach

A machine is an agent road machine: its only network card is a port of the agents' bridge `qagent0`, and its internet traffic leaves through the node's agent exit (`deploy/agent-exit/README.md`, contract section 19 "agent traffic leaves through the agent exit"). The executor plugs each machine in right before it creates it (`agent-plug.ts`: the node's plug tool gives the machine its address and the MAC its card carries), so the policy's `network` must be `qagent0`. The exit refuses our own networks and TCP port 25, its bridge rules tie each machine to its port, MAC and address, and LXD's MAC filter and port isolation keep machines apart; the exit's log names the machine's company. The agent exit must be installed and healthy on the node first (`deploy/agent-exit/README.md`, "Switching a node on").

Until 3 October 2026 machines used their own NAT bridge, made by `setup-machine-network.sh` (default `machine-net`, `10.88.0.1/22`), with an ACL that dropped these destinations. The script stays for reference; no machine uses that bridge any more:

- 0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.168/16, 198.18/15, 224/4 and 240/4;
- except two addresses, left out of those ranges by exact CIDRs (61 ranges, plus 2 rules for the gateway's ports): the bridge's gateway, where TCP and UDP are open only for DNS (53) and DHCP (67) (ICMP to it is not dropped), and 255.255.255.255, where a DHCP discover goes.

LXD applies drop and reject rules before allow rules, and its baseline DHCP and DNS allowances do not open a hole in them (seen on node 2, `deploy/test-machine/README.md`). An ACL that drops 10/8 or 240/4 whole leaves machines without an address; the script refuses one it finds (replace it: `lxc network unset <network> security.acls && lxc network acl delete <network>-egress`, then run the script again).

Together these covered the NAS and the node LAN, Tailscale, cloud metadata, the other bridges and the node itself. The agent exit covers the same destinations (its `internal4` set) and more.

### The desktop

A machine has no screen unless an agent asks for one (Jonas, 10 Nov 2026: agents live in headless machines and request a desktop computer, which gets the compute a desktop needs, with chosen company files or programs on it). `machine_start` with `desktop: true` makes a desktop computer: a machine of at least 2 processors and 4 GiB (`CLOUD_MACHINE_DESKTOP_LEAST`; a smaller size asked beside it is raised). The image is the same for every machine; what makes one a desktop computer is its size, and `desktop start` refuses a smaller machine (exit 3) and names the way to get one. Nothing of the desktop runs until `desktop start`. Measured on node 2 (10 Nov, 2 processors, 4 GiB): the desktop starts in 1.2 s, Chromium in 1.4 s, a screenshot takes under 0.1 s; the desktop adds 60 MB and Chromium's first tab 190 MB; on 1 processor and 1 GiB a real site took 22 s or never loaded, hence the least size.

Most work needs no screen: checking a page, taking pictures of it or filming it is done headless. The image has Playwright (pinned by version, with its own Chromium builds under `/opt/ms-playwright`; a login shell's `NODE_PATH` and `PLAYWRIGHT_BROWSERS_PATH` find both from any folder, `/etc/profile.d/qorpera-machine.sh`), ffmpeg, and `chromium` (`/usr/local/bin/chromium`: the image's Chrome for Testing; as root it runs without Chromium's sandbox, which root cannot use, as Playwright's does).

- `desktop start` (an agent's `machine_run`, as root) starts `qorpera-machine-desktop.service`: TigerVNC's X server on display `:1` at 1600x1000 and an XFCE session with the desktop's look (below), as the account `desktop` (`desktop-session`), with one session bus at `/run/qorpera-desktop/session/bus` that programs started later join. The unit has no `[Install]`, runs in `qorpera-machine.slice` like the commands, and stops with `desktop stop`, the watchdog and the machine. `--lang da-DK` and `--tz Europe/Copenhagen` set the browser's language and the programs' time zone (default en-US, UTC); `--size WxH` or `desktop size WxH` changes the screen's size. The start returns once the session has drawn its dock and its backdrop (1.2 to 1.6 s, measured 12 Nov 2026; it waits 6 s at most for XFCE's desktop to name its picture on the root window, `_XROOTPMAP_ID`, which it does the moment the backdrop is drawn, and for a screenshot that is not one flat colour), so the first screenshot or `machine_screen` look shows the whole desktop, never a bare ground or a dock without its backdrop.
- **The desktop's look** (12 Nov 2026; Jonas on the first desktop computers: "what happened to the agent wallpapers? the docker has 4 settings icons instead of file explorer and terminal?"). It is the office desktops' look (`deploy/lxd-company-computer-guest/README.md`, "One flat dock is the whole desktop chrome"), carried over, not drawn anew: the same bar, the same CSS and the same window and terminal settings, which a test compares.
  - *The dock.* One flat dark bar along the bottom edge (80 px, 64 px icons) is the whole desktop chrome: exactly three tools in its middle, browser, files and terminal, under Qorpera's own icon drawings; the date at its left and the time at its right; no top bar, no window list, no other launcher. An icon whose program has a window shows a white mark under its tile, minimised or not: the dock is the window list.
  - *A press on an icon* (`desktop-look press`) first brings back the window the program already has. With none, it asks root for the program by putting an empty file named `browser`, `files` or `terminal` into `/run/qorpera-desktop-dock` (root's folder, made at every boot by `/etc/tmpfiles.d/qorpera-machine-desktop.conf`, into which only the account `desktop` may put a name; the file carries nothing). `qorpera-machine-desktop-dock.path` hears it and runs `desktop-dock-open`, which starts the program with the image's own `desktop` command (`desktop dock browser|files|terminal`, an entry for the dock alone) the way `desktop open URL` and `desktop run` start one: as `desktop`, in a unit of its own, with the browser's flags and profile. So the browser a member opens from the dock is the one an agent's next `desktop open` finds, it opens maximised above the dock on its new tab page, the memory guard meets it as any program on the desktop, and a press puts off the idle stop like any `desktop` command. Files and the terminal open in the company folder at `/company` when the machine has it, else in the account's home; the file manager's side pane names the "Company folder" when `/company` is mounted at the desktop's start. The browser's icon shows an outlined mark and pulses while the browser comes, and turns grey with an amber mark for a few seconds when it did not come (20 s). Neither unit has a start limit: systemd refuses the sixth start of a service within ten seconds unless its unit says otherwise, which would have switched the dock off for a member who opens and closes a program a few times in a row. Measured: a click on Files or Terminal shows its window in 0.23 s, on the browser in 1.0 s.
  - *The backdrop.* The figure of the agent the machine belongs to, tone on tone, one frame for each hour of the day (the ground is light by day and dark at night). The machine names the figure in ONE place: the word in `/etc/qorpera-machine/desktop-figure` (planet, acorn, flame, rocket, crown, heart, star, cloud, bolt, mushroom, moon or puzzle; root's file). It is read at every `desktop start` and every three seconds while the desktop runs, so a figure set or changed later shows within seconds. A machine without the file, or with a word the image has no set for, shows the neutral backdrop: the Qorpera wordmark, drawn the same way (`deploy/machine/backdrops`, from `backdrops-source`). A saved ghost shows the moon, as every client draws it. The sets are one hue: no colour is needed beside the figure. Nothing writes that file yet: until something does, every machine shows the neutral backdrop.
  - *Time.* The dock's clocks and the backdrop's hour follow the time zone the desktop was given (`desktop start --tz`), also when it is given to a desktop that already runs. A desktop started without `--tz` takes the company's time zone when the machine names one: the word in `/etc/qorpera-machine/desktop-timezone` (root's file, an IANA name such as `Europe/Copenhagen`, written by the machine's executor as the figure is; a company has one zone, taken once from a member's browser). `desktop` reads it only at the start of a desktop, so a desktop that runs keeps the zone it has and a word that changes meanwhile is taken at the next start; `--tz` wins over it. The word came from a browser: only a plain file of root's own is read (never a link or a pipe; the way to it is root's alone, as to root's notes), its bytes must be exactly the word, or the word and one line end (what the shell read is compared with the file byte for byte, since its `read` skips a NUL and stops at a line end: a NUL anywhere, a carriage return, a second line or a byte before the word is no zone), and the word has a zone name's shape (letters, digits, `_`, `+`, `-`, at most two `/`, 64 bytes at most) before it is ever put after `/usr/share/zoneinfo/`, where it must name a file. Anything else, and a machine without the file, leaves the desktop on UTC. The machine's own time zone stays UTC.
  - *Windows.* No icons on the backdrop (files opened with `desktop open` are still linked in `/home/desktop/Desktop`). No compositor, one workspace, new windows in the middle, an outline while resizing, title bars without the roll-up button. The terminal is Bash with a prompt that shows the folder, on a calm dark palette, without menu bar or scrollbar, and with "Terminal" alone in its title. The programs' own pictures (the file manager's arrows and folders) come from the Adwaita icon set, which GTK brings and the image now names; XFCE's own defaults name a theme and an icon set the image does not have.
  - *Where it lives.* The pictures are in the image, read-only: `/usr/share/qorpera-desktop/dock/*.png` and `backdrops/<figure>/<HH>.png`, 9 icons and 13 sets of 24 frames, 5.7 MiB in all (the guest package carries them as one archive, `desktop-art.tar`, made the same bytes each time by `scripts/machine-desktop-art.mjs`). The look itself is written into the account's configuration by the session at EVERY `desktop start`, before XFCE reads it (`desktop-look write`): a desktop never drifts from the image, whatever was changed or removed in the account is put back, and the image keeps nothing in the account (its build removes everything there). It is only a look: XFCE starts whatever came of it, and the watcher that sets marks, hours and figures (`desktop-look watch`) is none of the jobs that keep the desktop's unit alive.
  - The image build refuses an image unless every picture is there and is a PNG of its size (every icon, every figure and the neutral set, every hour); XFCE itself answers that the desktop has one bar with three launchers between two gaps and two clocks, each launcher its one entry with its picture, no icons, one workspace and no compositor; a machine that names no figure shows the neutral backdrop, a named figure shows within seconds (a ghost as the moon, a word that is no figure as the neutral one), and the clocks and the backdrop follow a time zone (the one `--tz` gives, and the company's from the machine's file at a start without it: a desktop that runs keeps its zone, the next start takes a changed word, `--tz` wins, and a file that is a link is not followed); a real click on each icon opens its program as a unit of its own (the browser maximised above the dock, started as `desktop open` starts it), each icon gets its mark, a second press starts no second browser, and the terminal opened and closed eight times in a row from the dock still opens; and the look comes back whole in an account that was emptied.
- **Root and the desktop's account** (12 Nov 2026, reviews r1 and r2 of #1704). The account `desktop` is where pages and the programs an agent starts on the desktop run; root, which runs an agent's commands, reads the company folder's view. So what root notes about the desktop lives where only root writes, and root reads none of it from a place the account owns: the account could make any name there a link to a file only root may read, or a pipe that never answers. And root never looks at a path and then uses the path: between the look and the use the account can make a name on it a link.
  - *Two folders under `/run`.* `/run/qorpera-desktop` is root's (root:root 0755; the unit makes it so, empties it at every start and after every stop, and sets the idle clock, all as root): what root notes about the desktop lives there, the idle clock `last-use`, the language and time zone it was started with (`lang`, `tz`), the folders it serves (`serve-<port>`) and a screenshot on its way. `desktop`, the screen helper and the executor write and read these, at the paths they always used; the account may read them (the session reads the idle clock, the look the time zone) and can put, replace or point nothing there. `/run/qorpera-desktop/session` is the account's own (0700): its session bus and what its programs keep. Root hands that folder to the account's programs as a path and reads nothing in it. Until this change both were one folder, the account's, and root's `desktop` read `lang` and `tz` there for every program it started: with `lang` made a link to the folder view, a program of the account was handed the view, pass and all, as its `LANGUAGE`. That ran for an agent's own `desktop open` and `desktop run` too, so it was in the image before the dock.
  - *Files where the account can reach: `desktop open`, `--copy`, `desktop shot`.* `desktop` leaves them to `/opt/qorpera-machine/desktop-files` (python3, run as root) and does nothing with a target's path itself. Review r2 of #1704 found two ways past a look at a path: a link in the middle of a way root owns, and a part of the way planted after the look. So every piece of work is done in one of two ways, and none in a third.
    - *As the account*: in a process of the account's own (`setpriv`: its user, its group and its other groups, no right kept or gained, a new environment; a session of its own; no descriptor of root's). Whatever a planted link leads to, that process reaches only what the account could reach anyway. Everything in `/home/desktop/Desktop` is done so: the folder, a free name taken by making it (nothing there is ever replaced), the link, the copy of what the account can read itself. Root checks the three lines that process answers (a kind it knows, an absolute path, a plain name) before it opens anything by them, and waits 30 seconds for a link or a picture and 15 minutes for a copy, then ends the process: the account can stop its own, and `desktop` holds the desktop's lock meanwhile. What the account's process makes in steps is never seen half made (review r1 F1 of #1712): a copy is made as `Desktop/.qorpera-desktop-copy.<mark>`, a name the desktop does not show, and gets a free name in one step when it is whole (`renameat2` that replaces nothing); a picture is written beside its place and moved onto it. When the work does not end well, whatever ended it (root's patience, a signal from another such as the memory guard, a full disk, a file that cannot be read half way), root has the account take away what was on its way, under the mark root picked for that piece of work. Before it does, everything the account's process had started is ended and collected (review r2 F1 of #1712: its `cp`, when another ended the process itself, went on and could write after the cleanup): the whole process group is ended on every way out, while the process's number is still its own, and root's side collects what is left of it itself (it is the subreaper of what it starts). A signal that asks root's own side to stop (SIGTERM, SIGHUP, an interrupt) runs no code of it at all (reviews r3 and r4 of #1712 each found a window around a handler that raised; there is no handler now). The three are held back from root's side's first statement to its last, and the kernel keeps one that arrives waiting, however many arrive. Root's side is one thread that never waits blindly: every 50 ms it looks whether its patience is over and whether a stop waits, and either ends the account's side. After the collect it gives the work up; the taking away runs to its end, since a stop does not end it; and root's side ends as its last statement, by the signal itself, so the shell that called it sees a command ended by that signal. Which of the three it heeds is decided once, at its start, from what it was started with (review r5 F1 of #1712): a signal its caller ignores (`nohup desktop open TARGET --copy`) or holds back itself is neither held back nor read, and is at the end what it was at the start; held back, even an ignored signal would wait and be read as a stop. The account's processes are started with what root's side was started with: none of root's own holding back, and a signal the caller ignores is ignored by them too, as by any program started under it; they are ended with SIGKILL, which nothing ignores or holds back. `desktop` itself, a shell script with no trap, does with these signals what it did before. A SIGKILL of root's side cannot be held back: what is on its way then stays under its hidden name. A link is one step: it is there whole or not at all, and the next `desktop open` of the same target uses it again.
    - *As root, through folders root holds*: root opens the way part by part from `/`, each part inside the descriptor of the one before and never through a link (`O_NOFOLLOW`), and goes on only through folders that root alone can change: owned by root, not writable by a group or by everyone, with no ACL that lets another write. What it reads or makes, it reads or makes inside the folder it holds, and no name is looked up twice: a name is taken hold of once (`O_PATH`), and what is then held says what it is and is what gets opened.
    - `desktop open TARGET` (a link) is the account's work. A target the account cannot read gets no link, and the answer names `--copy`.
    - `desktop open TARGET --copy`: when the whole way to TARGET is root's alone (`/root/...`, `/company/...`, `/opt/...`), root reads it (a file, or a folder in which every folder is root's alone too) and sends it down a pipe to the account's process, which puts it on the desktop as the account's own; a link in it stays a link, and a copy that does not come whole is not kept. Any other TARGET (under `/tmp`, in the account's home, on a way with a link) is the account's to copy with its own rights; what it cannot read is not copied, and the answer says which part of the way stopped root.
    - `desktop shot FILE` and `--shot FILE`: root takes the picture into its own folder (`/run/qorpera-desktop/shot-<pid>.png`) and prints its size and pixels from there. When the whole way to FILE is root's alone, root writes it inside the folder it holds, makes missing folders (0755) and refuses a FILE that is a link. Otherwise the account saves it, as its own file, where it may write (written beside its place and moved onto it, so a name there that is the account's own link is replaced by the picture, never written through); where it may not, nothing is saved and the answer says why.

### Memory

Every machine, with a desktop or without, has compressed memory from its boot on and a guard at the edge of its memory (12 Nov 2026). Measured on node 2 that day (2 processors, 4 GiB, a desktop with three heavy web apps, a 1.5 GB job and one more tab at a time): without either, the machine was fine to 6 tabs, slow at 7 (17 frames a second), took 21 s to load tab 8 and stopped answering at tab 13; nothing was ended in time, and the executor's own call was lost. With compressed memory the same machine carried all of it and 24 tabs at 39-59 frames a second (2768 MB kept in 1080 MB).

- **Compressed memory** (`/opt/qorpera-machine/machine-memory swap`, run by `qorpera-machine-memory.service`). What programs hold but do not use right now is kept compressed inside the machine's own memory: a zram swap device with zstd, as large as the machine's memory, at priority 100, with `vm.swappiness=150` and `vm.page-cluster=0` (the measured values). It is set up through sysfs once `/dev/zram0` is there. The unit comes before `basic.target`, which the executor waits for before it counts a boot as usable, so it is on before anything of an agent runs.
- It never fails or holds up a boot. The script always ends well: a machine where it cannot be set up runs without it, as machines did before, and says so in one line of the journal (`compressed memory is OFF on this machine, ...` and why). `basic.target` only wants the unit, and a script that hung would be ended after 20 s. Run again, the unit changes nothing.
- The image build fails if a kernel in the image has no zram module, so a later kernel cannot drop it silently. It also runs the unit as a boot does, hides the module and sees the unit end well with that line, and brings it back.
- **The guard** (`machine-memory guard`, run by `qorpera-machine-memory-guard.service`). When memory and its compressed reserve are both nearly gone, one process is ended and the machine keeps answering. It is earlyoom (from apt), which ends the one process the kernel itself would end, the one with the highest `oom_score`: a browser tab first (Chromium marks its tab processes 300 and its helper processes 200), then the biggest other program, which may be an agent's own job. systemd-oomd is not used: it ends whole control groups, and here one group is a whole command, the whole browser with every tab, or the desktop with everything on it. The package's own earlyoom unit is masked; ours runs it beside the commands' slice (`qorpera-control.slice`), so its own work never counts as the machine being busy.
- Its limits are earlyoom's own measure: the memory still available as a share of what programs can use right now (available plus what they hold in memory, not the machine's memory), and the free share of the reserve. A process is ended when that share is at or under its limit and a tenth or less of the reserve is free, so compressed memory is really used first. The limit aims at an amount: about 300 MiB still available (8 % of the memory on a machine over 3.7 GiB), which a desktop needs for the files it runs from whatever its size. `machine-memory guard` turns the amount into earlyoom's share for the machine it runs on: 17 % on 4 GiB and more, 29 % on 2 GiB; 9 % and 16 % on a machine without the reserve, which is judged on memory alone (`machine-memory limits [KiB] [on|off]` prints them). Measured past the edge on 12 Nov 2026 (2 processors, heavy web apps, a job, tabs until three were ended): on 4 GiB the first tab was ended at about 300 MiB available, pages kept loading in about a second and `desktop click` answered in 0.6 to 0.9 s at worst; with a limit of 6.7 % (114 MiB) pages took 6 to 36 s before the first end. On 2 GiB with 29 % pages took 0.3 to 2.9 s and a click 1.8 s at worst; with 17 % (130 MiB) pages took 4 to 25 s and a click 3.7 s. It ends the process at once (SIGKILL), as the kernel's own killer does. At the edge it ends a few tabs one after the other (up to 4 when measured), until a tenth of the reserve is free again. What it cannot see is memory that does not compress: that fills the reserve without freeing anything, and the kernel's own killer ends the program (a job of twice the machine's memory, all random, was ended by the kernel after about 10 s, in which two clicks took 3.5 s).
- **Who is never the one ended** (`OOMScoreAdjust`, which the kernel's own killer follows too): the guard (-1000); the LXD agent and what the executor runs through it, which is the guest helper, the screen helper and a member's look and input (-900, `lxd-agent.service.d/qorpera-memory.conf`); the folder program and the watchdog (-900); the desktop's X server and session bus (-900), and the XFCE session with its window manager and panel (-100, set by the session script, so a big program someone starts from the session's own menus can still be the one that is ended). An agent's command and a program opened with `desktop open` or `desktop run` are units of their own and are not protected.
- **What an agent sees** when its own job is the one ended (measured: a job of twice the machine's memory was ended after 10 to 12 s, and the desktop answered throughout). When the program is the command itself, which is how bash runs the last program of a command line such as `cd app && node build.js`, the command ends as `failed` with exit code 128 and nothing in its output: the guest helper reports any signal as 128. When a shell or tool stays above the program (a script, a later step, `npm run`), that one says `Killed` and the program's exit code is 137. Nothing tells the agent in words that memory ran out; the machine's journal names the process (`journalctl -t qorpera-machine-memory-guard`). **What a member sees** when a tab is ended: that tab shows Chromium's own "Aw, Snap!" page ("Error code: 9") with a Reload button; the other tabs, the browser and the desktop go on.
- Nothing else changed: a machine's sizes, the least size of a desktop computer, billing and the node's accounting are as before. Compressed memory lives inside the machine's own memory.
- `scripts/prove-machine-memory.sh` proves all of it on throwaway machines made from a built image, in a node's image build space: compressed memory after a boot, the unit run again, a boot with the module hidden, the idle rule's measure on the quiet machine, clicks on one spot, past the edge (`desktop click` asked from the host every second keeps being answered the whole time: none fails, none takes 3 s or more, and at most 1 in 100 takes 2 s or more; every look of the guest helper is answered with an observation; every phase of the browser's work ends well; something was ended and named in the journal, and only what may be: browser tabs, Chromium's own helper processes and the agent's job, never the browser itself; the browser, the desktop, the helper and the machine's own services are alive after), and an agent's job that outgrows the machine. It passes on nothing that was not really answered: a helper that failed or timed out, an empty answer, a journal that could not be read and a browser phase that did not end well are each a failed check (`scripts/prove-machine-memory.test.mjs`).

### Sizing a machine for the job

An agent picks a machine's size, and until 13 Nov 2026 nothing told it why it would pick more than the default 2 CPUs and 4 GiB. Of the 38 machines agents had started by then, 30 had 2 CPUs, 5 had fewer and 3 had 4: none had more. The question came from a company's renders (Jonas, 13 Nov 2026: "how come we seem to not get very realistic animations for anything, even the things we want to make realistic?"): its agent had fetched Blender by itself and rendered with `-t 2` at 32 samples on a default machine. Custom machines were, in Jonas's words, "built, just not used well enough".

`machine_start`'s description now says what a size buys and costs (`MACHINE_SIZE_FOR_THE_JOB` in `packages/runtime/src/cloud-machine-tools.ts`), and the company instructions say how a render is lit and looked at before anyone sees it (`packages/runtime/src/cloud-native-company-context.ts`).

**Measured** on the operator test machines (10 vCPUs of a Ryzen 9 7950X each, shared with other test runs): official Blender 4.3.2, Cycles on the processors, OpenImageDenoise, fixed sample counts, one full HD frame of a lamp on a table in a room. "Dark world" is the scene as an agent writes it in one pass (boxes and cylinders, flat colours, a near-black world, the lamp as the only light); "real room" is the same layout from CC0 files (an HDRI as the world, texture sets, modelled furniture). The scene, its driver, every frame and its record are in `lanes/realistic-renders-20261113/`.

| Threads | Dark world, 64 samples | Real room, 64 samples | Dark world, 256 samples | Real room, 256 samples |
| --- | --- | --- | --- | --- |
| 2 | 317 s (5.3 min) | 319 s (5.3 min) | 1312 s (21.9 min) | 1338 s (22.3 min) |
| 8 | 83 s (1.4 min) | 81 s (1.4 min) | 319 s (5.3 min) | 299 s (5.0 min) |
| 10 | 69 s (1.1 min) | 65 s (1.1 min) | 257 s (4.3 min) | 244 s (4.1 min) |

The agent's own setting (1280 x 922, 32 samples, 2 threads, the dark world) took 94 s.

- **Processors divide the wait, not the work.** The processor seconds are the same at every thread count, so a machine four times the size finishes in a quarter of the time.
- **A larger machine costs the same.** Computer hours count `max(cpus / 4, GiB / 8)` times the time awake (`deploy/first-node/RUNTIME-COMPUTER-HOURS.md`): the 256-sample frame is 0.19 computer hours on 2 CPUs and 4 GiB and 0.17 on 8 CPUs and 8 GiB.
- **Idle time is what costs.** A task machine sleeps after an hour without use: on 8 CPUs that hour is 2 computer hours, more than forty 64-sample frames. Hence `machine_stop` when the work is done.
- **The room costs nothing.** The real room renders as fast as the dark world: what makes a frame look real is its light and its materials, not samples or processors. 64 samples with the denoiser are enough for a still.
- **A large machine may wait or be refused.** Its CPUs count in full against its node's budget while it is awake, beside every other awake machine; when no node has room it waits in line, and a size above every node's largest machine is refused at once. The words name 8 CPUs and 8 GiB and say to start a smaller one instead of waiting, after deleting the one in line: left there, it would start by itself when room comes, unused and counted.
- Not measured: more than 10 threads (the test machines have 10 vCPUs), and a company machine itself.

| Qorpera | `npm ci` and `npm run test:hosted-db` inside the machine: 471 migrations and 137 tests passed |
| Delete | A running `sleep 3600` stopped with the machine, which was deleted and released |

Nested KVM also works inside a machine (`/dev/kvm`, `svm` on every CPU). Docker's default AppArmor profile blocks remounting `/sys/fs/cgroup` read-write, so a container that runs systemd needs `--security-opt apparmor=unconfined` (the test machine's note).

### A coding session's work

A coding session's work is in the company folder, at `/company/code/<owner>/<name>/worktrees/<workerId>`, which a machine whose starter may read all of the folder sees (deploy/first-node/RUNTIME-FOLDER-TEST-MACHINES.md). A machine has no repository disk and is tied to no node: until migration `20260930506000` (F3 6e-1), `machine_start` with `repositoryWorker` attached the session's repository folder read-only at `/mnt/repository` and placed the machine on the node whose NAS held that session.

## Install on a node

The steps below need root on the node and a maintenance window. The coordinator runs them in a release cut.

1. **Package the guest** from a checkout whose `npm run check` passes:
   `node scripts/package-machine-guest.mjs --out /task-owned/machine-guest --folder-program <built qorpera-folder>`. The helper must stay under 64 KiB, because the executor re-reads it to check its pin.
   - The folder program is the build `deploy/folder-service/folder-program-linux-x64.json` records (`node scripts/build-folder-program.mjs`). The package refuses any other bytes, and the image script pins the same sha-256.
2. **Create the project** on the node, with the agent exit installed and healthy (`deploy/agent-exit/README.md`, "Switching a node on"):
   - `lxc project create machines -c features.images=false -c features.profiles=false`
   - The storage pool is the node's VM pool (ZFS), for example `qorpera-vm`. Machines get their own root disks.
   - The executor's unit joins the group `qorpera-agent-plug` and may write the exit's client map (`deploy/coding-worker/qorpera-coding-executor.service`).
3. **Build the image** in the node's image build space: the project and network of the observer policy's `buildSpace` (on node 2, `qorpera-build` and `qorpera0`).
   `deploy/machine/build-machine-image.sh /task-owned/machine-guest <node-version> <node-sha256> qorpera-build qorpera0 qorpera-vm machines > image-build.json`
   - The builder is a build machine there (no profiles, its own 10 GiB root, the smallest machine disk, the isolation NIC, `boot.autostart=false`, `user.qorpera.image_builder=true`), so the node stays `ready` while it builds. It takes 4 CPUs and 8 GiB of the space, and the script refuses while the space holds anything else, such as a runtime image build.
   - Anywhere else the builder is an unregistered instance and the node turns unavailable until it is deleted. The script refuses the machines project.
   - The image ends up in the store the `machines` project uses (the default project's, since `machines` has no images of its own). A build space that shares that store, as node 2's does (`features.images=false`, deploy/first-node/NODE-BUILDER-COEXISTENCE.md), publishes straight into it. One with its own store has the image exported and imported with the same fingerprint, and keeps no copy.
   - The builder joins the build space's network, not the agents' bridge, to fetch packages and Node.js. It holds no credential and is deleted when the build ends.
   - The builder NIC's IPv6 filtering needs the `br_netfilter` module, which nodes load at bootstrap (`deploy/first-node/bootstrap-lxd-host.sh`).
   - Take the Node.js tarball's sha-256 from nodejs.org's `SHASUMS256.txt`.
   - The image has the toolbox every Qorpera machine has (deploy/first-node/RUNTIME-FOLDER-COMPANY-MACHINES.md): npm, npx, `tsc`, `tsx`, pip, uv, mise, ripgrep, fd, jq, sqlite3, curl, zip, unzip and LibreOffice (without its desktop parts), from apt except uv and mise (their releases, pinned by sha-256 in the script; mise installs any other language or version in the user's home, without root) and `tsc` and `tsx` (npm, pinned by version). The script's own checks run every toolbox command with `--version` (unzip has none: `-v`).
   - Nothing in the image updates itself. apt's timers and services are masked, and so is fwupd's firmware refresh: `fwupd-refresh.timer`, `fwupd-refresh.service` and `fwupd.service`, which the refresh starts over D-Bus. Such work counts as busy like any other, so the refresh kept a quiet machine awake (C8 MA-5b). The script's checks refuse an image where a fwupd timer, a fwupd unit that starts at boot, or a fwupd bus name could still start anything.
   - It also has `fuse3`, the folder program at `/opt/qorpera-folder/qorpera-folder` and its unit `qorpera-machine-folder.service`, and an empty `/company`. Nothing starts the unit at boot: the guest helper's `folder-mount` starts it once the host hands the machine a view, and starts it again on a newer view, which replaces the one before (F3 step 6, deploy/first-node/RUNTIME-FOLDER-TEST-MACHINES.md).
4. **Compute the policy.**
   `node scripts/machine-provider-policy.mjs image-build.json <executor owner> <node id> <machine-id sha256> <coding providerId> <max cpus> <max memory GiB> <machine disk GiB> machines <pool> qagent0`
   - The provider id must be the coding executor's `vmPolicy.providerId`, because command routing reuses the coding peers.
   - The largest machine must fit the node's budget. `qorpera_enroll_runtime_node_provider` refuses more.
   - The machine disk is what the pool may promise machines in total (ZFS volumes are sparse, so leave the node's own VMs their share).
   - After a new image, keep the earlier helper's sha-256 in the block's `previousHelperSha256s` while any placement from that image still holds room (running or starting). Those machines keep their lease, and they wake fresh from the new image after they sleep or are stopped. Always-on machines keep the old helper needed until someone stops them; the block takes at most 16 earlier helpers. A helper from before the one idle rule (observation v1) cannot report busy commands: the executor refuses its observation, so such a task machine sleeps after the idle delay and wakes fresh.
5. **Configure the executor.**
   - Add the printed `machines` block to the executor's configuration (`qorpera.coding-executor-service/v7`).
   - Restart the executor while it is drained.
   - Run the two printed SQL statements as service role.
   - An executor without a `machines` block makes no machines, but still forwards machine commands to its peers.
   - Agents see the machine tools only once some executor is enabled and an enrolled machine provider holds its policy (`qorpera_company_machines_available()`, asked at the start of every company run). Until then they are not offered at all, so the SQL statements above are the switch that turns machines on for agents, and disabling every executor turns them off again. Running machines keep their leases either way.
   - The switch is global. Every identity host with a coding ingress then offers the tools, and its commands go through that node's own coding executor. So enable the first machine executor only after every coding executor runs `qorpera.coding-executor-service/v7`.
6. **Roll the observer.** Roll the node observer build that knows `qorpera.lxd-company-machine/v2` before the first machine. An older observer marks the node unavailable when it meets one. (The move from v1 to v2 rolls the database first: deploy/first-node/RUNTIME-FOLDER-TEST-MACHINES.md, "Rollout".)

A deleted company's machines are deleted with it: `qorpera_stop_company_work` (company deletion) sets each one `deleted` under the company's fence and machines lock, clears who would be woken, and each node's executor deletes and releases its placements. The purge waits for their allocations like any other (migration `20260928269360`).

Rollback:
- First stop and delete the node's machines with the agent tools or the members' action, while an executor is still enabled. Disabling the last one also takes the machine tools away from agents, and no client offers the members' action yet. Their allocations are released only by the executor's proven delete.
- Then `qorpera_configure_machine_executor(owner, sha, false, policy, diskBytes)` stops admission. Machines still running keep their leases.
- A node gone for good: disable its executor, then run `qorpera_abandon_machine_executor(owner, sha)` as service role once its disks are known to be gone. It releases the node's placements; their machines start fresh elsewhere on the next wake, and deleted ones finish.
