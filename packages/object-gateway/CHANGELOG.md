### Breaking Changes
- A member's chat images are folder-v2 files (`supabase/CLIENT-CONTRACT.md` "Chat images"; needs migration `20260930260000` first). The routes and their answers stay: `PUT /v1/member-session-attachments/upload/<sessionId>/<clientInputId>/<sha256>` begins the image with the member's token (`qorpera_room_image_begin`, which names the company's folder and the image's path), asks the writer check who the member is (`qorpera_member_folder_writer`), takes exactly the bytes begun, stages them as the platform (`PlatformFolderWriter`) and saves them for that member with the service key (`qorpera_room_image_commit`). `GET /v1/member-session-attachments/input/<sessionId>/<inputId>/<sha256>` asks `qorpera_room_image_download` with the member's token, reads the file by its manifest as the platform (with the Storage copy as fallback) and asks again before it answers. A refusal keeps the database's meaning: 42501 is 403, 22023 400, 23505 (an input id another member holds) 409, 54000 (the input's limits) 413, and 55000 (no folder, the file gone, a paused company) 423. `MemberCompanyRpc` and `MemberCompanyPublisherRpc` drop the snapshot-v1 functions (`qorpera_begin_member_session_attachment_upload`, `qorpera_authorize_member_session_attachment`, `qorpera_stage_member_session_attachment`), and `MemberCompanyFileOptions` drops `replication`, which only this route used; the route takes `MemberSessionAttachmentOptions`. A member authority RPC's 54000 is 413 now, not a 500 that opens the member circuit. `memberFolderWriter` (the writer check's answer) is exported. Rolls with the next object gateway release.
- `/v1/native-company-objects` is gone (legacy removal, step C; migration `20260930190000`): it served only snapshot-v1 companies' run objects (the native host's object store and the Company Computer's captures, file imports and exports). Its three authority methods (`authorizeNativeUpload`, `confirmNativeUpload`, `authorizeNativeDownload`), the `nativeObjects` option's `authority`, and the `code: "lock_conflict"` retry hint in its 409 answers go with it; `nativeObjects` keeps its token, and its `folder` is now required, for `/v1/folder-objects`. Rolls with the next object gateway release.
- `/v1/folder-objects` serves a native host's request only after it proves its run's lease (G2-6a; migration `20260930152000`; `deploy/first-node/RUNTIME-NATIVE-HOST-KEY.md` "G2-6"): the request sends `x-qorpera-identity: job.<job id>.<lease token>`, and the gateway asks `qorpera_native_binding_proven` before any other check of its binding. A missing or malformed holder is 401, a refused proof 403, and the value never reaches a log or a reply. `/v1/native-company-objects` keeps its old check until G2-6c (it also serves the Company Computer's captures).
- `CompanyBootstrapProvisioner` and `CompanyBootstrapOptions` (`company-bootstrap.ts`) are gone (legacy removal, step C): nothing has constructed the provisioner since the maintenance loop stopped running it, and new companies are created by the folder creation loop (`CompanyFolderCreator`). `MemberCompanyPublisherRpc` drops `qorpera_claim_company_bootstrap`, `qorpera_stage_company_bootstrap_object` and `qorpera_finalize_company_bootstrap`, so no gateway code calls them. The running gateway does not change.
- `/v1/member-company-file/` is gone (legacy removal, step C): a member's snapshot-v1 edits, uploads, proposals and their reviews. The database already refuses them for a folder-v2 company (the legacy path actor's `55000`, and the command and approval actors' `0A000` from migration `20260928259430`), and every company is folder-v2. Such a request now gets 404, and its preflight 403. The member CORS policy drops the route and no longer exposes `x-qorpera-plan-sha256`, and the observation operation `file_request` is no longer started. `serveMemberCompanyFile` itself stays exported until the next step removes its file. Rolls with the next object gateway release.
- `member-company-file.ts` is gone, with `serveMemberCompanyFile` and `MemberCompanyHeadConflict` (legacy removal, step C): nothing has reached them since `/v1/member-company-file/` went. `MemberCompanyFileOptions`, which the export and session attachment routes still take, moves to `member-company-authority.ts` without its `observation`, which only the old route read. `MemberCompanyRpc` and `MemberCompanyPublisherRpc` drop the old route's eight member and eight publisher functions, so no gateway code names them. A 409 with code `PT409` is now a plain 409 like any other: its body is cancelled unread, and the status is unchanged. Rolls with the next object gateway release.
- `/v1/member-company-objects/` and `/v1/member-company-snapshot-objects/` are gone (legacy removal, step C): a member's reads of a snapshot-v1 company's path versions and snapshots. Their only client, cloud-client's `CloudMemberCompanyFileReader`, is gone, and every company is folder-v2, whose member reads use `/v1/member-folder-objects/`. `member-company-objects.ts` goes with them (`serveMemberCompanyObject`, `MemberCompanyObjectAuthority`, `MemberCompanyObjectIdentity` and `AuthorizedMemberCompanyObject`), and so do the `memberObjects` option and `SupabaseObjectAuthority.authorizeMemberCompanyObject`, so no gateway code calls `qorpera_authorize_member_company_path_object` or `qorpera_authorize_member_company_snapshot_object`. Such a request now gets 404, and its preflight 403. The member CORS policy drops the routes, and with them the `x-qorpera-company-path` request header. Rolls with the next object gateway release.
- The member observations take only `object_read` and `command_submit` (legacy removal, step C): `file_request`, `command_status`, `command_content`, `command_review`, `proposal_content` and `proposal_review` named the snapshot-v1 member routes, which are gone, and no gateway code starts them. `MemberObservationOperation` narrows to the two names; `MemberCompanyObservations.start` and a span's `operation` drop any other name (counted in `dropped`), and the operator query refuses one with 400. Rolls with the next object gateway release.

### Added
- Git on the mount (F3 step 5d; `deploy/first-node/RUNTIME-COMPANY-FOLDER.md` §6, needs the core's git leases of 5b): in a code area's `repo.git`, an exclusive create of a ref's, `HEAD`'s, `packed-refs`' or `shallow`'s lock takes the core's lease (`EEXIST` while another session holds it, `EPERM` when refused) and brings the view up to the lease's versions before the open answers; the lock's rename onto its file publishes the file, its log and the session's new objects in one call (`EBUSY` when the file changed since), and the lock's removal publishes a branch's deletion or a rewritten log, or gives the lease back. A command's last boundary gives back every lease its view still holds; no lock file is ever published. The session's own `config`, `hooks/**`, `info/**` and `config.worktree` and writes of `objects/info/alternates` answer `EPERM`, shared files written without their lock too; the company's code host (a `code_host` view, marked `codeHost` in the hello answer) writes and publishes those files as plain files, the copies sessions seed theirs from. An object or objects folder another session published first is saved as it is. A file this view published keeps the time it showed while pending, until another version replaces it. A write opened as a draft (`draft`) joins the view only when its close lands it, and a close with `discard` gives its handle up (a draft's leaves nothing): the mount writes the caches it moves into the folder as drafts, so a move it gives up leaves no file behind.
- The folder service publishes a running command's view after a quiet period (F3 slice 4b-2, the contract's 14 October 2026 amendment, item 3; `deploy/first-node/RUNTIME-FOLDER-SERVICE.md` "Step 4b"; needs migration `20260930342000`, which opens a networked command's view as an offline one's). A `computer_shell_command` view now publishes 2 s after its last change while its machine holds it, as a desktop's does, each boundary releasing its reads first, as well as when asked. Its final ends a quiet period still to come, so a command that ends inside it publishes once, final; a view no machine holds publishes on no quiet period, kept or let go, nor does a change or a quiet period that waited behind a boundary while its last connection left.
- Desktop folder views transfer in place to an authenticated successor on the same company machine (F3 4c-3). The service fences admitted work, carries pending files, open handles, unreleased reads and byte roots, restages files under the successor's upload scope, and replays uncertain commits with their original actor and key. Closed desktops retain pending state for a fixed minute. Protocol-3 handles survive stream loss; a separate publisher abandons orphan handles only while holding the program's private lifetime lock, and a writable mount, which holds it from its start, says so on one IO hello before it serves a file, so what a crashed program left open goes back to its last fixed save when systemd restarts it. A desktop view kept only for files still open publishes what was closed when its last connection leaves; the open files wait. The Rust program retains accepted-view proof across primary-file replacement and crashes, fences stale connections by epoch, and preserves its journal, version map and FUSE descriptors. Helper activation remains 4d; no live deployment in this slice.
- The folder service releases a company machine's reads (F3 step 4c-1, `deploy/first-node/RUNTIME-FOLDER-SERVICE.md` "Step 4c"; the log's rules in `RUNTIME-FOLDER-COMPANY-MACHINES.md` "Reads"). Protocol 3: on a writing connection the machine sends its read log's entries (`I`, `{log, reads: [{seq, path, version, authority?}], lost?}`, consecutive) and hears how far the view took them and how far the core has them (`i`, `{log, taken, released}`). A core view takes writes only from protocol 3, so its hello says `readOnly` to a protocol-2 machine; an operator mount's view writes from protocol 2 as before, and its reads count as released. Each boundary first releases the reads the core does not have yet (`FolderCore.releaseReads`, `qorpera_folder_record_release`), the view as the actor, at most 10,000 at a time, each with the version the view showed or none and its receipt or none; one with no answer, or refused, is asked again under the same id. A member-held view's release (22023) counts as released. A refused release refuses the boundary, with nothing published: `unreadable` ("A released read is no longer readable"), `run_ended` ("Run is unavailable"), `denied` (any other 42501), `stopped` or `invalid`. A log the machine sent `lost` refuses every later boundary of the view (`unproven`). A desktop's view whose last boundary had no answer, or was refused by the pause or the run check, is kept and renewed when its last connection leaves, with its quiet period ended and its refused change set pending, until a later publish from its machine hears another answer; a command's view is kept unless its last boundary was refused for good. A boundary still running when the last connection leaves, or one that runs after, decides again as it ends: the view stays kept, or is let go (renewed once with null, then dropped); the idle sweep leaves it alone until then. A command's view that closed while its final had no answer takes `I` and keeps none of it (`taken` and `released` are the batch's last entry), so a dead program's last call can hand its log over and then ask the final again.
- The folder service serves shell commands' views (F3 step 4b, `deploy/first-node/RUNTIME-FOLDER-COMPANY-MACHINES.md`; needs migration `20260930183000`). A `computer_shell_command` view is served only to the company machine named after its allocation, read-write, and published only when its machine asks, or before a change that needs what is pending published first (4b-2 adds a quiet period, above). A publish may say `final: true` (only a command's view; else `BAD_REQUEST`): everything pending as one change set, or an empty one, committed with the view actor's `final`, after which the core closes the view and the report says `closed`. A path still open for writing holds the whole final back. A final with no answer is asked again, final, under its key and as the actor it was asked as; a view a renewal closes while the final is asked or after (the final may have closed it) stays for that, joined only with its pass and taking nothing else (`VIEW_CLOSED`), and the replay's answer is the report; a replay refused did not close the view, which goes (`VIEW_CLOSED`). A change set the core refuses whole (the command has ended, so it saves only the final; the pause; over 1000 units) stays pending for the final, and the report says `refused` with the reason (`denied`, `stopped` or `invalid`); so does any view's report, with `commitId` null where it was `""`. Its renewals never say it has changes unsaved, and it is kept, renewed and with what it has pending, when its last connection leaves. `FolderCore.commit` takes a `CommitActor`.

### Changed
- The maintenance loop no longer runs the legacy company bootstrap (`CompanyBootstrapProvisioner`): new companies are created at the founding table by the folder creation loop, so a legacy bootstrap job stays queued (lobby hardening, from #776's review).

- The replication reconciler reads folder GC's conflict (`qorpera_authorize_profile_object_replication` answering QRC01 409 with the folder core's "being collected" message, for an object folder GC holds) as a lock conflict: the entry stays pending instead of `blocked`, and the database circuit is left alone. snapshot-v1's cleanup fence, which also answers QRC01, keeps its 409, and no other RPC's answer changes.
- The folder route answers the folder core's storage allowance refusal (23514, which PostgREST sends as 400) with 413, so the runtime can tell a full company from a failed request.

### Fixed

- A lock conflict on the native object route says so in its error body: a 409 from a serialization failure, deadlock or lock timeout (40001, 40P01, 55P03) answers `{ "error": …, "code": "lock_conflict" }`. The database call that answered rolled back, and that route's request (content-addressed bytes, then read checks and one catalog upsert) may be sent again whole; the runtime's native object transport retries on it. No other refusal carries a code: a stop (423), a GC write fence or a deletion in progress (409), a denial or an unavailable dependency keep `{ "error": … }`, and so does every other route, including member Company File routes, whose earlier steps (a review before its apply) may have committed.
- One company's database state no longer refuses every company. PostgREST answers SQLSTATE classes 40 and 55, and 57014, with HTTP 500, which the database circuit counted as an outage for its cooldown (~5 s). The native and member object RPCs and the member Company File RPCs now read PostgREST's error code, with the folder core's codes (#560): a stop (55000) is 423, a serialization failure, deadlock or lock timeout (40001, 40P01, 55P03) 409. A statement timeout (57014) is 503 and opens the circuit only when no other call succeeded while it ran. Other 500s, 502/503/504, refused connections and the gateway's own deadline still open it. Profile, replication and deletion RPCs keep every 500 a dependency failure. The folder core's byte RPCs (#560) now use the same reading, so their statement timeout follows the same rule; their storage allowance (23514) stays 413 (#582), and their other 400s stay 400.
- A caller that gives up no longer opens the member Company File circuit. When the presence route passed its 2.5 s deadline, or a member closed the tab, the aborted database call counted as the database failing and refused every company for the cooldown. Only the circuit's own deadline and real upstream failures count now.
