# Changelog

## [Unreleased]

### Added

- The member commit route follows a saved commit up at once (folder core C4, P34a-2; F2's P15): it calls `qorpera_folder_follow_up_commit(environment, commit)` with the service key, one subject a call while it answers `more`, at most 8 calls and 3 s before the answer goes back, so a member's new agent has its grants, connectors and first run when the web reads it again. The follow-up has its own database client (its own circuit), so a failing follow-up never refuses members' commits, and without that client there is none. It starts only within 20 s of the request's start, so the answer stays inside the member gateway's 25 s, and the member's in-flight slot is freed before it. A best effort: any error ends it, and before P15 the function does not exist.

- Added a member's change sets to a folder-v2 company (folder core C4, slice P34a; `deploy/first-node/RUNTIME-COMPANY-FOLDER-C4-MEMBERS.md` §5): `POST /v1/member-folder-commits/<environmentId>` with the member's own token takes `{schema: "qorpera.member-folder-commit/v1", operationKey, units}` (write, mkdir, new folder, delete, move; text only, at most 64 KiB a file, 512 KiB and 32 files a request). The database answers the member's own actor for the token (`qorpera_member_folder_writer`); the route stages each file and commits as that member with the service key, each state file with its parse from the shared parser, and answers the core's commit answer as it is. The member's key goes as `member:<userId>:<key>`, outside the platform writers' keys. A unit at or under `human-tasks/` is refused (403) until P31, and a member has one change set in flight at a time (429). Member commits use their own database client. `PlatformFolderWriter` takes the actor as an option (the platform when left out). The member company gateway and the member CORS policy take the route.

- Added company creation's worker (C2-create, P14b; `deploy/first-node/RUNTIME-COMPANY-FOLDER-CREATION.md` §2 step 3, §5), off unless `QORPERA_COMPANY_FOLDER_CREATOR=1`: it claims a creation a founding table started, builds the seeded tree with the ids the creation row holds, stages each file as the platform through `PlatformFolderWriter`, and calls `qorpera_folder_company_create` once. The database sorts the answer; the worker releases with a back-off, or fails a claim only when its seed tree is refused or staging refuses its bytes (`stage_invalid`). Its own database client and loop.

- Added the vault's connection-file writer (core C3, P22b; `deploy/first-node/RUNTIME-COMPANY-STATE-FILES.md` §2 "How it is written"), off unless `QORPERA_CONNECTION_FILE_WRITER=1` (worker id `QORPERA_CONNECTION_FILE_WORKER_ID`, else random). Every 15 s, in a loop of its own (one drain at a time, 60 s at most, its own database client), it claims up to ten due company connections (`qorpera_claim_connection_file`, migration `20260930006000`), brings each `connections/<name>.md` of a folder-v2 company to what the vault says (a new file by the canonical writer; an existing one keeps every byte but the settings that changed, so the company's text below them stays; deleted once the account is disconnected or closed), stages its bytes as the platform in this gateway's store, commits one unit as the platform with the claim's operation key and the version it read, and finishes the claim, or backs it off with a code (`version_changed` when a member saved meanwhile). A claim carrying anything outside the allow-list of settings is refused unread; nothing it writes or reports holds a secret. `scripts/test-object-gateway-connection-files.mjs` runs it against a real database in the hosted-db step.

- Added a member's byte route for folder-v2 companies (folder core C4, slice P27b; `deploy/first-node/RUNTIME-COMPANY-FOLDER-C4-MEMBERS.md` §2): `GET /v1/member-folder-objects/<environmentId>/<sha256>` with the member's own token serves one manifest or chunk, checked by `qorpera_member_folder_object` before and after the NAS read (with the Storage copy as fallback), and answers `x-qorpera-access-mode: live-path-authority`. The member company gateway and the member CORS policy take the route. Inert until a folder-v2 company exists.
- Folder GC removes bytes with no catalog row (core C1d-2c part 1, slice P12, migration 20260930009100): a folder-v2 object whose put was never confirmed leaves a `blocked` journal entry and the gateway degraded. The scan checks each blocked entry under the object's lock with `qorpera_folder_gc_catalog_state`; once the object has been missing (no catalog row, no upload intent listing it) at every check, 10 minutes apart (or as soon after as the scan comes back to it), for 24 hours, its NAS file and replica are removed and the entry dropped. Entries of catalogued objects, of objects an intent still lists, and of companies folder GC does not serve (snapshot-v1, mixed, being deleted or purged) stay as they are. This pass has no switch: apply the migration before deploying the gateway.

- Added folder GC's unlink lane (core C1d-2b, slice P11): `DELETE /v1/folder-gc/<profileId>/<sha256>` on the control token with the GC lease (`x-qorpera-gc-lease-id`), which the artifact GC worker's folder phase calls for each object the folder core's claim marked. Under the object's journal lock it begins the unlink, moves the NAS file into `<root>/.quarantine/<profileId>/<sha256>.<leaseId>` (or, with no NAS file, writes a marker that the Storage replica is the only copy), removes the replica, and asks the folder core to finish: `removed` drops the quarantined file (and the replica, in the marker case) and the object's journal entry, `restore` writes a `replicate` entry and puts the file back. It answers `{ "outcome": "removed" | "restored" | "stale" }`, 503 when the NAS lanes are busy, 409 on a lock conflict. A scan before every reconcile settles what an interrupted lane left in quarantine, as the folder core's quarantine state says. Nothing calls the lane until the worker's folder phase is switched on.

- Added the folder core's byte route for folder-v2 runs (core C1d-1b): `/v1/folder-objects/<environmentId>/<sha256>` on the native credential with the run's binding. A put names its upload intent (`x-qorpera-upload-intent`) and is authorized by that intent alone, then stored, confirmed and replicated as native objects are; a get is allowed when an entry or path version the run may read references the hash, checked before and after the NAS read. The folder core's stop (55000) is answered 423 and its lock conflicts (40001, 40P01, 55P03) 409, instead of PostgREST's 500, so neither opens the gateway's database circuit for every company. A read that meets a busy NAS lane when Storage has no copy yet (replication pending) is answered 503, which the runtime asks again, rather than Storage's miss. The native route's token and binding checks are now shared helpers; its behaviour is unchanged.

- Added a bounded member presence endpoint that verifies native signatures and intersects current member/native path permissions in separate authority transactions. Responses contain display metadata only, with explicit browser CORS and no native bindings or routing keys.

- Added member-authenticated shared export downloads with exact asset/hash selection, completed receipt and audience checks, bounded binary verification, live authority rechecks and narrowly scoped browser CORS.

- Added bounded member binary upload admission with immutable source/manifest/chunk identity, current SQL authority and existing live publication or protected human review. Pending file downloads assemble and verify chunks with authority rechecks and exact plan identity.

- Added an explicit browser-origin allowlist for member Company File reads, edits, reviews and session attachments, with route-specific preflight checks and no browser access to private gateway routes.
- Added bounded, operator-only Company File request observations with canonical command/read linkage, timing, safe outcomes and available object-byte counts. The in-process window exposes restart/eviction gaps and excludes paths, file contents, tokens and raw errors.

### Changed

- The replication reconciler reads folder GC's conflict (`qorpera_authorize_profile_object_replication` answering QRC01 409 with the folder core's "being collected" message, for an object folder GC holds) as a lock conflict: the entry stays pending instead of `blocked`, and the database circuit is left alone. snapshot-v1's cleanup fence, which also answers QRC01, keeps its 409, and no other RPC's answer changes.
- The folder route answers the folder core's storage allowance refusal (23514, which PostgREST sends as 400) with 413, so the runtime can tell a full company from a failed request.

### Fixed

- A lock conflict on the native object route says so in its error body: a 409 from a serialization failure, deadlock or lock timeout (40001, 40P01, 55P03) answers `{ "error": …, "code": "lock_conflict" }`. The database call that answered rolled back, and that route's request (content-addressed bytes, then read checks and one catalog upsert) may be sent again whole; the runtime's native object transport retries on it. No other refusal carries a code: a stop (423), a GC write fence or a deletion in progress (409), a denial or an unavailable dependency keep `{ "error": … }`, and so does every other route, including member Company File routes, whose earlier steps (a review before its apply) may have committed.
- One company's database state no longer refuses every company. PostgREST answers SQLSTATE classes 40 and 55, and 57014, with HTTP 500, which the database circuit counted as an outage for its cooldown (~5 s). The native and member object RPCs and the member Company File RPCs now read PostgREST's error code, with the folder core's codes (#560): a stop (55000) is 423, a serialization failure, deadlock or lock timeout (40001, 40P01, 55P03) 409. A statement timeout (57014) is 503 and opens the circuit only when no other call succeeded while it ran. Other 500s, 502/503/504, refused connections and the gateway's own deadline still open it. Profile, replication and deletion RPCs keep every 500 a dependency failure. The folder core's byte RPCs (#560) now use the same reading, so their statement timeout follows the same rule; their storage allowance (23514) stays 413 (#582), and their other 400s stay 400.
- A caller that gives up no longer opens the member Company File circuit. When the presence route passed its 2.5 s deadline, or a member closed the tab, the aborted database call counted as the database failing and refused every company for the cooldown. Only the circuit's own deadline and real upstream failures count now.
- A lock conflict (40001, 40P01, 55P03) on a profile, replication, deletion or migration RPC is still 503 to its caller, so the replication reconciler keeps the object pending instead of blocking it, but it no longer opens the database circuit for every company. With migration 20260928339630 the native and member object RPCs and the replication RPCs end a lock wait after 2 s with 55P03, under the gateway's 5 s deadline, instead of running into that deadline.
- Return non-retryable HTTP 412 for stale Company File versions, context, policy and review preconditions, preserving authorization and receipt replay without managed API transaction-retry stalls.
- Resolve authoritative manifest byte counts before Company File bootstrap reads, preserving exact-size and hash validation across NAS reads and Storage fallback.
- Authenticate configured JWT service credentials on gateway publication, object authority, and Storage requests without replacing member identity or treating opaque API keys as bearer tokens.
