### Breaking Changes
- The gateway no longer serves raw object reads and uploads by hash, read leases and their revocation route, the verifier token, or the member file export route (legacy removal, step E3). Migration `20260928259430` already refuses raw reads, their read lease and raw uploads for a folder-v2 company, and every company is folder-v2. `GET` and `PUT /v1/profile-objects/<profile>/<sha256>` now answer 405; `DELETE` stays as it was for folder GC and erasure. `POST /v1/read-leases/revoke` and `GET /v1/member-file-exports/` now get 404, and the export's preflight 403; the export route is also gone from the member-company-gateway bridge. `/healthz` drops `readContinuity`, and `/readyz` always needs a healthy API (the NAS alone no longer counts for read leases). `member-file-exports.ts` (`serveMemberFileExport`) and `read-lease.ts` (`ObjectReadLeases`) go, and so do `MemberCompanyFileOptions`, `qorpera_member_file_export_source` in `MemberCompanyRpc`, the `verifierToken`, `revocationToken` and `readLeases` options, `ObjectGatewayReplication.upload`, `AuthorizedObject`, `SupabaseObjectAuthority`'s `authorizeUpload`, `authorizeDownload`, `authorizeServiceDownload` and `readLeaseSeconds`, and `confirmUpload` from the `ObjectGatewayAuthority` interface (the class keeps it for `migrate`). The gateway journal takes only `pending/` keys. `QORPERA_OBJECT_GATEWAY_VERIFIER_TOKEN`, `QORPERA_OBJECT_GATEWAY_REVOCATION_TOKEN` and `QORPERA_OBJECT_READ_LEASE_SECONDS` are no longer read. The SQL functions behind these routes stay until a later SQL slice. Rolls with the next object gateway release.
- A member's chat images are folder-v2 files (`supabase/CLIENT-CONTRACT.md` "Chat images"; needs migration `20260930260000` first). The routes and their answers stay: `PUT /v1/member-session-attachments/upload/<sessionId>/<clientInputId>/<sha256>` begins the image with the member's token (`qorpera_room_image_begin`, which names the company's folder and the image's path), asks the writer check who the member is (`qorpera_member_folder_writer`), takes exactly the bytes begun, stages them as the platform (`PlatformFolderWriter`) and saves them for that member with the service key (`qorpera_room_image_commit`). `GET /v1/member-session-attachments/input/<sessionId>/<inputId>/<sha256>` asks `qorpera_room_image_download` with the member's token, reads the file by its manifest as the platform (with the Storage copy as fallback) and asks again before it answers. A member authority RPC's 54000 is 413 now, not a 500 that opens the member circuit. `memberFolderWriter` (the writer check's answer) is exported. Rolls with the next object gateway release.

Its three authority methods (`authorizeNativeUpload`, `confirmNativeUpload`, `authorizeNativeDownload`), the `nativeObjects` option's `authority`, and the `code: "lock_conflict"` retry hint in its 409 answers go with it; `nativeObjects` keeps its token, and its `folder` is now required, for `/v1/folder-objects`. ### Added
- The folder service checks what a coding machine saves against its member's secret values (5j-5 (a), C4; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md` "Masking"). The coding executor sends each machine's values as keyed hashes over the control socket: `{op: "secrets", machine, key, values: [{length, start, whole}]}` (a 32-byte key, values of 8 bytes to 32 KiB, at most 4096), answered `{secrets: {machine, values}}`; each set replaces the one before, in memory only, so the service never holds a value. A file's bytes, a new name or a new link's target that carries one in its exact form is refused and kept on the machine, and what needs a refused change (a change into the path a refused move would free, or into a folder it would make) waits with it; a git change whose ref, log or loose object as stored carries one is refused whole (`NOT_PERMITTED`). A file staged under older values is checked again for new ones. A refusal, report or log line never names a value, and a change not checked yet is counted, not named. Until a coding machine's first values come, nothing of it is saved (its git changes are `BUSY`), so this ships with the executor half. The control socket's line limit is 320 KiB, for a full set (4096 × 66 bytes).
- A rename across a cache's edge works as an editor's atomic save needs (contract amendment item 8, MC2b; `deploy/first-node/RUNTIME-FOLDER-MACHINE-CACHES.md` "Across the edge"): in the folder program (`crates/qorpera-folder`), a cache file renamed onto a name of the folder where no cache goes is written into the view as a draft, the session's save of the file it replaces or a new file, with the cache file's executable bit (set each time, as the folder's file may have changed its bit since the feed last told of it), and leaves the machine's disk. A cache file still open for writing is waited for up to a second; one still open then, and a rename onto a file open for writing here or onto anything but a file, is `EXDEV`, onto a folder `EISDIR`, and `RENAME_NOREPLACE` onto a file `EEXIST`. A new file the view made that no boundary has published, renamed onto a cache name, moves to the machine's disk and leaves the view's changes. The program notes such a file when it makes it where the folder's listing has none, or when a cache file is renamed onto a new name, and the note follows the file's own renames. It drops the note at any change the feed tells of at or above the path, when the feed comes back or the view lists again, and at a rename of a folder above it (the folder service gives the files it takes along new versions). At the rename the folder service must list the file as the mount's own save, with no authority of its own, and nothing may have it open for writing. A removal whose answer is lost is asked for again for up to five seconds; a file whose removal is still not known stays in the cache as well, and the rename is `EIO`, so its bytes are never lost. Any other rename across the edge is `EXDEV`, so `mv` copies. An entry the kernel still has for a file such a rename moved is looked up again (`ESTALE`) and finds the file at its new side. `deploy/folder-service/folder-program-linux-x64.json` records the new build, and the guest installer's and the machine image build's `EXPECTED_FOLDER_PROGRAM_SHA256` pin it.
- What git ignores in a worktree is a cache (contract amendment item 8, MC2a; `deploy/first-node/RUNTIME-FOLDER-MACHINE-CACHES.md` rule 4): in a code area's worktree the folder program (`crates/qorpera-folder`) keeps on the machine's disk a new file or folder that git's ignore rules leave out, read from every `.gitignore` from the worktree's top down to its folder and from the repository's `info/exclude` (git's rules: negation, folder patterns, anchors and `**`; `ignore.rs`), a `.gitignore` git ignores (a cache itself) included; a machine's own global ignore file does not count. A pattern too deep or too long to match within the program's bounds leaves nothing out, and a negated one takes the path back. `out` is a cache there only when git ignores it. A path the worktree's index tracks is never a cache, nor one in a `.git` folder; a folder made where the index tracks a file of that name is not tracked. A changed `.gitignore` decides only names made after it: a published file stays published, and its rename or hard link onto a name git now ignores is `EXDEV`. When the index comes to track a cache path (`git add -f`), it moves into the folder and is published at the next boundary: a tracked path whole, and of a folder with tracked paths below it only those, so the rest of its untracked content stays on the machine. A cache file moves into the folder (this move and MC1's) only once the mount has it open for writing nowhere, and an open of it for writing, a change of its attributes or of its name waits until it is there, so nothing written to it is lost. A cache's entries made by a create, `mkdir`, `symlink` or `link` are not kept by the kernel, as its lookups were not already. A cache file renamed onto a published path is still `EXDEV` (MC2b publishes it). `deploy/folder-service/folder-program-linux-x64.json` records the new build, and the guest installer's and the machine image build's `EXPECTED_FOLDER_PROGRAM_SHA256` pin it.
- The machine's caches in every folder (contract amendment item 8, MC1; `deploy/first-node/RUNTIME-FOLDER-MACHINE-CACHES.md` "The rules"): the folder program (`crates/qorpera-folder`) keeps on the machine's disk, never published and unseen by other views, a new folder with a dependency name (`node_modules`, `.pnpm-store`, `.venv` and the rest of rule 2) in any folder, and one with a build name (`dist`, `build`, `target`, `out`, `coverage`, `.cache`) in a folder holding a project file, with all that is in it. Names match exactly, and the rules decide folders only: a file named `build` and a `Build` folder are published. One table (`cache.rs`) holds the names, and a worktree's cache list starts from it (rule 2's names and the build names but `out`, so six more than 5d's list). What the node has at a path wins: a cache whose name the node then has goes, and so do the caches of a folder the node no longer has, when the machine lists the folder above it or makes the folder again. A cache moves with its folder's rename and goes with its removal, and an `rmdir` of a folder holding one is `ENOTEMPTY`. A rename or a hard link between a cache and the folder is `EXDEV`, so `mv` copies; a cache's top renamed to a name that is not a cache is `EXDEV` too, in a worktree as well. Links and hard links inside a cache work, and a boundary does not wait for a cache file. The code host's view keeps no caches. The local layer keeps caches by the node folder they are in, under `caches/`; 5d's `cache/` is taken off the disk when the program starts. `deploy/folder-service/folder-program-linux-x64.json` records the new build, and the guest installer's and the machine image build's `EXPECTED_FOLDER_PROGRAM_SHA256` pin it.
- Git on the mount (F3 step 5d; `deploy/first-node/RUNTIME-COMPANY-FOLDER.md` §6, needs the core's git leases of 5b): in a code area's `repo.git`, an exclusive create of a ref's, `packed-refs`' or `shallow`'s lock takes the core's lease (`EEXIST` while another session holds it, `EPERM` when refused) and brings the view up to the lease's versions before the open answers; the lock's rename onto its file publishes the file, its log and the session's new objects in one call (`EBUSY` when the file changed since), and the lock's removal publishes a branch's deletion or a rewritten log, or gives the lease back; `git pack-refs`' rename of `packed-refs.new` (which `packed-refs`' lease guards) onto `packed-refs` publishes it as a lock's rename does, so a pack that cannot publish stops before it prunes a loose ref; the take of `packed-refs`' lock reads the feed first and the machine then forgets its listings of the loose refs, so git does not pack back a loose ref another session deleted, even before the feed told the machine, and after the publish the lock is git's until git removes it (another create of it is EEXIST). The machine is told its view's own new folder going live (it shows as the same folder) by a name below it that no folder holds, so it lists the folder again and keeps its entry: git working in a new `repo.git` keeps its directory (`getcwd`). The version such a folder showed while pending, which the machine's listing of the folder above keeps, is read as its live one, so a later `rmdir` or move of it does not conflict. After a publish under a lease the view shows live again every new folder above what it published, up to a folder it shows live (a new `repo.git`'s `refs` with `refs/heads`, while its `refs/tags` stays the view's own), so it sees the ref it published. An object or objects folder another session published first is saved as it is. A file this view published keeps the time it showed while pending, until another version replaces it. A write opened as a draft (`draft`) joins the view only when its close lands it, as the view's newest change at the path (over what this view did there since its open, published or not; against the file the view's removal or move would have taken away where a boundary let that go before the close; a file another machine made or changed there since is a conflict, not overwritten; it takes the executable bit of what it lands over), and a close with `discard`, or one that cannot land the draft, gives its handle up (a draft's leaves nothing, and the quiet period then publishes a file it held): the mount writes the caches it moves into the folder as drafts, so a move it gives up leaves no file behind. A test machine's view takes no git lock (`EPERM`): a git publish carries no command credits (F3 6b), so git there changes no shared git file. On a test machine a draft is credited as the file it lands as, and a file a draft held loses, when let go, the credits of the chunks it loses.

### Changed
- The save check reads git's own storage the way git does (5j-5, C4's repo.git path; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md` "Masking"). In a coding machine's save, a file at a loose object's name (`objects/<2 hex>/<38 or 62 hex>`, wherever it is saved) is inflated and its object scanned, its stored bytes too; a file at a pack's name (`objects/pack/pack-<40 or 64 hex>.pack`) is read by the node's git (`index-pack --stdin`, then `cat-file --batch-all-objects --batch`, in a scratch repository) and every object it rebuilds is scanned, deltas resolved. A git change one of whose new objects carries a value is refused whole (`NOT_PERMITTED`), as one whose ref or log does. What git could not read is refused as "could not be checked": a loose object that does not inflate, has bytes after it, no header, more than its header's size, or over 1 GiB; a pack git refuses (broken, cut off, thin, with bytes after it), one over 512 MiB, or one whose objects rebuild more than 64 times its size (at least 256 MiB, at most 4 GiB). Git runs as `prlimit --as=1 GiB` with system and global config ignored, `HOME` the scratch directory, no hooks and no remotes, for at most 30 minutes, one check at a time per service; the scratch directory goes on every exit. A machine with no values inflates nothing. `install-folder-service.sh` refuses a host without `/usr/bin/git` and `/usr/bin/prlimit`. At most 8 pack checks wait for a turn, with at most 2 GiB of packs together (`PackReading.waitingMax`, `waitingBytes`); one past either is refused as "could not be checked" for now (`SecretRefusal.again`) and checked again at the next staging, where any other refusal stays until the file changes. A refusal of anything in a code area's `repo.git` holds back everything else changed in that `repo.git` (`planBoundary`: "it waits for a change that carries a secret value", or the new `WAITS_FOR_UNCHECKED` when all it waits for could not be checked): its other objects, refs, logs, index, a pack's `.idx` and `.rev`, so a git change is never published in part, and a session that ignores the refusal publishes nothing more of that `repo.git` until its way out (`git reflog expire`, `git repack -a -d`, `git prune`) removes the refused objects. A check there that has not ended holds the rest back too, as waiting rather than refused ("it waits for a change whose check for secret values has not ended yet", the new `WAITS_FOR_CHECK`), since the check may yet refuse its file. A removal held back so (a pack's, a worktree's `MERGE_HEAD`) stays the view's when another change is saved meanwhile (`BoundaryPlan.removals`, `PendingView.settle`), and a later boundary publishes it. Files outside `repo.git` are not held. Nor does a git lease (a ref, `packed-refs`, `shallow`) publish or release anything there while it is held: its lock and lease stay until the lock is removed again after the way out, and a lock released with nothing to publish (a rolled-back update) still goes. A file moved, renamed or hard-linked to a name that stores its bytes in a git form its old name did not (git's `tmp_obj_*` or `tmp_pack_*` at its object's or pack's name) is checked again as that form, even when its temporary name was saved at an earlier boundary (`formChanged`); a folder moved so is refused as "could not be checked". A coding view's boundary, and a coding view's close, wait at most 10 s for the checks they start or find running (`FolderServiceOptions.checkWaitMs`), counted from when the boundary was asked (its wait for the view's turn behind another boundary included), inside the 20 s the executor's control client waits: a file whose check runs on (a large pack's) waits with "its check for secret values has not ended yet" (`CHECK_RUNNING`), and a later boundary joins that check rather than starting another, then saves or refuses the file.
