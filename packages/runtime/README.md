# Qorpera headless runtime

Cloud execution services live here. Explicit module subpaths contain native provider execution, durable tool fencing, Company File gateways, wake processing, identity recovery, secret custody, and shared office computer components.

For a repeatable standalone installation and public import/call check, see
[`scripts/headless-runtime/README.md`](../../scripts/headless-runtime/README.md).
The installer consumes an exact local tarball closure, verifies installed bytes,
and refuses transitive source-checkout dependencies. Its component receipts are
separate from node-hosted release and live headless/web acceptance.

The runner orchestrator remains in `@qorpera/runner-orchestrator`. Supabase owns canonical state and admission. This package consumes `@qorpera/cloud-client` wire representations and shared adapters; neither that package nor the web clients may import runtime implementation. `scripts/check-headless-packages.mjs` enforces source boundaries and bundles the runtime and browser client separately during `npm run check`.

Native provider credentials stay in isolated provider computers. Shared office guests contain a persistent workbench and concurrent agent desktops. Office tools must use the admitted run, existing effect ledger, exact screen/resource leases, current grants, and guest enforcement. A screen is a work coordination boundary, not a security silo.

Step 4 components were ported from `cb07a0269` with their regression tests. See `deploy/first-node/RUNTIME-STEP-4-INTEGRATION.md` for integration progress and the acceptance gates. Their presence does not imply that production admission or a guest deployment has been enabled.

Desktop tools require an explicit owner/admin desktop grant through the shared member access API. The database validates fixed-display coordinates, button/key names, bounded scrolling and text, and desktop screenshots independently of browser automation. A grant change increments the version atomically and invalidates previous screen leases. Browser-profile consent and private sign-in barriers continue to apply separately. The registry suite includes real SQL/member grant, native ledger and TLS admission connected to the contained Linux command adapter, Xvfb input/capture and immutable object storage. The fixture admits a disposable mount and X server; it does not establish full LXD/NAS or ordinary application acceptance.

`CloudNativeCompanyPresence` adds lossy file activity to company-audience native runs. The host signs the most recently accessed object/subtree, renews a short-lived SQL identity and uses the existing private Realtime channel. Only opaque path tokens travel on that channel. SQL checks current membership, native binding and path policy; token namespaces change with membership/grant state, including expiry. Receivers verify signatures, expiry, sequence and current reader/publisher scope before returning relevant agent/run identities. Private-audience runs are omitted from this shared channel.

Typed Company File event wakes select their exact path for initial presence composition. Other paths are selected through `company_read`/`company_list`; mutations publish writing activity through the same optional port. Startup records the resulting prompt digest, and read confirmations cover the complete result including presence. A two-second observation deadline reports unavailable state without blocking canonical work. Presence is never a lock, grant, durable activity event or wake. Shutdown removes the channel and exact registration; lost cleanup replies leave only expiring identity metadata.

`node scripts/test-runtime-company-presence.mjs` applies the migrations to disposable PostgreSQL, checks SQL admission/privacy/revocation, and connects two native clients through the installed Supabase SDK to a local Phoenix protocol fixture. It proves signed overlap, lease revocation, cleanup and unchanged canonical receipts/wakes/File head. Hosted Realtime authorization and native path presence in member clients remain live or client integration acceptance items.

Existing service packagers now use entrypoints in this package. Packaging is local; publication and deployment are separate operations.

`computer_transfer` supports explicit `export` from a relative `company_computer` workbench path into `object_storage`, up to 8 MiB. It requires the shell capability, current office/screen authority and original native effect receipt. The Linux broker reads through admitted directory descriptors without interpreting shell syntax, rejecting symlinks, hard links, other mounts, special files and observed mutation. The immutable object gateway stages exact bytes; SQL publishes one artifact with source provenance and a retention hold. The asset reference alone grants no future read authority.

An explicit `import` selects the ID/hash of a completed shared export asset from the same company environment, or an exact Company File path/version. Current company-audience native and office grants authorize reuse, including later runs; private screenshot artifacts and raw hashes are not accepted. Source authorization is rechecked after immutable object download and before writing. The Linux broker stages under the private screen-state parent on the same admitted persistent mount; desktop, browser and command namespaces receive only their selected child mounts. It links complete bytes atomically to the descriptor-bound workbench destination without replacing any existing entry, verifies the result, and records the import receipt with a source retention hold. Failures never delete a public destination. A receipt records historical import provenance, not the future contents of the mutable path. Worker transfers and member-selected upload/download remain separate work.

`company_write` accepts either UTF-8 `text` (32 KiB maximum) or a completed shared export `source: { realm: "object_storage", assetId, sha256 }` (8 MiB maximum), together with `path`, `expectedVersion` and `operationKey`. Source reads and canonical path writes require current cloud authority. The adapter verifies binary bytes, stages their immutable chunks/manifest and uses the existing atomic Company File mutation gateway. Ordinary paths update live; protected paths return the existing human-review proposal. The canonical receipt retains the source asset and plan atomically, even after the producing office connection closes. This neither creates a Company File checkout nor exposes a member-device path.

Company File sources use `source: { realm: "company_file", path, version }`, selecting a version observed by `company_list` or `company_read`. The existing path gateway checks current path/audience authority and remembers the read set. The transfer verifies the selected immutable manifest, each chunk and complete binary hash, up to 8 MiB, then rechecks path authority/version before installation and confirmation. The original receipt retains a source artifact with manifest/content hashes and a complete object graph. Only the internal import receipt and an exact match against the verified file closure admit this graph; generic member manifest graphs retain their prior verification boundary. Importing does not mutate the canonical path.

`node scripts/test-office-file-import-linux.mjs` verifies the physical writer's atomic visibility, concurrent no-overwrite publication, cancellation, aliases, moved directories, mutation and cleanup. The registry suite also imports its actual exported asset through SQL/native receipts, office TLS, the HTTP object gateway and the real Linux command adapter. Disposable mount admission and SQL HTTP transport are fixture adapters; this is not full LXD/NAS acceptance.

`node scripts/test-office-file-export-linux.mjs` exercises actual Linux descriptor reads and mutation/alias rejection. The office registry suite also runs `test-runtime-office-file-export.mjs` to combine actual PostgreSQL admission, native receipts, office TLS, guest automation, a disposable Linux file source, the HTTP object gateway and physical object/journal storage. Its SQL transport, office mount admission and initial office allocation are fixture adapters; it does not establish NAS replication, full LXD guest acceptance or hosted deployment. Its disposable Linux sources never pull an image. The desktop sources use a pinned local image ID, or the prepared local image named by `QORPERA_OFFICE_DESKTOP_IMAGE` (the command probe's image from `test-runtime-office-linux.mjs` works). The export read uses the pinned `node:22.22.1-trixie-slim` image for `linux/amd64`, so it needs an x86 host or amd64 emulation.

After a retained-boot service is stopped, `cloud-company-computer-boot-service-restart-control` accepts a separate typed restart packet. It retains the original `BootServiceStartRequest` unchanged and binds the new `CompanyComputerServiceSuccessor` to its predecessor's acknowledged stop. Root control verifies current credentials, retained directory custody, the original boot receipt and the stop archive under the kernel lock. A predecessor gets one immutable child claim before dispatch; unknown dispatches are observed without retry. Each successor has its own completion and nonce inspection, and subsequent stops select that actual wire schema. The local systemd acceptance now exercises two such restarts while retaining all original boot records. Ordinary workload and SQL/VM facts in this probe are synthetic; provider transport, journal and SQL activation for this restart lane remain required.

Protected service stop seals its verified evidence under `/etc/qorpera-office/history/<boot-id>/<activation-id>` before publishing the boot-scoped completion. Root-only directories contain an immutable claim, digest-addressed evidence and a manifest published last. Restart requires the predecessor's intact seal and rechecks it through dispatch and confirmation. Historical reads do not depend on `/run`, restore files, or grant new boot/SQL authority. An interrupted unsealed archive can finish from identical current evidence; a sealed archive with missing or changed contents is refused. Authorized reboot/resume configuration remains separate lifecycle work.

Protected boot configuration also accepts a stopped predecessor from a later boot. `verifyCompanyComputerBootPredecessor` reads that activation's typed start/restart, claims and acknowledged predecessor stop through the sealed archive, and compares the prior boot's persistent public configuration and receipt with those bytes. Original preparation remains the permanent workbench identity. The next configuration gets its own boot directory and credentials; preparation and ordinary units must remain unstarted throughout publication. The systemd probe's `--later-boot` option exercises this path after a synthetic prior boot with two service successors. Provider shutdown/resume composition for repeated VM cycles remains required.

`cloud-native-provider-service-main` selects the private office endpoint with `QORPERA_COMPANY_COMPUTER_URL` (canonical `https://<host>/office/<computer UUID>/native`) alongside `QORPERA_NATIVE_RUNTIME=company-path-v1`. Its distinct `qorpera-office-native` systemd credential must be available through `LoadCredential`; ambient tokens are rejected. The host must trust the office TLS certificate. No URL, token or native binding is supplied by the model or member client.

When that configured office is provisioning/recovering, the native session factory can offer only `computer_start`. It asks cloud authority for the current generation and grant, then records startup through the existing native receipt ledger. It makes no guest request and starts no screen. An accepted intent survives the native session ending; current membership/grants and founder pause are rechecked before provider preparation. Concurrent member/native requests coalesce one intent per generation. Cancellation retains the allocation until exact physical deletion is independently proved. The browser-safe `CloudCompanyComputerStart` API provides member request/status/cancel recovery for both clients. Client UI composition, provider execution and activation-triggered agent continuation are still required.

`HttpCloudCompanyComputerRegistry` also supports the two service-only office reservation/check RPCs consumed by the runner orchestrator's `LxdOfficeStartControl`. That adapter pins every provider configuration field and subtracts registry latency from its five-second preparation authority. Use the existing immutable operation journal before reservation; an uncertain reservation must retain the same allocation. No start API activates the office, installs an image, adopts state or grants native effects. `node scripts/test-runtime-office-start.mjs` exercises real SQL coalescing, reservation conflicts, the concrete provider adapter and cancellation lock races in a disposable database; provider identity and physical state remain fixtures.

`startCompanyComputerOfficeService` owns the native TLS and member WSS listeners, one shared action gate and independent supervision. `startCompanyComputerLinuxOfficeService` supplies `CompanyComputerLinuxGuest` and connects physical failure to both listeners’ cancellation lifetime. The guest composes contained native sessions, private RFB, profile/privacy enforcement and physical shutdown. The service factory constructs `CompanyComputerLinuxBoundary` from protected provider attestation and creates an immutable screenshot publisher per native run from protected `captureObjectGateway` configuration. `cloud-company-computer-service-main` loads this configuration and TLS/transport credentials from private systemd files, registers cancellation before startup, and awaits confirmed service cleanup. It performs no adoption or activation. Governed files and a current provider attestation remain prerequisites. Closing a member viewer does not stop the service.

`CompanyComputerLinuxCommands` implements command execution and PNG capture for `CompanyComputerGuestAutomation`. It requires an unprivileged Linux broker with `NoNewPrivileges`, an empty capability bounding set, finite cgroup v2 memory/PID/CPU limits, a provisioned workbench mount identity and a live guest-boundary adapter. Bubblewrap mounts the opened workbench and desktop-home directory descriptors, a read-only image, and only the assigned X socket; it provides no host network, host process view or browser-profile directory. Capture uses a separate private output directory. Cancellation, timeout and `close()` await the actual namespace process; a deadline during unresolved cleanup never establishes drain. The office composition must own and close these command adapters before acknowledging resource cleanup.

`CompanyComputerLinuxDesktopLauncher` starts persistent XFCE/TigerVNC desktops under the same Linux boundary. It requires existing adopted per-screen state and a prepared agent wallpaper, exposes private Unix X11/RFB sockets only, checks real readiness and current authority, and owns the desktop independently of the request or connected viewers. Closing a desktop terminates its namespace, destroys viewer sockets and removes only ephemeral state. The office composition must close admitted commands before closing their desktop.

`createCompanyComputerLinuxBrowserLaunch` supplies the mandatory contained launcher for `PersistentCompanyComputerBrowser`. Only this namespace mounts the granted profile, assigned X socket and broker-private HTTPS relay. Playwright uses inherited DevTools pipes, with no debugging TCP listener. The relay resolves and checks public IPv4 destinations before connecting, rejects private addresses, and drains on lost authority. Chromium retains its own nested renderer sandbox. Root-owned managed policy disables password saving, file pickers, downloads, extensions, developer UI, local files and omnibox JavaScript.

`startCompanyComputerLinuxPrivateSurface` starts a fresh X server and browser for one exact privacy challenge. It requires the containing service's physical drain proof and `CloudCompanyComputerPrivateSurfaceControl` authority. The browser uses the selected profile and a dedicated empty tmpfs; no shared workbench, persistent desktop, screen state, XFCE or autostart programs enter the private display. Its only returned transport accepts the matching owner's private viewer. No automation, X socket or capture handle is exposed. Authority renews while idle; revocation closes viewer sockets, Chromium and X before resolving `closed`. Cleanup retains the profile and removes ephemeral state. The service-only SQL check also guards entry acknowledgement; privacy-status recovery metadata is not browser authority. `CompanyComputerLinuxGuest` supplies the whole-guest barrier, pending-launch ownership, physical drains and shared-surface recovery. It validates recovered private viewers before launch and keeps ready private browsers independent of viewer disconnect.

`CloudCompanyComputerSharedSurfaceControl` renews idle shared desktops against current office, Company File, screen, staff membership and grant state. Physical desktop preparation occurs inside the native receipt-admitted effect, and screen-open success waits for readiness. Native session closure stops its commands/browser without powering off the shared desktop. Whole-guest drains await both pending startups and active resources; any unconfirmed cleanup retains quarantine.

`CompanyComputerLinuxBoundary` verifies the root-owned, digest-pinned completed adoption receipt, current boot ID, all shared/private mounts, kernel ceilings and a fresh service-only cloud machine allocation check. It rejects volatile workbench filesystems and overlapping private/shared paths. Its attestation comes from protected provider bootstrap configuration; image/bootstrap strings are compared with cloud registration and the receipt, not measured as an LXD image from inside the guest. The provider must still prove image provenance, NAS backing, inventory review and journal completion before publishing the receipt. This reader performs no adoption or activation.

All three adapters use Bubblewrap with Tini as namespace PID 1 and a trusted launch gate. Before the gate proves parent-death cleanup is armed, cancellation closes the execution-permission pipe; it must not kill the monitor during Bubblewrap's startup fork. After readiness, monitor termination kills namespace PID 1 and its descendants. A stuck setup remains an unknown drain. Browser shutdown first closes network access, then allows a bounded profile flush and awaits physical exit. Closing the automation connection alone cannot release a profile. The packaged systemd unit sends graceful shutdown to the main process and kills remaining cgroup members when it exits or the stop deadline expires. Actual service-manager crash/restart acceptance remains required.
