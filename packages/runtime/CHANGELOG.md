# Changelog

## [Unreleased]

### Breaking Changes

- `CloudRunLog` requires a trusted protection port before it can be constructed (memory tree W1c-3, component only; `RUNTIME-AGENT-MEMORY-TREE.md` §4.5). It classifies paths from complete arguments and tool results, every released read and current machine state before staging, stores only platform-keyed hashes and receipt identifiers for narrow steps, and preserves their full content only in the running process. `CloudRunLogRpcProtection` binds the port to one environment, job and run through the lease-scoped classification and keyed-hash calls, chunks complete inputs at their SQL limits and refuses malformed or unavailable answers. Pending results become final in order so an earlier narrow result cannot leave later public records; worker dispatch and followup wait for earlier results before committing the origin the worker inherits. Missing protection fails closed. The production folder adapter, origin-change and machine-refusal retries, and runtime activation are still pending; this change does not enable run logs for companies.
- The runner worker runs only the native company lane (legacy sweep step C, C-R1; no SQL): its whole-tree native lane and its Podman sandbox lane served only snapshot-v1 and are gone, with `executeNativeCloudRunnerJob`, `NativeProviderSandboxBackend` and `ExecuteNativeCloudRunnerJobOptions` (`cloud-native-provider.ts`) and the `start` member of `NativeProviderComputerBridge` (`HttpNativeProviderComputerBridge.start` stays, unsent, until the native host's legacy lane goes in C-R3). A folder-v2 job (`company-path-v1` with a native subscription) runs through `executeNativeCompanyRunnerJob`, unchanged. The worker fails any other run with no fallback: a `whole-tree-v1` run ("Runner does not support a whole-tree company run"), another sponsor, or a runner with no native bridge. `EphemeralCloudRunnerWorkerOptions` loses `backend`, `nativeWorkspaceGid`, `temporaryRoot` and `environment`; `executeJob` is the company lane's executor (`CloudRunnerCompanyExecutor`), and an injected one starts its assignment as production does. The native lease is released by the worker only when no completion was staged; a staged one is released by the governed completion with its receipt. `cloud-runner-service.ts` no longer builds `RootlessPodmanSandboxBackend`; its configuration has no `image`, `podmanPath`, `entrypoint`, `capabilities` or `jobTypes`, but the file still accepts `image`, `podman_path`, `entrypoint`, `capabilities` and `job_types` and ignores them, because the providers still write them (`native_bridge_shared_gid`, `temporary_root` and `environment` are still read, by the LXD guest bootstrap only). The runner no longer calls the `runner-broker` Edge actions `inputs`, `transcript`, `operations`, `artifacts`, `register_artifact`, `model`, `bind_provider_session`, `prepare_company_revision`, `begin_company_revision_graph`, `append_company_revision_graph`, `complete_company_revision_graph` and `verify_company_revision`, or its object GET and PUT, and so no longer reaches `qorpera_runner_broker_list_inputs`, `_list_transcript`, `_list_operations`, `_list_artifacts`, `_register_artifact`, `_authorize_input_object`, `_authorize_output_object`, `_authorize_company_file_object`, `_confirm_output_object`, `_reserve_model_request` and `_finalize_model_request`, `qorpera_bind_execution_provider_session`, `qorpera_runner_prepare_company_revision`, `qorpera_runner_begin/append/complete_company_revision_graph` or `qorpera_runner_authorize/finalize_company_revision_verification`. Their broker client methods go in C-R6 and C-R8; the Edge actions and the SQL in step D/E. The runner still calls `describe` and the native authority's acquire, renew and release.
