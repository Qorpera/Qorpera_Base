# Changelog

## [Unreleased]
- A studio patch can write a binary file: `StudioPatchOp` gains `write_file` (`StudioWriteFileOp`), whose `file` (`StudioBinaryRef`) names a file already in the company folder's storage by `manifestSha256`, `fileSha256`, `bytes` and `mediaType`, never its bytes. `parseStudioPatchOps` checks it closed with `parseStudioBinaryRef`: lower-case SHA-256 hashes, 1 byte to `STUDIO_BINARY_MAX_BYTES` (64 MiB), a media type of `STUDIO_BINARY_MEDIA_TYPES` (`model/gltf-binary`, `image/webp`, `image/png`, `image/jpeg`). `StudioTextPatchOp` is the three text ops. Nothing stages or lands a `write_file` yet: the runtime's `stage_surface_patch` refuses it, and the object gateway's and the runner's landings fail the job with a plain reason.
- `SurfaceAutomationSummary` carries `ownable`, `ownerUserId` (null: nobody) and `offer` (`SurfaceAutomationOffer`, open or turned down in the last day), as migration `20260930868000` answers them.
- `SurfaceImageRef`, `SurfaceMessageImages`, `SurfaceSessionImages` and `parseSurfaceSessionImages`: the images of an interface session's messages, as `qorpera_surface_session_images` answers them (migration `20260930865000`).
- `SURFACE_FIGURES`: the figures a surface can be drawn as; the web draws them and the agents' `propose_surface` picks from them.
- `CLOUD_MACHINE_HOME.sftpServer` (`/usr/lib/openssh/sftp-server`): the program of a home's file channel (Claude Code on the home, slice C1), from the machine image's `openssh-sftp-server`.
- `CLOUD_MACHINE_HOME`: where a machine keeps the pinned Codex for an agent's home (`/opt/qorpera-machine/codex`), the account its exec-server runs as (`qorpera-agent`, uid and gid 2000, home `/var/lib/qorpera-agent`, not root by default and with a password-free way to root of its own, `deploy/machine/qorpera-agent.sudoers`, so Codex's own shell can do everything `machine_run` does as root there) and the company folder's mount point (`/company`), so the runtime, the executor and the image build name one truth (agent-box slice 1). `CLOUD_MACHINE_HOME.codexSha256` (the pinned build the executor runs, equal to the artifact's) and `unitPrefix` (`qorpera-machine-home-`, each channel's unit in the machines' slice), home-lxd 14 Nov 2026.
- A page of a command's log holds up to 65,536 bytes of output (`CLOUD_CODING_COMMAND_PAGE_BYTES`; keyholes S1, 12 Nov 2026): `parseCloudCodingCommandRead` takes a `limit` of 4 to 65,536 (default still 4,096) and `parseCloudCodingCommandReceipt` an `output` of up to 65,536 bytes; both were 16,384 (`CLOUD_CODING_COMMAND_LEGACY_PAGE_BYTES`, what an executor or guest that does not say what it takes still gets asked for). An executor or guest from before refuses a larger read, so a caller asks each only for what it said.
- `CODING_GUEST_HELPER_MAX_BYTES` (`cloud-coding-command.ts`, 131,072 bytes): the one bound of a coding guest helper (the four programs in `/opt/qorpera-coding`), which `scripts/package-coding-guest.mjs` packages within and the executor reads each helper within. It was 65,536 in both places, and part W's package caches had taken the command guest to 66,607 bytes, past it: `CODING_PACKAGE_CACHES` and `CODING_PACKAGE_CACHE_ENVIRONMENT` were bundled into every program that imports contracts, used or not (an `8 * 1024 ** 3` that esbuild cannot prove pure, and an environment built by calls not marked pure). The limit is written out (`8_589_934_592`) and the environment's calls are marked `/* @__PURE__ */`, so the four helpers bundle none of it again (storage 54,474, command 64,835, Git 43,071, watchdog 14,925 bytes, as before part W); the executor and the guest agent read the same values.
- `CODING_PACKAGE_CACHES` and `CODING_PACKAGE_CACHE_ENVIRONMENT` (`cloud-coding-guest.ts`; own code storage, step 6, part W; `lanes/own-code-storage/STEP6-BUILD.md`): a coding machine's package caches, which the coding executor and the coding guest agent share. `/var/cache/qorpera-packages` with a folder for each of npm, pnpm, pip, uv and Playwright's browsers, the group `qorpera-coding`, the 8 GiB the tool folders may hold at boot and tmpfiles' age (`30d`); and the six variables that point each tool at its folder: `npm_config_cache`, `npm_config_store_dir` (pnpm 10) and `pnpm_config_store_dir` (pnpm 11 and later, which read only their own name; proven with pnpm 12), `PIP_CACHE_DIR`, `UV_CACHE_DIR`, `PLAYWRIGHT_BROWSERS_PATH` (`tools[].variables`), and beside them `PLAYWRIGHT_SKIP_BROWSER_GC=1` (`tools[].settings`): Playwright's own browser GC, run by one session, reads every install that uses the shared path and takes another session's, unreadable in its 0700 home, for gone, so it removed that session's browsers (reproduced on node01 and in the image's proof: the first user's `chromium_headless_shell-1243` and `ffmpeg-1011` went at the second user's install of another version, and its launch failed with "Executable doesn't exist"). `tools[].trees` names, per tool, the trees it runs or links from in place (Playwright's browsers, npm's `_npx` packages, pnpm's global virtual store links, uv's archives, environments and builds): tmpfiles ages none of their files, and the agent removes each whole at boot when nothing in it was used for `ageDays` (30; it replaces `age`). Not yarn 1, which the build first had: it makes its cache's folders with its own umask applied (0755), so the next session could read them but not add to them (EACCES in the image's proof), so it is left out. The mount request may be `qorpera.coding-guest-mount/v2` (`CODING_GUEST_MOUNT_V2`): the same request, also asking the agent to say in its answer whether the machine's package caches are ready (`CodingGuestMountAnswer.packageCaches`, optional). Two closed parses changed: `parseCodingGuestRequest` takes the mount request in v1 or v2 (an agent from before refuses v2 as an invalid request, having done nothing); `parseCodingGuestAnswer`'s mount answer is exactly the four keys for a v1 request, as before (an executor from before reads a new agent's v1 answer unchanged), and for a v2 request the four or the four and a boolean `packageCaches`.
- `CloudCodingRepository.host` is `"github.com" | "qorpera"` (`CLOUD_CODING_REPOSITORY_HOSTS`; own code storage, slice 1). A repository kept in Qorpera has a lower-case owner (`^[a-z0-9]([a-z0-9-]{0,37}[a-z0-9])?$`) and name (`^[a-z0-9_]([a-z0-9_.-]{0,98}[a-z0-9_-])?$`), which name its folder, and its default branch is always `main` (`CLOUD_CODING_QORPERA_BASE_BRANCH`), so a repository has one identity and one `main/`; GitHub's rules are unchanged. `parseGitHubCodingRepository` refuses any other host, for every step that reaches GitHub; `parseCloudCodingPullRequest` refuses a repository kept in Qorpera; `cloudCodingRepositoryInQorpera` says which it is.

### Breaking Changes

- `CLOUD_MACHINE_GUEST_PATHS.repository` (`/mnt/repository`) is gone (F3 6e-1): a company machine has no repository disk; a coding session's work is in the company folder at `/company`.
- A coding session's guest status is `qorpera.coding-guest-status/v2` (C1: idle sleep and the quiet-day archive on the folder model; P3 phase B run 11): beside its commands it carries the session's usage, `CodingGuestUsage` (`bootId`, `uptimeMs` from `/proc/uptime`, `cpuUsageUsec`, `ioBytes`, and `ioComplete`, false when the machine ran more processes than one status reads, `CODING_GUEST.usageProcesses` = 8192), for the executor's one idle rule. `parseCodingGuestAnswer` refuses a v1 status, a missing or malformed usage and any other key in it.
- The unreleased new-boot successor request now requires `bootIntentId`, binding it to a separately prepared pre-boot intent. Prior unbound handoffs cannot be reconstructed or resumed automatically.
- Unreleased preparation completion now uses `qorpera.office-preparation-completion/v2` and requires the independently read adoption-receipt digest. Older completions cannot satisfy the new preparation phase.

### Removed

- `ExecutionIntentBudget`, `ExecutionIntentCapability`, `COMPANY_OPERATION_KINDS` and `CompanyOperationKind` are gone (legacy removal, step C, HP-E2). Nothing used them. `JsonValue` and `ExecutionIdentity` stay; the hosted primary's session events still use `ExecutionIdentity`.

### Added

- The machine command receipt (`qorpera.machine-command-result/v1`) can carry `companyFolder` (F3 6e-2a), the executor's report on a test machine: `company` (`mounted`, `pending`, or `none` with `why`), `heldBack` (why output is held back), `lost` (why the machine lost the command) and the paths not saved, each with its outcome and reason: once, those the folder let go (`notSaved`, at most 8, and `moreNotSaved`), and on every receipt while they last, those it holds to try again (`stillNotSaved`, at most 8, and `moreStillNotSaved`). `parseCloudMachineCommandFolder` checks it closed and bounded, to 1536 bytes as the agent's tool measures it (`cloudMachineFolderBytes`). `CLOUD_MACHINE_FOLDER_LOST` holds the agent's words for each of the six causes (`restart_unproven`, `restart_view_closed`, `restart_view_gone`, `moved_unchecked`, `moved_starter`, `moved_unreadable`), used by the executor and the runtime (SQL's `qorpera_company_machine_folder_lost_text` says the same words), and `isCloudMachineFolderLost` checks a key. A runtime that reads it must be live before the executor sends it: an older parser refuses the receipt.
- Added `cloud-coding-guest`: the protocol between the host and the agent inside a member's coding machine (F3 step 5g-2b). The host runs `/usr/bin/node /opt/qorpera-guest/agent.mjs <verb>` with one JSON request on stdin and reads one JSON answer line (for `output`, followed by the raw bytes). `parseCodingGuestRequest` and `parseCodingGuestAnswer` check the six verbs (`mount`, `run`, `output`, `cancel`, `stop-session`, `status`) closed and bounded, and check that an answer belongs to its request; `parseCodingGuestRefusal` reads a refusal's error code. Errors never quote the value.
- `cloud-coding-guest` gains the `quiesce` verb (F3 step 5g-6a): one session's request, answered with `qorpera.coding-guest-session-quiesced/v1` once nothing of the session runs and its view is still mounted. A `status` answer lists every running command first, then the newest of the rest.
- `POSTGRES_UUID_PATTERN` validates the canonical lower-case text accepted by PostgreSQL UUID storage, including nil and reserved version/variant bits, for file formats that explicitly use that grammar. Runtime identity admission still uses the stricter `UUID_PATTERN` and `isUuid`; their rules are unchanged.
- Added `folder-key`: `folderKey(path)`, the folder core's key for a path exactly as `public.qorpera_folder_key` computes it (NFKC, Unicode simple case mapping to upper and then lower case, NFKC), for every JavaScript copy of the key. Each code point maps on its own to one code point, so 'Straße' keeps its ß and 'İ' folds to 'i', as in the database; JavaScript's own `toUpperCase`/`toLowerCase` use full case mapping. `parseCloudCodingDispatch` checks the to-do path's folded form with it. `scripts/test-folder-key.mjs` checks it against the database's function for every code point.
- The coding command receipt (`qorpera.coding-command-result/v2`) can say a member's coding machine stopped under the command (F3 step 5g-3a): state `machine_stopped`, with `exitCode` null, and `log.gapBytes`, a positive count of output the machine's ring dropped before the host saved it, present only when bytes were lost. Nothing emits either yet; the executor's folder transport does from 5g-3. A runtime that reads them must be live before that executor ships: an older parser refuses the receipt. `parseCloudMachineCommandReceipt` refuses both, so a company machine keeps its own `lost`.
- Added `idle-rule`: the one idle rule's busy measure for every machine kind (the 2026-10-03 amendment "one idle rule for every machine"): `idleRuleBusy(before, after)` over two samples of a program's processor seconds and bytes moved, busy at `IDLE_RULE_BUSY_CORE_SHARE` (5% of one core) or `IDLE_RULE_BUSY_BYTES_PER_SAMPLE` per `IDLE_RULE_SAMPLE_SECONDS` (512 KiB per 30-second sample, about 17 KB a second, reads and writes alike; scaled to the sample's real length). The thresholds live here so every machine kind tunes them in one place.
- `idle-rule` adds `idleRuleProcessIoBytes` (a process's `/proc/<pid>/io` rchar + wchar), every machine kind's data signal: a computer's shell and, summed over its processes, an agent's whole machine.
- Added `wire-values`: the one copy of the checks for values that cross a wire boundary. UUIDs follow one documented case rule: a check that returns the value it was given (`UUID_PATTERN`, `isUuid`) accepts lower case only, and either case comes in only through `parseUuid`/`normalizeUuid`, which return the lower case PostgreSQL prints. `parseTimestamp` takes only RFC 3339 / ISO 8601 times with an explicit offset (PostgreSQL's `2026-09-29 10:00:00+00` included; bare numbers and offset-less times refused, so no host time zone is involved) and returns the text unchanged with its microseconds, for cursors, alongside a millisecond `Date`. Also `parseSha256Hex` (lower-case hex only), `parseRecord`, `parseClosedRecord`, `parseBoundedText`, `parseInteger` and `WireValueError` (its messages name the label, never the value). The package's tests now run with `npm test`. `scripts/check-wire-helpers.mjs` (in `npm run check`) refuses new local UUID regexes and `record`/`uuid`/`sha256` helpers per package against `scripts/wire-helpers-baseline.json`.
- Added `parseCompanyComputerNativeRoute` for one-computer and company-wide native office routes.
- Added closed office root-reset contracts: the operator-authored `qorpera.lxd-office-reset-plan/v1` retaining every logical identity while naming fresh root-incarnation, successor-activation and physical command identities, a provider-validated custody manifest bounding the archived diagnostic outbox and allowlisted public root history, a restore receipt bound to the sealed custody digest and a distinct boot, immutable ordered phase records, five-second phase challenges/evidence, historical reset status and a reset successor request/metadata pair requiring a distinct activation, boot and configuration. Parsing grants no dispatch, deletion, restoration or admission authority.
- Allowed the selected boot's public adoption, configuration claim/completion and configuration JSON in protected stop history. Secret credential paths and other boot directories remain excluded; existing manifest bytes retain their order.
- Added closed retained-boot service-start and inspection contracts bound to the prepared boot successor, exact configuration acknowledgement and a distinct invocation. Historical packets grant no current SQL authority.
- Added canonical boot-directory derivation shared by the provider and root controls. Strict runtime UUIDs map to systemd's 32-hexadecimal boot-ID path without a mutable current-directory pointer.
- Shared the closed, bounded stop-history manifest and boot/activation path parser between root sealing and provider readback. Existing wire bytes remain stable; metadata is copied and frozen without granting runtime authority.
- Added explicit reboot/resume intents binding a planned activation to the acknowledged predecessor, protected stop history and VM shutdown evidence. Metadata is immutable and recoverable; current dispatch authority expires within five seconds and ends at post-boot handoff.
- Added a separate new-boot successor request for reboot or explicit resume after power-off, binding a distinct activation/boot/configuration to retained stop history, VM shutdown and boot observations. Metadata recovery stays distinct from VM dispatch and physical readiness; same-boot requests retain their original restrictions.
- Added a closed protected restart packet binding prepared successor metadata, exact service configuration and acknowledged predecessor stop. Completion rejects old invocation and command identities; nested history is copied and frozen.
- Added closed same-boot successor requests and metadata binding a distinct activation to its stopped predecessor. Retained metadata grants no physical start, fresh inspection or capacity release.
- Added closed, short-lived service-stop challenges binding current office revision, privacy version and drain inventory, plus immutable physical-stop acknowledgement. Historical acknowledgement grants no successor admission and cannot acknowledge newer drains.
- Added closed service-stop requests, historical completion and fresh-inspection records bound to the retained revocation, original startup and protected command. Completion distinguishes the admitted invocation from an unadmitted automatic restart and requires an absent or empty service cgroup; it grants no successor admission or capacity release.
- Added closed lifecycle revocation requests and receipts binding provider, activation, allocation, boot, service invocation and ordered screen drains. A revocation receipt conveys no physical stop, replacement or resource-release authority.
- Added closed service-start completion and fresh-inspection contracts binding the original request, activation, configuration, systemd invocation, PID and cgroup. Historical completion does not establish liveness; the provider must retain a new inspection nonce and enforce an end-to-end deadline.
- Added a closed bounded service-start request tying retained configuration completion to activation boot, configuration/receipt digests and listener ports. Protected file custody and live systemd measurement remain the root helper's responsibilities.
- Added closed immutable activation evidence, startup identity and authority contracts binding one allocation, boot, exact configuration digest, listener pair and nonzero service invocation. These records do not substitute for physical measurements or active-work authorization.
- Shared bounded confidential configuration requests, fixed file names/limits and closed hash-only completion validation between the provider and root helper. Completion requires independently derived command, preparation and file identities and grants no activation authority.
- Added deterministic copied-state adoption receipt data binding the prepared guest identity, adopted layout, mount and output-inventory/review digests. Publication and admission remain the protected helper's and cloud authority's responsibilities.
- Shared closed preparation command and completion validation between the provider and protected guest helper, matching the retained command, exact report digest and fresh systemd invocation without granting activation authority.
- Added closed preparation-report validation binding the delivered request and content hashes, scope, boot, copy, mount and counts, with an explicit systemd invocation ID. Callers must separately verify protected custody and a fresh completed invocation; valid data grants no admission.
- Added a closed portable office preparation manifest binding copied paths, private modes, lengths and hashes to one allocation, guest boot and reviewed copy. It contains no execution or admission authority.
- Added provider-neutral cloud execution identity, capability, budget, and JSON value contracts.
- Shared the portable company-computer layout validation and legacy screen/profile adoption mapper between provider preparation and the headless runtime, without filesystem or desktop dependencies.
- Added retained-workbench receipts and boot-configuration packets binding the original adoption, planned boot intent, shutdown bytes and resumed boot observation. Shared confidential material validation preserves the original configuration format. New receipts describe current directory custody without asserting that mutable files still match their copied inventory.
