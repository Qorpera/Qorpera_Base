# Changelog

## [Unreleased]

### Breaking Changes

- The coding executor configuration is `qorpera.coding-executor-service/v7`: `guest.resourceProfile` names only `maxLogBytes`. A turn no longer detaches its session: the host records the session's attachment (`qorpera_attach_coding_session`), and `CodingExecutorHost` gains `endTurn` and `keep` and loses `refreshLease`.
- Coding executor configuration now requires v6 with a separate peer command listener and explicit peer credentials. Environments can enroll multiple executor owners; retained machines and NAS writers remain pinned to their original host.
- New office VM operation events use v2 timestamped records. The current reader preserves v1 history and accepts mixed chains, but older provider binaries cannot read newly appended v2 records; automatic downgrade or journal conversion is unsupported.
- Node admission now requires a receipt from the enrolled complete-host inventory publisher. Hardware-only ready reports and observations for an older node policy cannot authorize new starts. Legacy VM metadata, unregistered computers and changed physical/configuration identities require explicit reconciliation.
- Login VMs now require company and node admission and use one immutable allocation per sign-in attempt. Completed or revoked attempts delete the VM before releasing capacity, retaining the Compute Identity disk. Legacy identity-keyed guests are preserved and refused pending explicit inventory reconciliation.
- Native job VM creation and first boot now require enrolled node/host/resource policy and fresh capacity admission. Existing native journals without node placement block new acquisitions until their physical resource limits and retained allocations are reconciled.
- Office creation, first boot and retained-VM resume now require explicit node/provider enrollment and fresh node admission. Missing configuration or observations refuse physical dispatch; existing company reservations are retained.
- Unreleased VM power-off requests now use `qorpera.lxd-office-power-off-request/v2` and bind a verified root stop-history manifest. Prior unbound shutdown records are preserved and refused, with no automatic reconstruction.
- The unreleased office guest binding now uses `qorpera.lxd-office-guest/v2` and requires an enrolled provider ID and policy digest. Old office journals/bindings are rejected without automatic conversion. Office start reservation/check RPCs require the same provider identity; the original unbound functions are private. Native runner bindings are unchanged.
- The unreleased office physical policy now uses `qorpera.lxd-office-physical-policy/v2` and requires exact project, network and storage-pool configuration digests. Prior policies are rejected without implicit enrollment or journal migration.

### Added

- `CloudFolderRunMaterializer`, in the reconcile lane by default, turns a `folder-v2` company's queued work into runs (folder core C4, P28 part 1, migration 20260930018000): on every pass it lists the due companies through the runner-orchestrator edge function's `folder_materialize_due` and materializes each with `folder_materialize_company`, one company per request (so one per transaction), before `reconcile` and the claim. One company's failure never stops the others. An edge function that predates the actions answers 400, and the materializer asks again after ten minutes.
- The routine reconciler starts a `folder-v2` company's dynamic routine's next run (folder core C1c-3e, migration 20260930009500): it lists them through the runner-orchestrator edge function's `folder_dynamic_routines` and restores each with `restore_dynamic_routine`, one company per transaction, after the schedule heads. An edge function that predates the actions answers 400, and the reconciler asks again after ten minutes.
- Added recovery volume clean-up for one-run VMs (session-buildup audit gap 7): when a settled run journal (stopped or lost, guest gone, capacity released) is archived a day after it settles, the LXD provider deletes the run's recovery volume first. It deletes only a volume carrying exactly the run's authority (schema, run, company, runner, Compute Identity, adapter) and confirms it is gone. A volume that drifted, or that LXD will not delete (in use), stays for an operator with its journal: the pass goes on (a failed pass would stop the node's claims) and the log names it as `recovery volume kept: acquisition=…` at most once an hour. The journal records `recoveryVolumeRetired` before the delete, so a provider that stops in between does not demand the volume back. A journal whose guest exists again is reconciled before it is archived. Volumes of runs archived before this build stay for the operator runbook (`deploy/first-node/RUNTIME-COMPANY-DELETE.md`).
- Added push wake-ups for the runner orchestrator behind `QORPERA_RUNNER_ORCHESTRATOR_WAKE=realtime` (off by default). The service joins a private Supabase Realtime topic with the publishable key it already holds; the topic is derived from its control token's sha256, so no new credential reaches the node. While the channel is joined and the loop is idle, it asks for work on a wake-up and every `QORPERA_RUNNER_ORCHESTRATOR_WAKE_BACKSTOP_MS` (default 5 s) instead of every 250 ms. It polls at the fast rate for 30 s after activity, whenever the channel is down, and for ten minutes after a backstop claim finds work no wake-up announced (reported). Wake-ups that bring a claim forward stay one poll interval apart. The WebSocket is a small RFC 6455 client on `node:https` that runs under `--jitless`. Measured against a fake with 50 ms Edge round trips: an idle orchestrator's Edge calls fell from 283 to 80 a minute (claims from 199 to 12), and enqueue-to-claim latency from a median of 151–237 ms to 51 ms. The database side (migration `20260928319550`) broadcasts on enqueue only while `qorpera_orchestrator_wake_settings.enabled` is on (off by default), within a 200 ms lock budget per enqueuing transaction; the channel follows each control rotation at once and gives up on a join Realtime never answers.
- Added workbench removal to office retirement (company delete D5b): once the deleted company's VM is confirmed absent and before `qorpera_retire_runtime_office`, `emptyLxdOfficeWorkbench` removes the top-level entries the office's journal accounts for on its NAS workbench mount (its adoptions' trees by adoption id, and the names its inventories saw), keeping the mount root. It refuses when another LXD instance's disk or another NFS mount on the host reaches the same export. The walk goes by directory descriptors through `/proc/self/fd`; every entry must belong to the workbench account and sit on the root's mount; links are removed, never followed. A pass ends 30 seconds after it starts or 10 seconds before the retirement's 60-second budget ends, whichever is first (its reads count against it), and the retirement reports `pending` until the root lists nothing; the gate and the VM's absence are then checked again. Failures hold the office with an `OFFICE_WORKBENCH_<reason>` token.
- Added sign-in identity retirement for a deleted company (company delete D4, migration `20260928269450`): the login gateway asks `qorpera_runtime_identity_retirements_due` at most once a minute, and for each identity SQL names (none of the company's machines released in the last ten minutes, no unreleased sign-in machine of its own here; each tried at most once a minute, eight a pass) checks the volume is exactly the identity's, detaches the execution-host device of exactly the identity shape (`LxdExecutionHostIdentities.detach`), deletes the volume (`LxdClient.deleteStorageVolume`), confirms both gone and records it with `qorpera_confirm_runtime_identity_retirement`. While SQL names it, its sweep does not attach it again. A native run journal that never starts again (stopped, lost, or its guest's deletion or capacity release recorded) no longer needs or re-creates its identity volume when reconciled, so a retired volume cannot block the node's claims after a restart.
- Added office retirement for a deleted company (company delete D3b, migration `20260928259320`): after a confirmed `power_off` (also one from before a node reboot), `LxdOfficeRetirementWorker` asks `qorpera_runtime_office_retirement` (until a delete is pinned, at most once a minute per process), pins SQL's delete command id in `office-retirement-request.json`, takes a nonce-recorded five-second window, dispatches the one journaled `delete` of the stopped VM, confirms it absent and releases it with `qorpera_retire_runtime_office`, then writes `office-retired.json`. Unknown or failed deletes are held from the journal alone, without SQL calls, and never redispatched.
- Added the node base for automatic company machine setup (step 1): `qorpera-office-node-base measure CONFIG` reads a node's own values (host identity, LXD socket group and daemon identity, project/network/pool digests as the office gate compares them, the local journal mount), refuses when they differ from the node observer's enrolled host, and prints the base with its digest; `check CONFIG BASE` measures again and compares (exit 0 same, 1 changed, 2 error). - Added the coding keeper: every 10 s it observes each awake machine's attached sessions, renews their attachments (`qorpera_keep_coding_attachments`) and guest leases, takes off archived, revoked or lost sessions (cancelling their running commands first) and adopts attachments after a restart from the journaled guest configuration. ### Changed

- Office fleet units now require `qorpera-node-host-namespace.service`, which the node observer installs on every node, instead of the single-office installer's `qorpera-office-host-namespace.service`. Both run the same helper and write the same namespace record.
- Native office routes may name every computer of a company (`/office/{companyComputerId}/native`); still one route per company environment, and its token is accepted by all of that company's computers.
- Warm conversations (contract amendment 2026-09-27), off unless `QORPERA_SHARED_EXECUTION_WARM_IDLE_MS` is set: after an attended run the shared execution service parks its slot (runner stopped and wiped, capacity released, native host kept with its scratch and bridge credential) for the conversation's next run, which claims it after the identity is verified again and starts only its runner. A changed identity, a stopped host or a passed window evicts the slot; under capacity pressure the slot parked longest gives way.
- The orchestrator asks for new work on every poll (250 ms) and reconciles (control renewal, occurrence reconcilers, expired claims, provider, retained claims) every `QORPERA_RUNNER_ORCHESTRATOR_RECONCILE_MS` (default 2 s) instead of before every claim; a failed reconcile still blocks claims and is retried on the next poll, a failed dispatch brings the next reconcile forward to the next poll, and retained claims keep their priority until they have been re-read. An assignment that races a runner's activation is retried after 50 ms, doubling to 3 s, instead of after 250 ms.
- The one-run LXD provider no longer runs everything under one provider-wide lock. Each acquisition's journal has its own lock (held through that VM's boot), so independent runs create, start, bootstrap, deliver and stop side by side; runs of one Compute Identity create its shared volume under a per-volume lock. A reconcile pass works on up to 8 journals at a time; a journal an acquisition, delivery or stop holds is looked at again at the end of the pass once they let go of it, or on the next pass. Within a pass, one unreadable or stuck journal no longer stops the others (an unreadable journal still refuses new starts and stops, as before). What bounds concurrent starts is unchanged: the node ceiling, admitted by the database under the node row's lock right before every create and start; the capacity inventory check before a new start is unchanged too. Measured with a Unix-socket LXD fake at a quarter of node 1's boot time: 4 queued runs were all ready after 4.4 s instead of 17.4 s.
- The orchestrator reconciles in a lane of its own: asking for new work no longer waits for a reconcile pass that is still running (with the old provider a pass waited for any VM that was booting, so a node claimed nothing during a boot). Claims still wait for the first pass, stop while the latest pass failed (it is reported and retried after one poll interval) and, after a failed dispatch, wait for the next pass; retained claims are re-read after every successful pass.
- The shared execution service starts a sandbox's runner unit right after its host unit (systemd orders it after the host's start) and waits for both health endpoints together, polling every 25 ms; the assignment is still delivered only once both answer.
- The shared execution service defers a run whose Compute Identity volume is not attached to the execution host (`NODE_IDENTITY_ELSEWHERE`, this orchestrator only) before it takes a slot, provisions a runner row or reserves capacity, so a login that just moved to the node waits for its volume instead of failing its run. The wait is bounded: after two minutes the start fails like any other.
- Shared preparation/configuration journal mechanics while preserving existing preparation authority and event bytes. Configuration records additionally bind the acknowledged preparation observation and use separate schemas and directories.
- Connected the adoption copier to repeated creation-journal, stopped-VM, physical-policy and cloud mapping checks. A root-protected, boot/plan-bound infrastructure maintenance handoff is required at each checkpoint; it records operator responsibility for excluding other NAS writers and does not acquire a remote lock. Copy completion still grants no boot or activation.
- The orchestrator accepts a run without a Company File snapshot id and substrate version id, as a `folder-v2` run has (folder core C4, tolerant before any such run exists): both or neither, each checked when present; `CloudRunnerWork.substrateVersionId` and `companySnapshotId` are optional.

- Extended routine reconciliation with weekday-anchored intervals and advanced month, weekday, time-window, and time-zone schedules.
- Replaced the Pi protocol dependency with the provider-neutral `@qorpera/contracts` package.

### Fixed

- The code package loader's locked child, which reads the protected packet, now runs with ignored stdio like the other office controls. Before, it inherited the exec's recorded streams, so its tools' JSON results and any uncaught stack trace were stored in LXD's host exec logs. The loader now writes nothing on success and only `OFFICE_CODE_PACKAGE_LOADER_UNCONFIRMED` on failure; `bootstrap.cjs` and `measure.cjs` no longer print their results, which the provider already reads back from the files they publish.
- Fixed the exec host reusing a machine key for a later attempt of the same run on the same slot: the key now names the attempt's acquisition id, since a released allocation keeps its key.
- Stopped the company computer provider from suspending the same node demand on every lifecycle pass. While a computer stays powered off, the lifecycle replays its completed power-off every few seconds, and each replay called `qorpera_suspend_runtime_node_machine`, which locks the profile fence, the allocation, the node row and the demand only to answer "already suspended" (2026-09-28, node 1: about 16 calls a minute for 42 hours, amplifying a lock convoy on the node row). The power-off worker now treats any confirmed answer as final for that transition and asks again only after an unconfirmed answer or in a new process. Replays still recheck the stopped VM and SQL stop authority. No SQL change ([#505](https://github.com/Qorpera/Qorpera_Base/pull/505)).
- Fixed a deadlock between a node's first inventory binding and admission of the same machine: an inventory observation now takes the binding foreign-key locks on its managed allocations, in UUID order, before the node lock, matching admission's allocation-then-node order (migration `20260928242000`, re-cut of closed draft #326). Historical receipt replay and every check after the node lock are unchanged.
- Continue completed office startup and wake phases without waiting for the next polling interval, while retaining backoff for pending work and failures.
- Bound office-provider startup to the enrolled journal and NAS workbench mounts, so a node reboot cannot leave required storage inactive when the provider starts. Mount dependency paths preserve literal dollar signs while escaping systemd specifiers.
- Corrected boot-successor SQL admission to preserve the original preparation observation while requiring fresh boot, configuration and receipt evidence. The prior check required a new preparation digest and rejected the concrete retained-workbench resume path. An additive migration preserves existing history and refuses a substituted preparation identity.
- Kept configuration confirmation within its bounded reconciliation time by sharing one fresh five-second authority window across each of two complete credential-read passes. Both passes still verify all protected bytes and the unchanged receipt, and a final authority check precedes publication. Repeating full preparation before every file could exhaust the 30-second limit in the actual-systemd acceptance test.
- Included the kernel-lock launcher in the required office image executable digests, so an image cannot pass dependency admission while omitting the command needed by every protected root control.
- Preserved the office host mount-namespace check for non-root systemd services when Linux denies PID 1's namespace link. A separate fixed root startup helper records the actual namespace and boot on a protected local path; missing, stale or unsafe records remain unconfirmed. The root helper alone needs `CAP_SYS_PTRACE`; the provider retains zero capabilities. Packaging includes the helper, and the startup unit preserves the host mount namespace.
- Kept the packaged runner provider, login gateway and orchestrator compatible with Node 22 under `--jitless`: require builtins through CommonJS and use pinned Node HTTP request/response types instead of loading Undici/WebAssembly. Narrow service ports retain JSON, bytes, headers and cancellation without requiring multipart or clone APIs. Package regressions cover real startup, repeated polling, credential rotation, HTTP boundaries and SIGTERM with and without forbidden-global guards.
- Provisioned a separate governed guest, credentials and recovery volume for each execution attempt so sponsor handoff can continue the same run after its first guest is retired. Preserved earlier journals and rejected continuation while a prior guest remains live.
- Kept the live Company File mount optional for copy-mode guests and excluded it from isolated proposal-review VMs.
- Refused redirected guest credential delivery and provisioning requests, validated exact HTTPS control-plane origins, and closed unused response bodies, including stalled redirect responses.
- Fixed the LXD provider keeping the capacity of a start whose create LXD reported as failed ([#511](https://github.com/Qorpera/Qorpera_Base/pull/511)): the journal is lost with its deletion confirmed and the capacity released at once, so the run's next attempt does not wait on it. A create whose outcome is unknown (a wait that timed out, a lost reply) is left as before. The LXD client names an operation that ended in Failure or Cancelled `LxdOperationFailed`; after the error envelope LXD 5.21-6.x also writes for a wait that timed out, it reads the operation's own end to tell them apart.
