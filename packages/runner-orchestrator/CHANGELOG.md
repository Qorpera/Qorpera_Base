# Changelog

## [Unreleased]

### Breaking Changes

- Company machines (agents' test machines) are made with `security.devlxd=false` (F3 step 6c; `deploy/first-node/RUNTIME-FOLDER-TEST-MACHINES.md` "The security line"): `/dev/lxd` offers the guest nothing, and every stream into the machine is started by the host. No pass or secret is in its LXD config. A machine made before has `/dev/lxd` and is refused as drifted (`COMPANY_MACHINE_DRIFTED`).

- The office image package may carry the machine's agent card files (E6, guest half; merges with #925): `OFFICE_IMAGE_AGENT_PLUG_PACKAGE_FILES` (`qorpera-agent-plug.rules` to `/etc/udev/rules.d/70-qorpera-agent-plug.rules`, `qorpera-agent-plug.network` to `/etc/systemd/network/00-qorpera-agent-plug.network`, `qorpera-agent-plug-networkd.conf` to `/etc/systemd/networkd.conf.d/qorpera-agent-plug.conf`). `parseOfficeImagePackage` refuses some of them without the rest, or any of them without the computers' network files (`OFFICE_IMAGE_PACKAGE_INCOMPLETE`). The image's `qorpera-computer-network.service` now requires the card (`qagent`): on a machine without one the computers start with loopback only.

- No service key reaches a guest, a slot or the execution host (G2-5; `deploy/first-node/RUNTIME-NATIVE-HOST-KEY.md` "G2-5"; needs the G2-4 runtime and guest image): the LXD provider and the login gateway push no `qorpera-supabase-service-key`, the shared execution service writes none into a slot and refuses to start if it is given one, also as a file left in its credential source (`qorpera-shared-execution.service` no longer loads it; `QORPERA_SHARED_EXECUTION_CREDENTIAL_SOURCE` names that directory, default `/etc/qorpera/shared-execution-credentials`), the slot's `qorpera-shared-run-host@` unit no longer loads it, `rebuild-exec-host.sh` keeps the staged key on the node host for its own calls, and the process provider passes none to its native host. Journals from before carry a bootstrap digest with the key's file and are refused.

- Agents' machines and coding machines plug into the node's agent exit (E2c; `deploy/agent-exit/README.md`): their only network card is a port of the agents' bridge `qagent0` (`nictype: bridged`, MAC and IPv6 filtering, port isolation, no `ipv4.address`), and its MAC comes from the node's plug tool, which `reconcileCodingMachine` runs right before each create (`agent-plug.ts`; a plan names its `agentPlug` claim, and the hosts take an `agentPlug` option for tests). The machine policy's and the coding executor's `vmPolicy.network` must be `qagent0`; a binding on any other network is refused. The executor unit joins the group `qorpera-agent-plug` and may write the exit's client map and leases, so the agent exit (group, plug tool, units) must be installed on the node before this executor starts. The exact-device checks accept the agent card with a plug MAC only, and detaching a stopped coding machine's sessions keeps the machine's own card.

- Company Computers plug into the node's agent exit too (E6; `deploy/first-node/RUNTIME-AGENT-EXIT.md` §6, `deploy/agent-exit/ROLLOUT.md` step 7; merges with the office image's half, #926): the office guest plan has a second NIC, `plug`, a port of `qagent0` (`agentPlugCard`), and `network` keeps the first card for the computer's own services. The creation worker (after checking the VM is absent) and the reset worker (once the old root is gone) get its MAC from the node's plug tool right before each create (claim kind `office`) and inspect their gate again after it. The journal refuses a create without the MAC before its claim, and the guest check accepts the plan's card with one plug MAC, the same in both views; a VM made before has one card and is refused as drifted. The office gate requires `qagent0` as an unmanaged bridge (read without the 64 KiB limit, since its `used_by` grows with the node's plugged machines) and refuses an offices project that LXD would refuse the card in (one LXD restricts, unless it has `restricted.devices.nic=allow` and a `restricted.networks.access` that is empty or names `qagent0`); allowing it changes the project's digest, so the office policy is re-enrolled. Both office units join the group `qorpera-agent-plug`, so the agent exit must be installed first, and the fleet installer refuses the installed units (it never replaces a differing file) until they are removed.
- The coding executor reads the guest's observation v3 and calls a session busy by the one idle rule (`idleRuleBusy`, `@qorpera/contracts` idle-rule; 2026-10-03 amendment, item 1): at least 5% of one core, or 512 KiB read or written in 30 seconds, between two looks of the same boot. Its own copy of the 5% share is gone. Busy reaches SQL as before (`qorpera_keep_coding_attachments`). It needs a coding image whose storage helper publishes v3.
- The node host mints, binds and delivers each native host's identity credential (G2-3bc; `deploy/first-node/RUNTIME-NATIVE-HOST-KEY.md` "G2-3bc"): the LXD provider for a job guest (journal `credentials.nativeIdentitySha256`, required; bound as `job_guest` after the reservation), the login gateway for a sign-in or refresh guest (`bridge.json` is `{token, identity}`; bound as `login_guest`; once the guest's agent answers it also pushes the identity's recovery state, which a login guest may not read, and the guest's purpose; the gateway configuration requires `supabasePublishableKey`, a publishable key), and the shared execution service per run (journal `nativeIdentitySha256`; bound as `exec_slot` through its entry point; written into the slot's credentials and the runner's `native_identity_credential`, whose configuration is removed with the runner). Guest images from before G2-3bc refuse the new credential list, so a node takes the image first.
- The node observer also posts the node's agent exit health (E2d; `deploy/agent-exit/ROLLOUT.md`): every 5 seconds it reads `/run/qorpera-agent-exit/health.json` and posts whether the exit is healthy, how many problems it saw and when it checked (`qorpera_observe_runtime_node_agent_exit`, never the problem texts). A node without a healthy, current exit takes no new Company Computer or agents' machine, and no new member's coding machine (`NODE_AGENT_EXIT_UNHEALTHY`, which the coding executor and node admission treat as a wait for room).
- The coding executor configuration is `qorpera.coding-executor-service/v7`: `guest.resourceProfile` names only `maxLogBytes`. A turn no longer detaches its session: the host records the session's attachment (`qorpera_attach_coding_session`), and `CodingExecutorHost` gains `endTurn` and `keep` and loses `refreshLease`.
- Coding executor configuration now requires v6 with a separate peer command listener and explicit peer credentials. Environments can enroll multiple executor owners; retained machines and NAS writers remain pinned to their original host.
- New office VM operation events use v2 timestamped records. The current reader preserves v1 history and accepts mixed chains, but older provider binaries cannot read newly appended v2 records; automatic downgrade or journal conversion is unsupported.
- Node admission now requires a receipt from the enrolled complete-host inventory publisher. Hardware-only ready reports and observations for an older node policy cannot authorize new starts. Legacy VM metadata, unregistered computers and changed physical/configuration identities require explicit reconciliation.
- Login VMs now require company and node admission and use one immutable allocation per sign-in attempt. Completed or revoked attempts delete the VM before releasing capacity, retaining the Compute Identity disk. Legacy identity-keyed guests are preserved and refused pending explicit inventory reconciliation.
- Native job VM creation and first boot now require enrolled node/host/resource policy and fresh capacity admission. Existing native journals without node placement block new acquisitions until their physical resource limits and retained allocations are reconciled.
- Office creation, first boot and retained-VM resume now require explicit node/provider enrollment and fresh node admission. Missing configuration or observations refuse physical dispatch; existing company reservations are retained.
- Unreleased VM power-off requests now use `qorpera.lxd-office-power-off-request/v2` and bind a verified root stop-history manifest. Prior unbound shutdown records are preserved and refused, with no automatic reconstruction.
- The unreleased office guest binding now uses `qorpera.lxd-office-guest/v2` and requires an enrolled provider ID and policy digest. Old office journals/bindings are rejected without automatic conversion. Office start reservation/check RPCs require the same provider identity; the original unbound functions are private. Native runner bindings are unchanged.
- The unreleased office physical policy now uses `qorpera.lxd-office-physical-policy/v2` and requires exact project, network and storage-pool configuration digests. Prior policies are rejected without implicit enrollment or journal migration.

### Added

- The coding executor runs a session on the folder model (F3 step 5g-6a; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md`): with `LxdCodingExecutorHostOptions.folder` (the session's views, the folder service's control socket, the LXD exec stream client, optional repositories and an `onMount` hook), a turn plugs, configures and seeds nothing in the guest. It wakes the member's machine as before, refuses a session SQL gives no user in the guest agent's range (`CODING_FOLDER_SESSION_UID_MISSING`), waits for the machine's LXD agent, reads the boot and the start it came from (`codingMachineStartOperation(journalRoot, plan)`, the last succeeded effect in the machine's journal, which must be a start: `CODING_MACHINE_START_UNCONFIRMED`), attaches the session in SQL and then mounts its view for that attachment, held until the attachment's end (a later turn on the same boot of the machine attaches under the attachment its view's record names, so also after the executor restarted, and keeps that view; a view the record names from an earlier boot first ends, while its attachment is still the live one, and a turn whose old view ends unsaved or unclosed fails with `CODING_FOLDER_VIEW_UNSAVED` or `CODING_FOLDER_VIEW_CLOSE_UNCONFIRMED` before it attaches; a view on another machine is left to SQL), and lastly asks the session's repositories where its commands start (`CodingFolderRepositories.prepare`, `coding-folder-repositories.ts`; until 5g-6b none, at `/company`). Its commands run through `LxdCodingFolderCommandTransport` as the session's user, at that place, with Git's settings for the company folder (`CODING_FOLDER_GIT_ENVIRONMENT`), under the boot's start and kept in the session's custody folder. A finished turn first asks the folder service for the machine's boundary (`CODING_FOLDER_BOUNDARY_HELD` unless it released every read and every view's report saved every changed path, `codingFolderViewSaved`), then has the repositories export the bundle it pushes and publishes as before (none: no change, or `CODING_FOLDER_EXPORT_EMPTY` for an open pull request). The keeper asks the guest agent which commands each session runs and reports those the host kept a start of (`codingFolderKeptCommand(custody, workerId, commandId)`), a session busy while one runs, and renews no guest lease. Taking a session off cancels its commands through the guest agent, has the agent quiesce the session (`LxdCodingGuestClient.quiesce`: nothing of it runs, its user manager included, and its view stays mounted; one the agent can't confirm quiet keeps its view and fails the take-off), ends its view (`CODING_FOLDER_VIEW_UNSAVED`, `CODING_FOLDER_VIEW_CLOSE_UNCONFIRMED`) and has the agent stop the session; a machine's sleep cancels its sessions' commands, quiesces them, stops its slices and ends its views before the power-off, and reports a view it did not save, a session not confirmed quiet or views whose records can't be read once the machine is asleep. `CodingFolderViews` keeps each view's pass in a record on the NAS (`CodingFolderViewsOptions.records`; the executor's is `<journalRoot>/folder-views`, one `<workerId>.json` of mode 0600 in a folder of mode 0700, used only while the NAS is mounted, naming the view with its pass and the attachment and machine boot it was opened under; a write's temporary file that a dead process left there is removed at the folder's next use), so a restarted executor mounts again, ends or replaces the views the last one opened. `held(workerId)` names a session's view's machine, boot and attachment token from its record, and `attach` (whose session now names the machine's boot, `bootId`) also resolves with how a view it replaced ended (`replaced`), which `onMount` gets too. `attach`, `end` and `endMachine` reject with `CODING_FOLDER_VIEW_RECORD_FAILED` when a record can't be read, written or removed, and an `end` whose caller stopped rejects with the caller's reason and keeps the view's record for a later end. The executor's configuration may name the folder model (`folder`: the guest agent and folder program it carries, each a path on the node with its SHA-256, and optionally the control socket), and logs `coding-executor-folder` at start and `coding-folder-mount` for each mount. The idle sample, `security.devlxd=false` and the image's own checks (its helpers, watchdog and self-update) are not on the folder model yet.
- A coding session's folder view (F3 step 5g-4; `coding-folder-views.ts`; nothing calls it yet, the executor does from 5g-6a): `CodingFolderViews.attach(session, until, signal)` makes sure the machine has the executor's guest agent and folder program (`install`: one `sha256sum` in the machine, and whichever differs is written beside its place and renamed over it), opens the session's view with `qorpera_folder_view_open` (`coding_session`, anchored on the session and its attachment's token) and has the guest agent mount it for the session's user, the pass only on the agent's stdin. A later turn of the same attachment mounts the view it holds again; a new attachment, or a view the node closed, first ends the old one. A refused open rejects with `CodingFolderViewRefused` (`CODING_FOLDER_VIEW_REFUSED:<code>`: `ATTACHMENT_NOT_CURRENT`, `FOLDER_UNAVAILABLE`, `PRINCIPALS_UNAVAILABLE`, `AUTHORITY_REQUIRED`, `VIEW_INVALID`, or `VIEW_CLOSED` when the node closed the view under its mount); an invalid id, a uid outside the sessions' range or an invalid `until` rejects with `CODING_FOLDER_VIEW_REQUEST_INVALID` before anything; an agent's answer that is not one rejects at once with `CODING_GUEST_ANSWER_INVALID`; an open or a mount with no answer is tried again until `until` (`CODING_FOLDER_VIEW_UNCONFIRMED`, `CODING_FOLDER_MOUNT_UNANSWERED`). `end(workerId)` and `endMachine(machineId)` ask the folder service for the views' final boundary and then close them, and say whether each was saved and closed; they never reject (from 5g-6a, they reject when a view's record fails). Saved means the boundary released the reads and the view's report says every changed path `saved` and was not refused whole (`codingFolderViewSaved`): a commit with no answer yet, a path waiting on an open file, a denial, a conflict or a refusal is not saved, and the close loses it. For that, `CodingFolderControl.boundary` checks each view's report for shape and gives how many of its paths are not saved (`unsaved`) and its whole refusal (`refused`), not the paths themselves. Passes stay in the process's memory (from 5g-6a, in records on the NAS). `CODING_HOST_RPCS` gains `qorpera_folder_view_open` and `qorpera_folder_view_close`, and the coding control (`deploy/coding-worker/control.ts`) answers those two methods' refusals with `CodingControlRefused` and the core's own words, only for the messages the core raises for them with 42501 or 22023 in a complete PostgREST error body; every other failure stays `CODING_CONTROL_UNCONFIRMED`. `LxdUnixClient.pushInstanceProgram(project, name, path, content, mode)` (`LxdInstanceProgramClient`) writes up to 16 MiB of bytes as root's file, only directly in `/opt/qorpera-guest/` or `/opt/qorpera-folder/`.
- The coding guest agent's host client (F3 step 5g-2c; nothing calls it yet, the executor does from 5g-3): `LxdCodingGuestClient` calls the agent in one member's coding machine, one verb per `execInstanceStream` (`mount`, `run`, `output`, `cancel`, `stopSession`, `status`). It checks the request with contracts' `parseCodingGuestRequest` and sends it as the exec's stdin (at most 64 KiB), and gives each verb a deadline that covers the agent's own waits (`output` adds its request's `waitMs`). The answer is the guest's word: it is read only after the exec ended with exit 0, as one strict UTF-8 JSON line of at most 128 KiB checked against its request, followed by nothing but, for `output`, exactly the bytes it names (`CodingGuestOutputPage`). A refusal rejects with `CodingGuestRefused` (`CODING_GUEST_REFUSED:<code>`, so the guest can never answer with a host error), a crashed agent with `CODING_GUEST_FAILED`, any other answer with `CODING_GUEST_ANSWER_INVALID`, and a bad request with `CODING_GUEST_REQUEST_INVALID` before any exec; no error quotes the request or the answer. `scripts/package-coding-guest-agent.mjs --out <new-directory>` bundles the agent (runtime's `cloud-coding-guest-agent`) into one `agent.mjs` of at most 256 KiB with a manifest of its SHA-256, for the executor to push to `/opt/qorpera-guest/agent.mjs`.
- The LXD client runs a command over LXD's exec websockets (F3 step 5g-2a; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md` "Commands and sessions"; nothing calls it yet, the coding guest agent's host client does from 5g-2c): `LxdUnixClient.execInstanceStream(project, name, {command, stdin, maxStdoutBytes, maxStderrBytes, timeoutMs})`, a separate capability (`LxdInstanceExecStreamClient`), runs it non-interactive with `wait-for-websocket` and `record-output: false`, as root in `/` with LXD's default environment. It writes `stdin` (at most 64 KiB) to the command and closes it, and reads stdout and stderr (each at most its bound, up to 8 MiB) off their websockets, so neither the input nor the output is in an argument, a request body or LXD's output log on the host. The control websocket stays unconnected: a call that ends early (its deadline or signal, an output past its bound, a stream that ends without its end message) closes the stdout websocket, on which LXD kills the command, and fails. The deadline and the signal also stop a websocket handshake LXD has not answered yet. `NodeWebSocket` takes binary messages (`binary` handler, `sendBinary`), a Unix socket (`socketPath`) and a `signal` that stops a pending handshake (its request is destroyed and the connect rejects at once); without a `binary` handler it drops them as before.
- The coding executor tells every session attached to a member's machine stopped from outside before it does anything else to that machine (F3 5g-1b; migration `20260930431000`; `deploy/coding-worker/README.md` "Machines stopped from outside"). `qorpera_record_coding_machine_stopped` ends each attachment with the commands last seen running there, stopped for `MACHINE_STOPPED`, which the session's thread and its next turn's context show. The executor names the stop by the start it ended (the LXD operation in the machine's journal), and SQL keeps each stop once, so a retry or a late request of an abandoned try ends nothing. The session folders then come off while the machine is stopped (under the turn's run receipt, or the sleep's stop custody), so the next turn starts it with only its own session plugged in again. A turn whose record fails starts nothing and the next one tries again. The keeper observes only running machines, so the stop is recorded by the next turn, sleep or removal. Rollout: the runtime that knows `MACHINE_STOPPED` goes out before or with this executor.
- The coding executor can ask the folder service's control socket (F3 step 5g-3b; `coding-folder-control.ts`, 5c's `/run/qorpera-folder-control/control.sock`): `CodingFolderControl.boundary(machine, final, signal)` asks a coding machine's boundary and returns what came of its reads (`released` alone lets output go) and each view's error code, and `restarted(machine, signal)` says the machine stopped and starts again. Each request goes on a connection of its own; the answer is read whole, to the service's end, as one strict UTF-8 JSON line of at most 16 MiB, checked against the request, and never quoted in an error (`CODING_FOLDER_CONTROL_REQUEST_INVALID`, `_UNAVAILABLE`, `_TIMEOUT` after 20 s, `_ANSWER_INVALID`, or `CodingFolderControlRefused` with the service's code). Nothing calls it yet: the folder command transport (5g-3c) and the views (5g-4) do.
- The folder model's command transport (F3 step 5g-3c; `coding-folder-command-transport.ts`; nothing chooses it yet, 5g-6 does for sessions on the folder model): `LxdCodingFolderCommandTransport` has the NAS transport's `start`, `read` and `cancel` and answers the same v2 receipts. The guest agent runs the command as the session's user in the session's cwd with the session's environment and the command's secrets, and keeps its output in a ring. Each call pulls up to 8 pages of it, asks the folder service for the machine's boundary, and keeps the output only when the machine's reads are `released`; until then the command shows `running` and nothing of it is kept. The output is masked (`CodingCommandSecrets`, `coding-command-secrets.ts`: a command's environment and its mask; none by default) and kept in the worker's custody on the host (`host-commands/<command>/`: `request.json` and `outcome.json` linked once, `progress.json` replaced whole, `output.log` up to the profile's limit), where the machine can't reach it; every file is the executor's, opened without following links, and a custody that isn't is refused (`CODING_COMMAND_CUSTODY_UNPROTECTED`). Pages and receipts are read from what was kept. Bytes the ring dropped count in `log.gapBytes`. A command the guest no longer has ends `machine_stopped` when the machine started again since the command did, and `unconfirmed` otherwise. Each call takes at most 25 s of its own and is serialized with every other call for the same command in the process. The mask holds back a tail that could still start a value, and the next call pulls that tail again: `progress.json` keeps how much of it was already shown as `***` (`masked`), and that call's mask takes over there (`CodingSecretMaskStream.masked()` and `resume()`), so a match already masked stays masked and the `***` isn't written twice. A gap starts the matching afresh, but the bytes past it that the kept `***` already covers stay behind it. That the guest has no such command is the guest's word too, as is the count of its bytes lost with it: a command the guest doesn't have shows `running` until the machine's reads are released, and only then ends or counts them in `log.gapBytes`, once even when a call stops before the outcome is linked.
- Member coding machines run only under a host lease (5g-1; `deploy/coding-worker/README.md` "Host leases and the host watchdog"): `CodingHostLeases` keeps one 90 s lease per machine under `/run/qorpera-coding-host` (`qorpera.coding-host-lease/v1`, boot id and uptime, never the wall clock). `LxdCodingExecutorHost` writes it before it starts a machine, renews every machine SQL still reserves on the node on each keeper pass (a lease it cannot write is that machine's `keep` failure) and drops it once a sleep has stopped the machine or a removal deleted it. `runCodingHostWatchdog` force-stops every member machine VM in the executor's project that is not stopped and has no live lease, and stops nothing when LXD cannot confirm its inventory; `qorpera-coding-host-watchdog.service` and its timer run it every 5 s, independent of the executor and SQL, and ship disabled.
- A coding machine's secret values can be masked in its output (F3 5j-2; `coding-secret-mask.ts`): `CodingSecretMask` holds a machine's values (8 bytes or more, `CODING_SECRET_MASK_MINIMUM_BYTES`) and hands out one `CodingSecretMaskStream` per byte stream, which writes `***` for the exact bytes, their base64 in both alphabets (padded or not, at any offset in a longer run), their URL encoding (`%XX` in either case, `+` for a space) and newlines a terminal wrote as CR LF, across chunk boundaries. `push` holds back only a tail that could still start a value (`pending` bytes), and `end` lets it through. Nothing uses it yet: 5j-4 wires it into commands and terminals.

- `coding-setup.ts` reads a repository's setup file for its coding machine (5h-1; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md` "Setup file and snapshots"): `readCodingSetup` takes the first of `.qorpera/environment.json` (Cursor's keys), `.cursor/environment.json` and `.devcontainer/devcontainer.json` at one commit through a read port (the code host's `git show`, 5e), maps it under a strict schema to one `CodingSetup` (base, user, initialize, install, start, terminals, ports, environment (devcontainer's `containerEnv` and `remoteEnv` kept apart, with `remoteEnv`'s unsets), repository dependencies, features, MCP servers), and gives its setup digest: SHA-256 over a versioned, length-framed canonical form of the setup with each named Dockerfile's path and bytes. Comments are read in all three formats and trailing commas in devcontainer.json only; a duplicate key, an unknown key, a wrong value, a path out of the repository, a compose devcontainer or a missing named Dockerfile refuses the file, and the session gets the empty setup (digest `e3b0c442…`, 5a's default) with every problem reported, so the attach never fails over a setup file. Keys the platform decides (`snapshot`, `egressAllowlist`, devcontainer's mounts and privileges, …) are ignored with a report.
- The records of coding snapshots (5h-2; migration `20260930435000`; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md` "Setup file and snapshots"): `CodingSnapshotRecords` asks SQL at a session's attach whether this node's snapshot of the member's repository is current for the setup digest and commit, whether a build of it runs (one per member and repository, on any node), whether this node's last build of them failed (with its masked log), or starts a build lease; it renews and finishes the build (`ready` with the image's fingerprint retires the node's older snapshot, `failed` keeps it, `abandoned` is tried again), lists the snapshots whose images the node may keep and which are due for removal (the retired ones; the list retires the ready snapshot of a member who left the company), and records a removal. `codingSnapshotLog` keeps a log PostgreSQL can hold, its last 64 KiB as a JSON string, the form the coding control carries it in. The coding control lets `CODING_SNAPSHOT_RPCS` through. Nothing calls it yet: the builder and the setup at attach are 5h-3.
- The code host's jobs (5e-1; `deploy/first-node/RUNTIME-FOLDER-CODING-MACHINES.md` "The code host"; `code-host-jobs.ts`): every git command on a company's code area that must not run as a member's root, run through a `CodeHostShell` (LXD exec in the code host VM, 5e-2) with the pinned git, no system or global config, every setting in the command's environment (hooks, fsmonitor, filters and submodules off, `safe.directory` only for the code area), and the repository's config put back to the platform's before each job (`include.path`, `extensions.worktreeConfig`, filters and `core.worktree` dropped; `config.worktree`, `commondir` and alternates removed; each restore reported). `seedCodeArea` fetches the broker's bundle of the default branch into a scratch repository on the code host's disk, refuses names that are not UTF-8 or NFC, names in one folder that differ only by case and files over 256 MiB (naming the paths), repacks into packs under 256 MiB (a pack of 256 MiB or more is refused), then indexes them into `repo.git` and moves the base ref (compare-and-swap) and `main/` (a locked, detached worktree) together: one `update-ref --stdin` transaction holds the base ref's lock while `main/` moves and commits only after it, so a racing seed fails rather than leave `main/` behind the base; `readCodeAreaBase` reports the base only while `main/` is at it. `addCodeWorktree` adds and locks a session's `worktrees/<workerId>/` on `qorpera/coding/<workerId>`. `exportCodeBranch` exports a complete bundle of the session's own branch only. `collectCodeGarbage` holds new leases in `repo.git` with the core's gc block, waits until none is held, packs every ref but the sessions' and runs gc. `withCodeCommit` reads one commit's files by path for 5h's setup file (`missing`, `file` or `other`, cut after `maxBytes + 1`). A base branch `qorpera`, `qorpera/coding` or under `qorpera/coding/`, in any case (the folder's names), is refused.
- The quiet coding check-ins join the shared folder drains (C3c; migration `20260930107500`; `deploy/first-node/RUNTIME-COMPANY-FOLDER-C1C.md` §6.20): `CLOUD_FOLDER_DRAINS` runs `coding_checkins` (company limit 8) after `machine_checkins`, asking the run that started a folder-v2 coding session, once per mark, whether a session quiet for 1, 3 or 7 days can be archived; the edge function's `FOLDER_DRAINS` maps `coding_checkins` to `qorpera_folder_coding_checkins_due` and `qorpera_folder_coding_checkins_company` (maximum 32). An orchestrator ahead of its edge function gets the 400 and pauses that drain alone.

### Changed

- A member's coding machine that LXD shows stopped after its settled start (the host watchdog's forced stop, a poweroff inside, a node reboot) is stopped, no longer `recovery-required` (F3 5g-1b; `deploy/coding-worker/README.md` "Machines stopped from outside"): the next turn starts it again on the same disk, and a sleep or removal goes on. Only LXD's own state counts; the guest's word does not. Each such stop is written next to the machine's journal once per start (`outside-stop-<segment>-<sequence>.json`, schema `qorpera.coding-machine-outside-stop/v1`, with its `count`), and the 4th outside stop within an hour leaves the machine `recovery-required` for good (an operator settles it). Company machines and the legacy per-session VMs keep their rules.
- Office fleet units now require `qorpera-node-host-namespace.service`, which the node observer installs on every node, instead of the single-office installer's `qorpera-office-host-namespace.service`. Both run the same helper and write the same namespace record.
- Native office routes may name every computer of a company (`/office/{companyComputerId}/native`); still one route per company environment, and its token is accepted by all of that company's computers.
- Warm conversations (contract amendment 2026-09-27), off unless `QORPERA_SHARED_EXECUTION_WARM_IDLE_MS` is set: after an attended run the shared execution service parks its slot (runner stopped and wiped, capacity released, native host kept with its scratch and bridge credential) for the conversation's next run, which claims it after the identity is verified again and starts only its runner. A changed identity, a stopped host or a passed window evicts the slot; under capacity pressure the slot parked longest gives way.
- The orchestrator asks for new work on every poll (250 ms) and reconciles (control renewal, occurrence reconcilers, expired claims, provider, retained claims) every `QORPERA_RUNNER_ORCHESTRATOR_RECONCILE_MS` (default 2 s) instead of before every claim; a failed reconcile still blocks claims and is retried on the next poll, a failed dispatch brings the next reconcile forward to the next poll, and retained claims keep their priority until they have been re-read. An assignment that races a runner's activation is retried after 50 ms, doubling to 3 s, instead of after 250 ms.
- The one-run LXD provider no longer runs everything under one provider-wide lock. Each acquisition's journal has its own lock (held through that VM's boot), so independent runs create, start, bootstrap, deliver and stop side by side; runs of one Compute Identity create its shared volume under a per-volume lock. A reconcile pass works on up to 8 journals at a time; a journal an acquisition, delivery or stop holds is looked at again at the end of the pass once they let go of it, or on the next pass. Within a pass, one unreadable or stuck journal no longer stops the others (an unreadable journal still refuses new starts and stops, as before). What bounds concurrent starts is unchanged: the node ceiling, admitted by the database under the node row's lock right before every create and start; the capacity inventory check before a new start is unchanged too. Measured with a Unix-socket LXD fake at a quarter of node 1's boot time: 4 queued runs were all ready after 4.4 s instead of 17.4 s.
- The orchestrator reconciles in a lane of its own: asking for new work no longer waits for a reconcile pass that is still running (with the old provider a pass waited for any VM that was booting, so a node claimed nothing during a boot). Claims still wait for the first pass, stop while the latest pass failed (it is reported and retried after one poll interval) and, after a failed dispatch, wait for the next pass; retained claims are re-read after every successful pass.
- The shared execution service starts a sandbox's runner unit right after its host unit (systemd orders it after the host's start) and waits for both health endpoints together, polling every 25 ms; the assignment is still delivered only once both answer.
- The shared execution service defers a run whose Compute Identity volume is not attached to the execution host (`NODE_IDENTITY_ELSEWHERE`, this orchestrator only) before it takes a slot, provisions a runner row or reserves capacity, so a login that just moved to the node waits for its volume instead of failing its run. The wait is bounded: after two minutes the start fails like any other.
- Shared preparation/configuration journal mechanics while preserving existing preparation authority and event bytes. Configuration records additionally bind the acknowledged preparation observation and use separate schemas and directories.
- Connected the adoption copier to repeated creation-journal, stopped-VM, physical-policy and cloud mapping checks. A root-protected, boot/plan-bound infrastructure maintenance handoff is required at each checkpoint; it records operator responsibility for excluding other NAS writers and does not acquire a remote lock. Copy completion still grants no boot or activation.
- The orchestrator accepts a run without a Company File snapshot id and substrate version id, as a `folder-v2` run has (folder core C4, tolerant before any such run exists): both or neither, each checked when present; `CloudRunnerWork.substrateVersionId` and `companySnapshotId` are optional.

### Fixed

- Failed or forgotten office service-stop attempts without a completion retry the same retained command after 30 seconds, doubling to ten minutes. Each retry has its own observed dispatch journal; a persisted schedule survives provider restarts and retains only the original and latest attempt directories. Pending operations are not repeated, and stop acknowledgement still requires protected completion plus fresh inspection.

- A journal that never starts again no longer stops the node's claims (4–6 Oct 2026: node 1 claimed no run for two and a half days). The LXD provider's reconcile no longer demands the recovery volume of a stopping, stopped or lost run whose guest is gone, and it still releases that run's capacity; a run whose guest exists, or that may start again, still has to name its volume. A dead journal (stopping, stopped or lost, its own guest gone in LXD) that still fails its share of a pass, for example one this build cannot read because it was written before G2-3bc's identity credential digest (node 2), is named in the log at most once an hour (`dead journal kept: acquisition=… stage=…`) and no longer fails the pass; the capacity inventory before a start, a stop's runner lookup and the prior-attempt scan pass over it too (the scan still counts its attempt). Every other failure is named in the log as `reconcile failed: acquisition=… stage=…`, with the failed call's function, status and code where there is one, and never the error's text.
- The code package loader's locked child, which reads the protected packet, now runs with ignored stdio like the other office controls. Before, it inherited the exec's recorded streams, so its tools' JSON results and any uncaught stack trace were stored in LXD's host exec logs. The loader now writes nothing on success and only `OFFICE_CODE_PACKAGE_LOADER_UNCONFIRMED` on failure; `bootstrap.cjs` and `measure.cjs` no longer print their results, which the provider already reads back from the files they publish.
- Fixed the exec host reusing a machine key for a later attempt of the same run on the same slot: the key now names the attempt's acquisition id, since a released allocation keeps its key.
- Stopped the company computer provider from suspending the same node demand on every lifecycle pass.
