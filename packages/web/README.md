# Qorpera web client

This is the product web application. It uses member authentication and the shared `@qorpera/cloud-client` SDK; execution, storage authority and computer lifetime belong to the headless cloud runtime.

From the repository root, install with `npm install --ignore-scripts`, then run `npm run build --workspace=@qorpera/web` or `npm run dev --workspace=@qorpera/web`. Both commands build the SDK dependencies first. `npm run check` checks the web app separately with DOM types and verifies its executable dependency graph contains no runtime, provider or desktop implementation.

The conversation Computer panel discovers the company's computer, reads its state, submits an explicit start intent and opens an explicitly requested screen viewer. Viewer connections are bound to the current company, member, staff screen and physical generation. Closing the panel, changing company or signing out releases the viewer; it does not stop cloud work. Private or transitioning computers do not offer shared viewing. The renderer and noVNC source reuse the checksummed browser assets in `packages/member-web/ui`; the build verifies those hashes and includes the noVNC license.

Cloud configuration contains only public endpoints and a publishable key. `officeViewerOrigin` is a separately configured `wss://` origin with no credentials, path, query or fragment. The app does not infer it from an object gateway or accept it from a server response. Until the deployed viewer origin is verified, the default preview configuration leaves viewing unavailable. Unconfigured preview builds allow a local override of the complete `CloudConfig` under `qorpera-web-cloud-config/v1`.

For deployment, put the exact `projectUrl`, `publishableKey`, `objectGatewayUrl` and `officeViewerOrigin` in a public JSON file. After building the SDK, run `QORPERA_WEB_CONFIG=/absolute/path/public-cloud.json node packages/web/scripts/build.mjs --release` from the repository root. For Cloudflare Pages, set `QORPERA_WEB_CONFIG_JSON` to the same public JSON instead of providing a file, and use `npm run build:release --workspace packages/web`. File and JSON inputs are mutually exclusive. The release build requires all four fields, rejects unknown fields and unsafe origins, and compiles the endpoints into the app. It generates `_headers` from those same endpoints and ignores stored browser overrides. An explicitly configured preview also locks its endpoints. Publish the generated `dist` directory, including `_headers`; the source header file is a build template. `web-deployment.json` records the public configuration and checksums of the headers, HTML and entry bundles. This manifest describes a build, not successful live acceptance or release authorization.

Provider sign-in additionally accepts an optional `nativeProviderLoginUrl`: an exact public HTTPS base URL ending in `/`, without credentials, query or fragment. The exported `HttpNativeProviderIdentityBridge` resolves its `login` child route. The configured origin is included in the generated CSP. No default is inferred: enable this field only for the accepted browser gateway. The existing project route is `/functions/v1/native-provider-login/login`, but its current proxy lacks browser CORS/preflight support. Deployment must support the exact approved web origins, POST preflight with Authorization and Content-Type, and CORS on success and error responses. It must keep the upstream service private. A configured URL alone does not prove gateway readiness.

## Acceptance status

The Computer panel offers one action, Open computer: it starts the Company Computer when it is off, opens the agent's screen if it has none, and shows the live desktop in a movable preview; Enter takes the browser full screen with the guest screen inside a thin frame, and Back to thread (or leaving full screen) returns to the preview. When the browser refuses full screen the same frame opens over the thread. Every agent has computer access by default; there is no permissions form and no private member browser (see DECISIONS.md, 2026-09-17).

The product composer atomically submits member input and sponsorship through the exported `NativeSubscriptionControlPlane.requestSessionTurn` API. Room startup refreshes account usage through a separate, bounded identity-host operation, then the cloud selects the eligible account with the greatest remaining allowance in its tightest limit window. The account stays with that member's conversation across turns and reloads; exhaustion follows the runtime's fenced sponsor handoff. Unknown usage ranks after measured allowance and is never presented as a full balance. Settings → Connections shows provider email, connection identity, remaining-usage bars and reset times, and can add or revoke accounts. With a configured public login gateway, Connections starts provider sign-in using the exported compute-identity, login-admission and identity-bridge interfaces. Only the interaction link, device code and expiry reach the view. Login and refresh capabilities stay in memory; adding an account enables it for the member's messages. An uncertain login requires discovery refresh and an explicit new attempt, because SDK login admission generates a new capability each time and cannot safely replay the same login ID. Selected PNG, JPEG, GIF and WebP images are uploaded first through the shared member attachment API, bound to the same member, conversation and input ID. The protocol allows up to five images totaling 8 MiB; other file types use Company File. Account, company, route and write permission are checked after token refresh and before accepting a response. Sending has a bounded deadline, never retries automatically, and retains request identity, sponsor authority, draft and immutable selected files for an explicit retry while the company remains open. Starting a new request requires an explicit action after uncertainty because the original may have been accepted. Canonical member-input images can be previewed on demand after byte/hash verification; transcript URLs never become fetch destinations. This submits work to the runtime; it does not execute work in the browser.

Conversation run controls use exported `CloudSessionRunControl` reads and exact observed-run cancellation. Execution history uses SDK turn provenance; a materialized request is not presented as completed work. Reconnect and explicit refresh reconstruct cloud state. Disposing a view cancels local requests only. Track A source identity, bundle and release checkpoints are recorded in [RUNTIME-CHECKPOINTS.md](RUNTIME-CHECKPOINTS.md); final product acceptance must consume its completed runtime release.

Team-room conversations use the documented `qorpera_list_company_rooms` and `qorpera_post_company_room_message` member contracts. The client observes the exact room/session/environment and active human membership, then submits one text input with the selected sponsor; the cloud owns recipient wakes and delivery. Room posts retain their destination and sponsor on an uncertain retry and cannot upload images. The single-staff run-control and turn-provenance APIs do not apply to room fan-out. Current member transcript reads expose a run ID but no historical staff speaker identity for room replies; the UI reports that absence instead of attributing replies to the room title, human requester or a current activity observation. Named room-speaker acceptance requires an authoritative member-readable projection from Track A.

Company execution settings use Track A's documented authenticated member RPCs with the SDK's bounded request helpers. Owners/admins can explicitly pause/resume the company and change observed-version monthly spend/token and hourly wake ceilings. SQL owns authorization, enforcement and accounting; this UI does not implement a scheduler or budget engine. Ceiling accounting may include reservations and is not an invoice or exact model-token meter. The separate Policy tab remains a behavior-policy preview.

Company File uses the shared governed path APIs for current reads, versioned text edits, selected-file uploads, verified browser downloads, exact proposal review, shared exports and optional recent activity. It preserves drafts on cancelled navigation, binds all operations to account/company access, and offers explicit reload recovery after a conflict or uncertain response without replaying a change. Snapshot history remains separately accessible. Browser source is typechecked without Node globals; the Node-hosted tests have a separate typecheck.

This is an integration candidate, not launch acceptance. Production HTTPS/CSP, normal human sign-in, actual message and attachment transfers, File operations, presence and screen viewing, physical privacy and revocation, client-independent work, NAS durability and governed reset remain live acceptance gates. Local fixture tests do not establish those live properties. The `packages/member-web` proof interface does not substitute for acceptance of this app.

macOS/Windows release and installation proofs are deferred until after the web launch, alongside Azure.


## Cloudflare Pages release build

Pages settings for the integrated candidate:

- Repository root: `/`; output directory: `packages/web/dist`.
- Build command: `npm ci --ignore-scripts --no-audit --no-fund && npm run build:release --workspace packages/web`.
- Environment: `NODE_VERSION=24`, `SKIP_DEPENDENCY_INSTALL=true`, and `QORPERA_WEB_CONFIG_JSON` containing only the approved public endpoints and publishable key.
- Configure the production and preview environments explicitly. Never use a service role key, Cloudflare credential, native-login capability, or private gateway address in the public JSON. Native sign-in needs the optional `nativeProviderLoginUrl` public base ending in `/`.

The release command checks the frozen runtime manifest against source, builds the shared SDK declarations, and produces a release artifact from a clean Git checkout. JSON environment configuration avoids creating untracked configuration files inside that checkout. `web-deployment.json` records the public config and measured source/runtime identities. GitHub's checks-only workflow builds against reserved `.invalid` endpoints and cannot publish those artifacts.

The Pages production branch is deployment authority: pushing to it can publish immediately. Before advancing it, complete runtime/SQL activation and gateway/browser preflight checks, confirm the exact production configuration and release build command, and retain the previous deployment ID. After publishing, verify the manifest is JSON with the expected commit, bundle identity, and file hashes; verify the served CSP and perform authenticated web acceptance on the canonical app origin. A Pages preview origin does not grant viewer or native-login access by itself.
