# Company41 runtime rollout tooling

This source replaces the lost scratch-only packet builders. `templates/` derives from the preserved v4 controller/files/transport and transcript-recovered v5 builder, contract, SQL and tests, including the v6/v7 broker-login and bundle-version corrections. Historical execution windows and release approvals are deliberately not copied.

Run `node --test scripts/runtime-rollout/create-packet.test.mjs` for an isolated generated-packet proof. The test creates a synthetic clean detached git repository, runs the generated controller/transport suite, rejects source and baseline drift, and confirms that a missing SQL rehearsal prevents sealing. It never invokes Supabase or a model.

For a real candidate, `node scripts/runtime-rollout/create-packet.mjs /absolute/reviewed-specification.json /absolute/new-private-packet` creates a disabled packet and verifies it. The specification's exact required keys are in `create-packet.mjs`; they include the current Company41 head, identities, policy before/after versions, initial enablement/reason, baseline and preflight evidence hashes, source commit, new/prior bundle hashes and versions, activation migration, manifest hash and the pinned CLI path. Baseline evidence retains the captured `[{"r":{"count":...,"versions":[...],"activeBundle":"..."}}]` shape. The generator derives the migration delta and retains all 18 production-only ledger versions.

The output must be a new canonical directory. The source must be clean and detached at the reviewed commit. For a single upgrade, the new activation migration must be last in the source delta. An explicit `bundleActivations` specification can instead describe an ordered chain of `{migrationVersion, version, sha256}` entries. Every version advances by exactly one, every activation is in the pending delta with matching source bytes, and the last entry equals the final bundle fields. This supports v13 → v14 → v15 followed by the remaining Step 4 schema migrations. Every wrapper and reconciliation checks the exact intermediate bundle; trailing migrations retain the final bundle. Missing transitions, reordered versions, substituted hashes and unexpected database bundle changes are rejected. SQL remains guarded by before/after state checks inside a serializable transaction. Capture current admission state before preparing a packet; its pause step disables admission and advances the reviewed reason/version.

Run the generated `verify-offline.mjs`, then `rehearse-wrapper.mjs /absolute/pinned-production-schema.sql`. The required schema is the preserved read-only August 29 dump (SHA-256 `aa4c1baf0b3b410361ea18c2107e5e34236ffedbf591c18b97044d95d88e4fc0`); its baseline inventory is versioned beside the runner. It preserves the production-only schema, applies the candidate's baseline migration suffix in disposable PostgreSQL, seeds synthetic target readback metadata, and exercises every wrapper, reconciliation state and replay rejection. Confirmed cleanup precedes the actual `WRAPPER-REHEARSAL.json` receipt. The freezer binds that runner and receipt along with the actual offline tests. Production dispatch remains disabled. A separately reviewed activation successor must bind fresh execution-window, source-acceptance, physical-fence and disabled-installation receipts, with founder approval. No script here signs an image, reopens admission or issues those approvals.

The CLI transport retains the Supabase 2.116.0 SHA-256 pin `42a9fe8b8a266bc0fbde804c08efb75cc0653480e91ba3f20fba1c3c27a7b49a`; restore and verify that executable before production use. Never substitute an unpinned system CLI. Mutations have one local invocation after durable intent. Unconfirmed outcomes require read-only reconciliation and never automatic replay.
