# Computer subscription integration

The initial server catalog contains Basis (185 DKK/month, 74 standard-computer hours), Standard (630 DKK/month, 286 standard-computer hours), and Dedicated (1,592 DKK/month, the actual paid calendar period at standard size). One standard computer is 4 vCPU / 8 GiB. Version 1 normalizes awake elapsed time by `max(reservedCPU / 4vCPU, reservedRAM / 8GiB)`. Half-size computers consume half an hour per awake hour; a double-size computer consumes two. Sleep and login helpers consume zero. This reference matches the documented coding worker configuration; deployment resource policies still pin the actual shape per machine.

All offers default to `active_for_checkout=false`. Separate `runtime_accounting_ready` and `checkout_enabled` flags also default to false. Publishing a tariff alone cannot enable purchases. Companies default to shadow mode; physical observations do not automatically debit paid allowance. Migration `20260927012100` adds operator-configured rollout enrollment: when both readiness flags and the company enrollment policy permit it, new/open founding companies acquire paid mode through the authoritative founding read. Explicit company mode decisions remain intact. These defaults have not been enabled in production by this work.

Each metering epoch pins its allocation, exact instance digest, resource kind, tariff version, and the admitted node demand's CPU/memory shape when available. Unknown shape remains null and nonbillable. Checkpoints are cumulative, replay checked and monotonic; sequence gaps remain explicit. Multiple screens or coding sessions do not create additional machine hours. The node observer/outbox feeds shadow observations; gaps count zero uncertain active time, not guessed uptime. Paid execution additionally requires the protected permits and independent physical guards described below.

Model subscriptions and credentials remain member-bound. Computer pool participation is self-authorized and company-scoped. Founding readiness accepts available funded paid allowance only in paid mode and under the same current pool-consent authority used for reservations. Expired, fully reserved and payment-fenced allowance cannot make a company ready. Explicit operator complimentary access remains supported separately. A Computer Usage owner is a contact/preference; that role alone does not consent to sharing their allowance.

## Allowance kernel and remaining runtime work

Only a canonical paid Stripe subscription-cycle/create invoice issues an allowance bucket. Active subscription status alone issues nothing. A bucket belongs to one member and one paid subscription period globally, so participating in multiple companies never copies the balance. Overlapping periods cannot be funded twice. Dedicated uses the exact invoice line period length (February differs from March); no artificial pooling limits are added.

`qorpera_reserve_computer_allowance` holds a finite integer number of standard-computer microseconds against an exact allocation/epoch. It derives the direct responsible member from the run requester or coding-machine member, then uses currently consenting eligible company members. Shared computers have no arbitrary direct-member bypass; the company's Computer Usage owner may be preferred only with pool consent. Candidate global buckets lock in a consistent order. An insufficient pool rolls back the whole hold. A timeout never releases money while a physical computer might still be running.

`qorpera_settle_computer_allowance` reads an immutable checkpoint and its pinned resource shape/tariff, differences cumulative normalized time, and atomically converts holds to debits while releasing unused allowance. Cumulative rounding happens at microsecond precision, so checkpoint frequency cannot increase the bill. Immutable receipts and exact request replay prevent duplicate debit; exceeding a reservation fails closed and requires reconciliation. Withdrawal prevents new reservations but does not erase usage authorized by an existing hold. `qorpera_my_computer_usage()` exposes only the signed-in member's current paid balance and subscription summary.

**Before enabling paid service:** require completed acceptance for every enabled physical execution path, deploy the restricted accounting monitor and connect it to the operator's alert collector, and rehearse unresolved legacy/dispatched holds and journal-loss recovery. Refund/dispute/credit fences, proportional funding, exact billing-command recovery and a read-only accounting checker are implemented and have separate SQL/Stripe-test evidence. They do not establish deployed monitoring or a complete physical lifecycle pass. Keep both readiness flags and every offer disabled until the reviewed rollout gates pass.

### LXD computer enforcement

The coding permit migration (`20260927010800`) adds protected prepare, describe, bind, checkpoint, renew and finish RPCs. Prepare reserves 300 seconds of execution plus a 30-second stopping margin, normalized to the admitted shape, before physical create/start. It creates a zero-usage epoch and never invents a boot. Binding requires observed physical identity and guest boot. Renewal atomically settles the previous interval and holds the next; failure leaves the original deadline and reservation intact. Exact replay does not refresh a permit's lifetime.

`CodingComputerController` reserves and renews funding and submits physical samples. The separate `qorpera-paid-computer-guard.service` owns paid start dispatch and expiry stop. Its private host journal survives executor failure and uses host boot identity and uptime, subtracting request latency. It needs no database, network, guest or NAS access. Systemd watches the guard independently of the executor. A lost start reply remains unresolved until its actual LXD operation settles; an absent/stopped VM alone does not permit refund while an unknown queued start could still execute. Guard operation receipts reconcile into the existing NAS lifecycle journal without another start dispatch.

The paid meter uses paired host/guest clocks and physical identity. A restart, uncertain observation, changed boot or discontinuity creates a zero-charge gap. It does not reconstruct unobserved time from wall-clock guesses. Settlement after confirmed physical stop charges only proven checkpoints and releases the remainder. The independent node observer must enroll the physical instance before binding; a delayed inventory pass can temporarily refuse binding, and the original guard deadline still applies.

The admission-boundary migration (`20260927010900`) makes mode changes operator-only and requires quiet execution before switching modes. Paid coding run admission uses a version 2 receipt; a host without the paid controller refuses it. Legacy admission paths refuse unfunded execution. Login helpers remain excluded. Stop, detach and deletion custody remain available.

The generic runtime permit migration (`20260927011100`) adds the equivalent host-protected kernel for native and office LXD allocations. It uses the same allowance and sample tables, with immutable source context and independently enrolled provider/host/resource authority. Native begin and runner claim require the exact current, physically bound permit. Office admission (`20260927011200`) retains the existing creation, resume and reset intent checks. Shared systemd execution remains explicitly unsupported in paid mode, including at host-key enrollment. No model-runner work is treated as free overhead. No checkout/readiness flag is enabled by these migrations.

For a disposable-node pilot, package with `node scripts/package-coding-executor.mjs --out <new-directory>`. The package includes the independent guard executable/unit and an explicit executor drop-in. Install the guard before opting the reviewed executor configuration into `paidComputers:true`. Enroll the SHA-256 of a unique 43–128-character base64url host credential in the private `qorpera_computer_executor_keys` table, bound to the environment, executor owner and host machine hash. Load the plaintext only through the drop-in's `qorpera-coding-computer-executor` systemd credential. The general runtime service credential cannot enroll a host or invoke paid meter operations by itself.

Retain the guard's entire private host journal across package upgrades, including `prestarts.json` and `archive/`. It refuses new permits at 4,096 active records; existing stop enforcement continues. Controllers automatically archive settled version 2 attempts through the private guard socket. Historical receipts and exact replay denial remain permanent. Never delete journal entries to make an uncertain computer restart. Never release an orphan hold without establishing physical stop and closing queued start custody.

### Recovery before a paid start

Migration `20260927011500` adds version 2 prepare receipts and an immutable prestart record. Before either prepare RPC, the guard fsyncs an intent containing the exact non-secret request, host boot, allocation, instance digest and journal incarnation. Coding lease tokens and executor credentials are excluded. The original registration clock bounds the initial deadline; replay never renews it.

If preparation fails before start dispatch, the guard can fsync an irreversible abandonment decision. Protected coding/runtime abandonment RPCs then close only an untouched generation-one permit and return its original reserved shares with zero debit. If prepare never committed, SQL stores a tombstone that rejects a delayed prepare. Lost replies retry the same decision. Ordinary service credentials cannot authorize abandonment, and an expired deadline or absent VM alone is insufficient evidence.

Financial cancellation does not release physical capacity. Native create requests explicitly disable autostart and retain dispatch custody: an uncertain create may still materialize, so its allocation remains held until exact physical cleanup is confirmed. Office journals retain a terminal abandoned-start outcome and workers report `OFFICE_PAID_START_ABANDONED`; they do not invent a successful LXD operation or fall back to an unguarded start. Coding retains the attempt identity across a claim retry and checks guard ownership before routing any start.

Recovery enumerates prepared-only guard intents as well as attached machines. Read-only historical RPCs authenticate the original host enrollment and exact retained request, so a closed attempt remains recoverable after a native run or office generation changes. Legacy holds without trustworthy prestart evidence remain operator recovery cases. A dispatched start always uses existing physical stop and measured-settlement recovery; it cannot be converted into zero-use cancellation.

The guard archives terminal decisions and normally retired intents only after a validated SQL closure. Every attached guard must have a durable stopped receipt with any dispatched start settled; prestart-only abandonment requires its exact zero-debit SQL receipt. Legacy records and inconsistent or skipped generations remain active for reconciliation.

Lost-renewal recovery accepts the stopped guard's current SQL window or its immediate successor. The successor requires a successful settled start, identical permit/epoch/host/prestart/resource identity, the same physical machine and guest identity when previously bound, a distinct reservation and an advancing window. The original guard generation, deadline and physical stop receipt remain unchanged in the archive alongside the newer SQL closure. No terminal recovery calls `arm` or grants another start. A valid renewal can commit after the old stop cutoff while waiting on allowance locks; its late issue timestamp alone does not invalidate terminal settlement.

Controllers refresh the exact historical permit and observation predecessor before finishing a stopped version 2 attempt. They use the original enrollment even after the live source moves, recover an already committed finish without repeating settlement, and stop accounting/renewal attempts while the guard is stopping or its generation differs. Migration `20260927011600` moves only coding **finish** authentication to the original prestart enrollment; revoked or mismatched host keys remain refused. Runtime finish already uses its retained host context. Prepare, bind, checkpoint and renewal retain their existing live authority requirements. SQL settles the newest reservation against the last proven checkpoint; terminal recovery adds no guessed active time or duplicate debit.

Archival first fsyncs an immutable receipt file in a SHA-256 chain, then atomically fsyncs the chain count/head and remaining active intents in the version 2 `prestarts.json` snapshot, and only then removes the redundant active guard file. Startup validates the entire anchored chain before cleanup. It completes an interrupted unanchored tail only when the original active records match exactly; missing files, differing duplicates, corrupt chains or a missing anchor refuse initialization. An uncertain write closes admission until guard restart/recovery. Historical status, cancellation and stop receipts remain readable, and archived attempts cannot register, arm or start again. Active recovery enumeration excludes archived entries; an archive-aware ownership query prevents cancelled coding attempts from falling back to unguarded start.

Keep the anchor, active files and archive together in backups. Restore them as one consistent journal while the daemon is stopped; never prune individual files or restore an older journal to reopen an attempt. Local hashes detect partial loss/corruption, not deliberate rollback of an entire consistent backup. The archive has no expiry or lossy compaction: disk usage and the exact in-memory index grow with history, and startup verifies that history before the guard begins sweeping. Monitor disk capacity; exhaustion fails closed and still requires operator recovery. Exercise interruption, disk-failure recovery and worst-case restart latency with retained history and active VMs on the disposable Linux pilot before sustained production use.

Current integration points:

- Coding: `coding-executor-host.ts` consumes paid admission and delegates start/stop to `coding-computer-controller.ts` and the independent guard. `#sleep` still performs ordinary cleanup and suspends node demand after physical stop. Guard expiry may stop a live leased turn; ordinary housekeeping authority does not override the paid deadline.
- Shared company computers: `lxd-office-paid-computer.ts` connects creation, boot, resume and reset to the generic controller. Funding is reserved for the exact durable VM start command; operation recovery uses the guard's original LXD reference. An independent five-second loop maintains usage while adoption, NAS or guest operations are busy. Normal lifecycle stop settles only after physical stop. Confirmed unexpected stops receive a separate outage report and revoke admission. An opt-in retained-VM outage restart lane provides recovery; actual node failure acceptance remains a rollout blocker.
- Native per-run VMs: `lxd-provider.ts` uses the protected permit before create/start, binds physical/guest identity before assignment, and delegates paid start/stop to the independent guard. Its five-second maintenance loop runs separately from bootstrap and provider operations. Host-only credentials are not serialized into guest material or journals.
- Shared systemd execution: `shared-execution-backend.ts` calls `#reserveMachine` before starting host/runner units, then `#retire`/`#releaseMachine` after unit cleanup. It needs its own measured unit-uptime and expiry-stop adapter. LXD observations cannot stand in for these sandbox allocations.

All TypeScript paths above are under `packages/runner-orchestrator/src`. Keep provider-neutral SQL/permit definitions under one owner; provider-specific host adapters can be implemented independently. Paid readiness must cover every enabled physical path, or structurally refuse paid use on unsupported paths. Required tests include failure before/after provider dispatch, lost reserve/renew replies, cross-company contention, concurrent sessions sharing one machine, membership/pool withdrawal, host restart, database/network loss, stop failure and exact retry without duplicate debit. Run those against a disposable real node before publishing Checkout.

### Office power-loss recovery

A stopped paid guard and an orderly guest shutdown prove different things. The guard proves that the exact physical attempt has stopped and its dispatched start has settled. It does not prove that the guest saved its work, drained its private screens, or acknowledged a service-stop request.

Migration `20260927011700` and `lxd-office-computer-outage.ts` add the office outage path. It retains an exact request before reporting confirmed power loss through a dedicated host-authorized RPC. The request binds the current office activation and startup to the original paid permit, prestart identity, physical instance and stop receipt. SQL records the outage and revokes admission while preserving privacy challenges, private profiles, workbench provenance and physical allocation custody. The office remains held; outage registration creates no graceful service-stop record or restart authority. Lost report replies retry the retained request, including when the physical guard has already been archived.

The ordinary shutdown path remains separate. A maintenance transition alone does not establish orderly shutdown; only its genuine guest stop acknowledgement can do that. A stale outage report must never revoke a successor activation, and an exact completed retry must not repeat revision or drain changes. Generic funding, network or observation failures without confirmed physical stop remain held without claiming an outage.

Migration `20260927011800` adds the distinct outage restart lane. One immutable request owns a fresh paid start and successor activation on the same retained VM. An external-stop journal bridge preserves the original guard evidence without inventing a graceful shutdown. On a fresh guest boot, a protected termination inspection verifies retained preparation/adoption/configuration and mount custody, unstarted units and empty cgroups. A short-lived SQL challenge authorizes ending the exact old resources/viewers/drains while retaining privacy state/version/challenge and company profiles/files. Termination advances the office revision. Separate configuration and successor checks then install fresh boot credentials, inspect readiness and the exact service invocation, and admit the successor. Later ordinary lifecycle readers preserve the outage origin.

Power loss during an already draining maintenance transition remains held for explicit recovery when no genuine guest acknowledgement exists. Missing/replaced roots, host migration, uncertain start/journal custody, exhausted recovery budgets and configuration operations without confirmed success also remain held. Exact retries never mint a second start or rearm the stopped permit. Keep paid readiness disabled until the integrated protocol and real-node failure acceptance are complete.

### Native and office host setup

Package the independent guards with `node scripts/package-runtime-computer-guard.mjs --out <new-directory>`. Review its manifest and runtime digest, install the executable under `/opt/qorpera/computer-guard`, and install only the applicable unit/drop-in. Native uses `qorpera-provider`; office uses `qorpera-office-provider`. Each guard has its own account-private socket, persistent 0700 journal and systemd watchdog. The guards receive no database credentials and have only Unix-socket network access. Their lifetime is independent of the provider unit. The packaged units assume the standard LXD socket and `lxd` group; a different reviewed host socket/group requires matching unit arguments and a separately reviewed deployment.

Through a trusted database-owner connection, enroll `qorpera_runtime_computer_host_keys` with the exact node, provider kind/ID, policy digest, host machine hash, CPU/RAM shape and `backend='lxd'`, plus the SHA-256 of a distinct high-entropy executor secret. This table has no service-role enrollment RPC. Office requires the pinned bootstrap digest. Native may use a null expected bootstrap because its generated per-run bytes contain credentials; each permit still retains the exact generated digest, and changed recovery context is refused. This trusts the enrolled host's generation process; it is not independent attestation of a bootstrap template.

Keep plaintext secrets in root-owned local files, mode 0440 for the provider's dedicated primary group, with protected ancestors. Native uses `QORPERA_NATIVE_COMPUTER_EXECUTOR_SECRET_FILE`; office uses the optional `computerExecutorCredentialPath` in its protected service configuration. `RuntimeComputerHttpControl` supplies this separate credential only to the closed paid-computer RPC allowlist. The guest's service JWT cannot acquire paid control. These configuration references opt into the controller; they do not enroll a host, publish an offer, or enable a company’s paid mode.

For the reviewed office outage pilot, also set `outageImagePackageManifestPath` in that protected provider configuration. It requires `computerExecutorCredentialPath`; the provider rejects the option without paid control. The file must be the accepted guest package manifest whose byte digest equals the enrolled `guestPackageManifestSha256`, and it must contain the outage termination, configuration and service-start executables installed under `/opt/qorpera-office`. Package them with `node scripts/package-company-computer.mjs --out <new-directory>` and complete the ordinary image provenance/acceptance process. A manifest file alone cannot upgrade an old VM, change enrolled policy, or enable paid billing. Without this opt-in, confirmed paid office outages retain the previous held behavior.

Before deployment, prove real LXD stop timing and recovery with the complete host and guest packages, including stalled asynchronous journal/LXD I/O. Review the exact candidate's physical reports; a unit test or an earlier image pass cannot substitute for joined lifecycle acceptance. An absent VM cannot by itself justify returning allowance or releasing physical capacity. Only the retained, durable prestart abandonment protocol can cancel an unused hold independently of physical cleanup. Legacy/dispatched orphan and skipped-generation reconciliation remain operator cases. Archive disk-failure recovery, retained-history restart latency and deployed alert delivery still require operational acceptance. See the [accounting monitor](computer-accounting-health.md) and [billing-command recovery](computer-billing-recovery.md) runbooks; neither tool infers a refund from a timeout or an absent machine.

## Deployment prerequisites

Stripe test-mode acceptance has been exercised in an isolated account/database boundary. No production account, payment endpoint or runtime deployment is established by those tests. Configure reviewed deployment credentials separately; never use production payment credentials in unit tests.

Deploy `computer-billing` with gateway JWT verification disabled so Stripe can deliver raw webhooks. The handler verifies Stripe signatures itself; member routes separately validate their bearer token against Supabase Auth.

```toml
[functions.computer-billing]
verify_jwt = false
```

Required secrets/configuration:

- `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`: database/Auth access. Runtime guests also hold the service role, so it is not sufficient billing authority.
- `QORPERA_COMPUTER_BILLING_RPC_SECRET`: independently generated payment-bridge credential, 32–512 characters, enrolled by its SHA-256 digest in the operator-only `qorpera_computer_billing_keys` table. Keep it exclusively in the billing edge function secrets; never deliver it to browsers, guests, executors, or runtime configuration.
- `QORPERA_STRIPE_SECRET_KEY`: Stripe server key for the configured account.
- `QORPERA_STRIPE_WEBHOOK_SECRET`: endpoint signing secret, never a client key.
- `QORPERA_STRIPE_LIVE_MODE`: explicitly `false` for test, `true` only for a reviewed live deployment.
- `QORPERA_BILLING_RETURN_URL`: fixed HTTPS application URL. Its origin is the only member CORS origin.
- `QORPERA_STRIPE_PORTAL_CONFIGURATION`: reviewed Stripe portal configuration ID. The service rechecks that it is active, belongs to the configured mode, and disables subscription updates before opening a portal session.
- `QORPERA_STRIPE_PRICE_PLANS`: JSON mapping explicitly configured Stripe price IDs to catalog versions, e.g. `{"price_example":{"planKey":"basis","version":1}}`. Price currency, amount, quantity, and monthly interval are rechecked against the server catalog.

The edge adapter calls only `qorpera_computer_billing_rpc(method,args,billingSecret)`. Its explicit allowlist retains the command leases and canonical reconciliation transaction; direct funding, reconciliation, customer mapping, complimentary grants, and legacy allowance mutations are not executable by the service role. Billing tables and key enrollment have no API-role write grants. Catalog and personal balance reads keep their existing member permissions. Missing or revoked bridge credentials fail closed without exposing the secret or database response.

Enroll a freshly generated high-entropy secret through a trusted database-owner connection using bound parameters, not shell interpolation or an API RPC:

```sql
insert into public.qorpera_computer_billing_keys(key_sha256,label)
values (encode(extensions.digest(convert_to($1,'UTF8'),'sha256'),'hex'),$2);
```

`$1` is the secret stored in `QORPERA_COMPUTER_BILLING_RPC_SECRET`; `$2` identifies the deployment for rotation. Do not put either real secret in source control or SQL logs. There is deliberately no guest-accessible enrollment endpoint. Rotation can enroll a second key, switch the edge deployment, then set the old row's `revoked_at=clock_timestamp()` through the operator connection. Revocation waits for already authorized transactions to finish; it does not invalidate their immutable receipts. Never remove or reset command/event records to recover a rejected secret. The billing bridge secret and physical executor secret serve different authorities and must be different values.

Pin the Stripe webhook endpoint API version to `2026-08-26.dahlia`, matching outbound requests. Subscribe to `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`, `invoice.payment_action_required`, `charge.refunded`, `charge.refund.updated`, the `charge.dispute.*` events, `refund.created`, `refund.updated`, `refund.failed`, `credit_note.created`, `credit_note.updated`, and `credit_note.voided`. Endpoint URL: `/functions/v1/computer-billing/webhook`.

After publication, Checkout creates the authenticated member's Stripe customer using a durable server command and then atomically records its immutable mapping. Existing verified customers can be mapped only by a trusted database operator through `qorpera_map_computer_billing_customer`; the service role cannot call it directly. Members cannot supply customer IDs. Customer and Checkout commands have stable provider idempotency keys and database leases; a second request UUID cannot create another open payable session. Ambiguous creates older than 23 hours stop for provider reconciliation because Stripe can prune idempotency keys after 24 hours. Resolve those commands by verifying the exact existing Stripe customer/session before recording a result; never clear the command and blindly create another object.

## Routes and payment truth

- `POST /computer-billing/webhook`: verifies bounded raw-body HMAC and a five-minute signature timestamp window; rejects wrong mode/version. Claims a database lease per subscription and retrieves its canonical Stripe state. For `invoice.paid`, also retrieves the canonical invoice and validates paid status, customer, subscription, one configured non-prorated monthly line and its service period. Snapshot, invoice funding and event completion commit atomically. Old events trigger current retrieval rather than rewind state; an old paid period stays expired. Exact completed retries do not fetch again; changed replays fail. Original event timestamps/body digests remain in the inbox. Canonical retrieval times order snapshots, including events created in the same Stripe second. Unsupported adjustments/prorations require reconciliation and cannot mint a second full allowance.
- `POST /computer-billing/portal`, body `{}`: authenticated user's mapped customer only, with fixed configured return URL. Returns a hosted `billing.stripe.com` URL. Members cannot choose another customer or return address. Configure the portal without plan updates until checkout publication and the tariff are ready.
- `POST /computer-billing/checkout`, body containing `planKey`, `version`, and UUID `requestId`: authenticates, checks the server catalog/readiness and configured Stripe price, then creates the customer and hosted subscription Checkout using durable commands. Before creating another session it also checks canonical customer subscriptions, so a late payment webhook cannot allow a duplicate purchase after session expiry. Returns `{url,expiresAt}` for the resulting `checkout.stripe.com` session. Retry the same member/offer request ID after a lost reply; retain it until the known session expiry. Unpublished offers are rejected before customer/session creation. Success/cancel URLs come only from server configuration.

A successful browser redirect never grants access. Stripe subscription status alone also does not grant paid runtime allowance in the shadow phase. Provider timeouts and database errors return retryable failure without exposing provider responses, tokens, or secrets. Monitor webhook delivery failures and unmapped/unsupported subscriptions before enabling a live deployment.

Canonical refunds, disputes and credit notes update an invoice's funding authority under the same subscription serialization. New holds exclude fenced funding; a reduced cap never erases already authorized holds or debits. Failed refunds, won disputes and void credits restore only canonically verified funding. The original issued allowance, paid period and plan remain immutable. Delayed events cannot independently issue a second full period. Recovery of a billing command older than the idempotency retention boundary requires positive, immutable proof of its exact existing Stripe result; an empty search never unlocks another purchase.
